# The checkup: reviewing the whole tree at a pause

How the tree on `main` is reviewed against the standards at a pause, a checkpoint merged or a step of the build order begun (`docs/process/best-practices.md`, rule 9): a model-driven review, run from a session of its own, over the whole tree rather than a diff, whose findings are issues the owner triages (`docs/process/code-changes.md`, rule 28). It is the third layer of decision 0033, above lint and the review skill (`docs/runbooks/review-change.md`), and reports nothing those two catch. The Claude Code skill `.claude/skills/checkup/` points here, and decision 0034 records why a finding is an issue. The rules below are the procedure; the brief the session works from is at the end.

## Rules

1. **When, and by whom.** At a pause, in a session started for the checkup and nothing else, never one with an issue in flight. The owner starts it, or starts it from the card a session proposes at the pause; the session is given the brief below and the background the app requires, and no steps of its own. It runs over the whole tree, or over one area of rule 4's table when the owner names one: after a triage, to pick up what the cap of rule 7 left, or when a step of the build order touched one area.
2. **The tree is `main`, read in place.** The session reads the checkout, which must be a clean `main` at `origin/main` after `git fetch origin` (`git status --porcelain` prints nothing and `git rev-parse HEAD` equals `git rev-parse origin/main`); otherwise it stops and says so, and does not stash, reset or switch. It makes no worktree and changes no file. Its only writes are the issues of rule 8 and, where they are missing, the labels of rule 9. It reports the commit it reviewed.
3. **Lint has run.** The latest "Build and test" run on `main` is green (`gh run list --branch main --workflow "Build and test" --limit 1`); where it is red or still running, the session says so and stops. The checkup reports nothing a lint rule or tflint expresses (`docs/standards/typescript.md`, rule 16; `docs/standards/terraform.md`, rule 17).
4. **One pass per area.** Each area is reviewed in a pass of its own, with only that area's documents and files in view, so that a pass reads one rubric closely rather than every rubric thinly; the passes may run beside each other. A pass reads its documents in full before any file, then every file under its paths, and reports its findings in the format of rule 6 to the session, which reads the cited lines itself before it files anything (rule 8). The brief a pass is given is the brief at the end of this document, with the area filled in.

   | Area | Paths | Documents |
   | --- | --- | --- |
   | Packages | `packages/**`, `scripts/**`, `manifest.json`, `package.json`, `tsconfig*.json`, `eslint.config.mjs`, `.node-version` | `docs/standards/typescript.md` |
   | Client | `packages/client/**` | `docs/standards/angular.md`, beside `typescript.md` |
   | Hub | `packages/hub/**` | `docs/standards/graphql.md`, beside `typescript.md` |
   | Terraform | `terraform/**` | `docs/standards/terraform.md` |
   | Pipeline | `.github/**`, `.claude/settings.json`, `terraform/allowed-resource-types.txt` | `docs/process/code-changes.md` and `docs/process/best-practices.md`, which hold the guardrails |
   | Documents | `docs/**`, `AGENTS.md`, `CLAUDE.md`, every `AGENTS.md` and `CLAUDE.md` under an area, `.claude/skills/**` | `docs/README.md`; `docs/decisions/README.md` for `docs/decisions/**` |
   | Art | `art/**` | `docs/process/assets.md` |

   The Packages pass reads the engine and what is common to every package; the Client and Hub passes read their package under their own document, with `typescript.md` beside it, and report only against their own document what the Packages pass would otherwise report twice.
5. **The documents pass does the sweep, and asks the drift questions.** Beside its rubric it does what `docs/README.md` rule 8 names for a pause: history that has crept into a design or process document is a finding under that rule, and a document that describes as built, applied or enforced what is not is one under rule 6. Every item under a standards document's "Held back" is checked: its issue exists and is open, or the item is stale (rule 5 of `docs/README.md`). Then, for each standards document, the two questions of `docs/process/best-practices.md`, rule 9: does the shape still fit the requirements, and has current guidance moved from what the document states as practice. A claim that guidance has moved is checked against the provider's or the framework's documentation, not recalled, and names the page read and the date (best-practices, rule 3). A drift that breaches a numbered rule, a major not taken under `typescript.md` rule 1, a practice stated and not followed, is a finding; one that breaches none is raised in the session as rule 10 says, never filed.
6. **A finding cites one rule.** Each finding is one breach of one numbered rule of one of the documents in rule 4's table: the severity, the document and rule number, the files with their lines, what breaches the rule, and a proposed shape of the fix, in a few lines. The severities are those of the review skill: **blocks**, a breach of a rule that guards a guardrail, security, a secret, records or money; **fix**, any other rule breached; and **note**, a breach with no effect beyond the reader. A rule a document lists under "Held back" is not breached by code it names as held back. An ambiguous rule is read as its document's "Why" section means it; where it is still ambiguous, nothing is reported. Zero findings is a checkup, not a failure.
7. **Deduplicated, then capped.** Before anything is filed the session reads every issue labeled `finding`, open and closed (`gh issue list --label finding --state all --limit 200 --json number,title,state,labels,body`). The same rule on the same file as an open `finding` is already filed and is skipped; as a `finding` closed with the label `excused` it is excused and is skipped, however long ago; as a `finding` closed without that label it was fixed and has come back, so it is filed anew and its body names the old issue. At most 10 issues are filed per run, the most serious first and, within a severity, in the order of rule 4's table; what the cap leaves is counted per area and severity in the session's final message, and a later run of that area picks it up.
8. **A finding is an issue.** One issue per finding, created with `gh issue create --title <title> --body-file <file> --label finding --milestone <milestone>`, the body written to a file first. The title says what is wrong and where, in plain words, under about 80 characters, with no severity or rule in it. The body opens with the line `**Checkup · <severity> · <document>, rule N**`, then the files and lines, the breach, the proposed shape of the fix, the line `Reviewed <short commit> on main, <date>.` and, after a blank line, the closing line `_🤖 Filed by the checkup skill ([Claude Code](https://claude.com/claude-code))_`, because the issue is created under the owner's login and a reader must be able to tell. The milestone is "1 Platform", the housekeeping milestone, unless the fix changes what the player sees, when it is the milestone of the build-order step that owns that feature (`docs/architecture/overview.md`, "Build order"). No assignee and no other label.
9. **Two labels, with descriptions.** `finding`: "Checkup finding: one breach of one rule. Open is accepted; closed with excused is not raised again." `excused`: "Closed by the owner with a one-line reason; the checkup does not raise it again." A description is at most 100 characters, GitHub's limit. Created once, by the pull request that introduced this runbook; where either is missing, the session creates it with that description (`gh label create <name> --description <text>`) before filing, and says so.
10. **Candidate rules go to the owner, in the session.** What a pass would report but no numbered rule covers is not a finding. The session's final message lists each as a rule worded for the document it would join, with the place that prompted it, and asks the owner; an accepted one is filed before the session ends, as an issue under "1 Platform" for the document change, labeled `documentation`, since chat is the one surface nothing reads back (`docs/process/collaboration.md`, "In practice"). A rejected one is dropped.
11. **The owner triages on GitHub** (`docs/process/code-changes.md`, rule 28). A `finding` left open is accepted and is a checkpoint worked like any other; closed with the label `excused` and a one-line comment giving the reason, it is excused and the closed issue is the record; closed without that label, it was fixed. The session that ran the checkup fixes nothing and decides nothing.

## The session's brief

What the checkup session is told when it starts, with the area filled in where the owner names one. Nothing is added to it.

```text
Run the checkup of the HEAT repository, following docs/runbooks/checkup.md on main: review the whole tree (or only the area <area>) against the numbered rules of the documents the runbook's table maps to each area, from a clean checkout at origin/main. Read every finding issue, open and closed, before filing anything. Report only a breach of a numbered rule, cited by document and number, with the file and lines; what no rule covers is a candidate rule for the owner, in your final message. Deduplicate, cap and file as the runbook's rules 7 and 8 say. Change no file, make no worktree, push nothing, fix nothing. Read an ambiguous rule as its document's "Why" section means it; where it is still ambiguous, do not report. A rule a document lists under "Held back" is not breached by code it names as held back.
```

The brief a pass is given adds its row of the table, the finding format of rule 6, and the instruction to read nothing outside its paths and documents.

## Why

The checkup reviews the tree in place rather than a diff because the review skill already reads every change as it lands and lint already fails what it can express; what neither sees is the shape that forms across changes, a rule added after the code it would have governed, a document that drifted from the code, a hold-back whose issue closed. Those are visible only in the whole tree, and only at a pause, when nothing is in flight to confuse the reading.

A finding is an issue because the open issues are the backlog and there is no other list (`docs/process/code-changes.md`, rule 1): a finding that is accepted has to become a checkpoint, and the issue already is one. The closed issue with `excused` is the suppression record for the same reason in reverse: the decision not to fix something is made where the finding was made, by the owner, with a reason, on a surface a later session reads cold and a phone shows. A file of suppressions in the tree would be a second list, and a report comment would be read once (decision 0034).

One pass per area, each with one rubric, because a reader given every rule reads each thinly, and because the rubrics were written one per area for the same reason. The cap exists because ten issues are triaged and forty are skimmed, and because a run on the subscription is bounded by its usage limits (decision 0033). The session reads each cited line before filing because a pass reports in the same confident register whether it is right or wrong, and an issue is a durable thing.
