# What enforces the process

Which of the rules in `docs/process/code-changes.md` a mechanism holds, and which are an agreement only. It was that document's own section until Issue-363, which moved it here because a session needs the rules at its start and needs this list only when it changes a hook, a ruleset or a workflow.

Most of `docs/process/code-changes.md` is an agreement, not a mechanism. What is enforced today:

- `.claude/settings.json` denies an agent the commands `git push origin main`, `git push origin HEAD:main`, the same two for `release`, pushes of `v*` tags and `gh pr merge`. This is a guardrail against the obvious forms, not a guarantee: a command pattern can be worded around. It is also the only guard GitHub's side cannot give: the agent pushes with the owner's credentials, so a ruleset that names the owner names the agent too.
- `.claude/settings.json` also wires two hooks from `.claude/hooks/`, which every session of this repository runs. `allow-npm-in-worktree.mjs` is a loosening, and the only one (decision 0054): in an issue's worktree it answers "allow" for `npm test`, `npm ci`, `npm start` and `npm run <script>`, with the workspace options and the script's own arguments after `--`, optionally piped into `tail`, `head`, `grep`, `wc`, `cut` or `tr`, and for an `echo` between them; for everything else it answers nothing, `npx` and every other npm option among them, and the command goes through the session's normal permission flow: a prompt, or in auto mode the classifier, which runs or refuses it without asking, until repeated refusals bring the prompt back. It is a convenience and not a boundary: those scripts run what the branch holds, which the agent writes. `wrap-up-no-promises.mjs` refuses an end-of-turn box that promises content to come (`docs/process/sessions.md`, rule 11). A hook that answers "allow" is tested: `.claude/hooks/*.test.mjs`, run by `npm test`, lists the commands each hook must allow and the ones it must refuse, a pipe into each filter it admits and each option of each command included, and a change to what a hook allows changes its test and this paragraph together.
- The agent's AWS profiles carry read-only roles. An agent cannot apply Terraform or run a changing command, even by mistake. The plan role of decision 0017, when it exists, is read only as well.
- The repository's merge settings allow merge commits only; the squash and rebase buttons are off.
- The "Build and test" workflow runs on every pull request and on `main`: typecheck, lint (`docs/standards/typescript.md`, rule 16), tests, schema currency, bundling, that `.github/workflows/actions.lock` covers every action the workflows use, at commits that still verify upstream (decision 0047), and the size of what the root `AGENTS.md` loads (`docs/README.md`, rule 3; decision 0060). Its four jobs report four checks, "Build and test", "Lint the stylesheets" (stylelint, `docs/standards/angular.md`, rule 17; Issue-384), "Terraform format, validate, lint and scan" and "Lint the workflows", and both rulesets below require all four to pass.
- **Two rulesets, defined in `.github/rulesets/` and applied by the owner.** `main` (2026-10-15): changes only through a pull request, merge commits only, the four checks of "Build and test" passing on a branch that is current with `main`, review threads resolved, no force pushes, no deletion, and no bypass, so the owner's own changes go through the same door. `release` (Issue-41): the same, with two differences. Its checks are not strict, because after a release the tip of `release` is a merge commit that is not on `main`, and a strict check would hold every second release; and it requires one more check, "Release source", the guard job of `release.yml`, which refuses a pull request whose head is not `main` or a `hotfix/<issue>-*` branch, or whose target `release` carries content beyond its merge base with the head, so a hotfix on `release` has to be merged into `main` before the next release (decision 0021 as amended). The `release-tags` ruleset it replaces let only an organization owner create a `v*` tag; the tag is no longer the gate, and the workflow writes it. A change to a ruleset is a change to its file here, reviewed, then applied by the owner with `gh api --method PUT`. Which jobs they require is rule 29 of that document.

What is not enforced yet:

- **The pipeline's applies and their guardrails.** Rules 18, 22 to 24 and 26 of that document describe the shape decided on 2026-10-16 and 2026-10-17 (decisions 0017, 0018, 0020 and 0021). The roles exist (Issue-36, applied 2026-10-16), and `deploy.yml` plans a permanent root on its pull request and applies it on the merge (Issue-37); since Issue-40 `dev` is one of those roots, with a smoke test after its apply. Since Issue-38 every working branch has a stack, applied by `sandbox.yml` on every push, with its API URL in the run summary and, since Issue-39, its hostname. Since Issue-41 `release.yml` plans `prod` on the pull request to `release`, applies it on the merge behind the guard, runs the token-free smoke test and writes the tag and the Release; the first release ran on 2026-10-18 (Issue-64), and the procedure as it has run is `docs/process/deployment.md`. The rules are written for the shape being built so that the issues building it have one text to build to.
- **The actions lockfile at run time.** Until the owner turns on the repository's "Require lockfile" policy (Issue-245), the runner uses the lockfile's commits for a workflow it covers (observed on run 42503840764), and nothing requires a workflow to be covered; "Lint the workflows", a required check of "Build and test", refusing an uncovered workflow is what stands in until then.
- **Signed commits.** The agent's commits are unsigned, and the `main` ruleset does not require signatures. Deferred until the agent has a signing key; what it leaves open is that authorship in the log is asserted, not proven.
