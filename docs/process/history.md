# How the process rules got here

The dated accounts behind the rules of the documents in this directory: what happened, in which session, and what was tried first. Each document's rules say what to do, with a clause of reason and a reference, an issue's number or a decision's; the account that reference stands for is here, under its document, and opens with its rule's number, or with the practice's name where `collaboration.md` numbers none.

Nothing loads this file, and no session reads it at its start (`docs/README.md`, rule 17). It is read when a rule's reason is in doubt, or when a rule is about to be changed, by a search for the rule's number under its document's heading. An account is added here in the pull request that adds or changes the rule, and is not rewritten afterwards.

## collaboration.md

In practice, the recommended shape and the identity terms. The two practices added on 2026-10-13 come from the AWS review that preceded the platform work, and match the same two in the `dcg-platform` repository. A menu of options pushed the identity decisions back onto the owner, who does not want to be the identity expert; a recommendation with its reason did not. And "account" and "user" each name several different things in AWS, so a sentence that does not say which kind is a sentence that can be misread.

In practice, a missing tool is asked for. The practice added on 2026-10-14 comes from the first code: Docker was missing on the owner's machine while the agreed local design runs its stand-ins as containers, and the agent downloaded a jar instead of asking. It worked, and it would have made the laptop's tests differ from CI's, which is the kind of difference that surfaces weeks later as "it passed for me". A workaround that keeps the work moving is the wrong trade when the thing it works around is the environment itself.

In practice, what is handed to the owner. The delivery practice added on 2026-10-17 comes from the Issue-37 session: a turn's summary said a checklist was "below", the summary ended the turn, and the checklist was never written. Chat is the one surface in this workflow that nothing reads back, so what the owner is owed has to be complete before the summary or live on GitHub. The first attempt put the items on the checkpoint's issue, which the merge had already closed; a closed issue is off the backlog, which is why the after-merge items go to a follow-up issue.

In practice, PR-n and Issue-n. The naming practice added on 2026-10-16 comes from the cloud-first pivot of that day, when pull requests, issues and the numbered decision records were all in one conversation and "#34" could mean two things. GitHub renders `#n` as a link to whichever of the two it finds, so the prefix is the only thing that disambiguates a number in prose.

## code-changes.md

The cycle, rules 20 to 28. Agreed 2026-10-15; rules 21, 22 and 24 to 27 rewritten 2026-10-16 for the cloud-first shape (decisions 0017 and 0018); rules 23 and 24 gained Auto-fix and the review skill 2026-10-25 (decision 0033).

Rules 5 and 18. **Production through a release branch.** The tag applied `prod` in the run that planned it, and the repository, private on the Team plan at the time, could have no required reviewers, so nobody could read the `prod` plan before the apply. A pull request from `main` to `release` is a review surface that already exists; the tag then records the release instead of causing it (decision 0021). The repository has been public since 2026-11-02 (Issue-178), which makes required reviewers available; they are not added while the repository has one person, who would only be approving their own merge (decision 0011's status line).

Rule 20. **One issue per session.** A long session accumulates context the next issue does not need. A fresh session finds everything from the issue, its comments and the documents `AGENTS.md` names; the private working context adds only what cannot be committed. Until Issue-318 that file also carried the state of the work, a second backlog beside the one rule 1 names, which only one laptop could read.

Rule 25. **The backend ends with the apply too.** The rule named the `bootstrap` stack as the one the owner applies, and the backend stack, which only the owner can apply either, had not changed since the rule was written. Issue-270 changed it, a tag and `prevent_destroy` on the state bucket, and the review of PR-433 on 2026-11-27 found that nothing said whether its apply and its README's status line come before the merge; the pull request was already doing both, and the owner accepted the rule the same day. The same applies showed that a plan can hide a policy: where a policy document refers to a resource with a change pending, Terraform reads it at apply and the plan prints `(known after apply)`, so the agent read each saved plan and compared its document with the policy in place before the owner applied.

Rule 30. **Done where it is found.** Every issue filed for later is a session to start, a context to read cold and a pull request to review, and by 2026-11-10 the open list was growing faster than the work moved (the owner). The review of PR-293 found the overview past the length its rule allows, and the first answer offered was an issue; the owner's call was to split it there, and to write that down. One purpose still bounds what a pull request sets out to do; it does not send what the work turns up to the backlog.

Rules 20 to 28. The earlier shapes of this cycle, the owner applying every stack and the branch staying checked out under the IDE, are recorded in decisions 0011, 0017 and 0018.

## best-practices.md

Rule 2. The rule to propose the recommended approach first comes from a real miss. The first plan for command-line access to the project's AWS accounts reused a long-lived access key on a user in the organization's management account, because that matched an existing setup. The recommended practice is single sign-on with short-lived credentials. The project owner caught it. The shortcut should never have been the first thing proposed.

The sentence added to rule 3 on 2026-10-13, and rules 7 and 8, come from the organization-level work in the `dcg-platform` repository. Console descriptions given from memory were wrong more than once during the AWS review; descriptions checked against the documentation were not. Rules 7 and 8 describe how every stack in the organization treats what already exists, and HEAT's accounts are Control Tower accounts, so they apply here as they do there.

Rule 9 was added on 2026-10-16, after the Terraform layout changed from one configuration per stack to one root directory per environment (decision 0016). The first shape had been fitted to a second environment with a `-reconfigure` flag and a map of account ids. It worked, it would have been built upon, and the owner asked for the question to be put the other way round. A workaround hides the mismatch; the next requirement lands on the workaround, and the cost of moving compounds. Paying for the move early is the cheaper habit, and a periodic review is how the need for one is noticed.

Rules 10 to 12 were added on 2026-11-02 (Issue-186), when the review of its pull request found the header's height written twice, as `2.25rem` in the stylesheet and `36` in the layout arithmetic, each true only at the browser's default font size, and the first answer offered was to decline the finding as older than the change. The owner's call was the opposite: the page follows the player's settings, a shape found wrong is reopened where it is found, and the practice goes into the documents in the same pull request, because a note or an issue for later is how the two copies had survived.

Rule 13 was added on 2026-11-04 (Issue-202), from the review of PR-230, which found the browser test's install step and Chromium running with the apply role's keys in their environment when the test needed one parameter read. A browser and a package's install step run code the project did not write, and the role can change the stack. It was rewritten from a step to a job on 2026-11-06 (Issue-231, decision 0046), when the work of meeting it showed that a step with its keys removed could still reach the role. Its sentence on declared permissions came from the review of PR-240: a job that inherited the workflow's `permissions` held no role only while the default stayed narrow.

Rule 14 was added on 2026-11-08 (Issue-241), from the review of PR-244, which locked every action to a commit and found the step that verifies the lockfile installing its own tool by a release tag, the exposure the change closed for every `uses:`. `gh extension install --pin` takes only a tag for a binary extension, so the release's binary is downloaded and its attestation verified, as actionlint's already was; applying the rule the same day found tflint taken by its tag through `setup-tflint`, which now pins the archive's checksum. Its sentence on what an action downloads was added on 2026-11-09 (Issue-267), from the checkup of 2a146cf: `setup-terraform` with no version took the latest Terraform, and `setup-node` took Node 24 by its major, each downloading with no check, in the jobs that plan and apply `prod`. Both are now one exact release with a pinned checksum, in every job; decision 0048 records why, and the newest patch verified by its signature that was refused. Its sentence on a publisher that signs nothing is a candidate rule from the review of PR-425 (Issue-396), accepted by the owner on 2026-11-27: Chrome for Testing publishes no signature, and the headless shell's checksum was read from Playwright's CDN and from Google's bucket, which served the same bytes.

Rule 15 was added on 2026-11-17 (Issue-318), from the review of PR-321. A hook that let the repository's npm scripts run without a prompt had lived in one laptop's settings for three weeks on the strength of a sentence in a chat; moved into the repository, it was described as allowing four commands "and nothing else", and the review ran a command of its own through a pipe into `sed`. A permission nobody wrote down is a permission nobody read. Its clause on permission modes was added the same day (Issue-320), from the review of PR-322: the record and the cycle both said that what the hook leaves alone "still asks", and the check of the committed hook ran in a session in auto mode, where the classifier ran an `npx` command with no prompt.

Rule 16 was added on 2026-11-19 (Issue-328), a candidate rule from the review of PR-333 that the owner accepted. The trace report was the first job to read another run's artifact, under a role, and it already took the artifact only from `main` and checked every value; nothing said that the next job to read one must do the same, and an artifact is the one input a job has that another run wrote.

## assets.md

Rule 7. The first party's sets left 23 characters that were not kept and carried no tag, findable only by name (Issue-76).

Rules 8 to 13. Each rule in rules 8 to 13 was chosen by the owner after looking at the alternatives in the game's own scale and setting on 2026-10-18; decision 0025 lists what was tried. The set is the same for every class so that a class's pool of sprite sets can grow by adding sets, with no per-class art rules.

Rules 10 and 11, hand edits and the mirrored west still. Re-rolling a look for one bad pixel throws away a look the owner otherwise kept, and an edit made before animation carries into every frame. A west rotation can be bad where the east one is not, and the mirror is what the animations already use for west. Both were added with the first party's sets (Issue-73), with the cost read from their receipts.

Rule 11, frames lined up by the feet. PixelLab places the figure differently on each animation's canvas: in most sets the walk south stands about 8 px higher than the other directions, and every `down` ends with the body 9 to 11 px above where the feet stood. Measuring from the pixels fixes every set, present and future, without editing the exported files (Issue-73).

Rules 14 to 19. Rules 14 to 19 were chosen by the owner in a mock-up of the first camp (Issue-80, decision 0027). A tileset gives every location the same ground in the same style, laid out by the scene; a painted background would have to be redrawn whenever a camp's facilities change, and two players' camps at one location can have different ones. A facility is one sprite because a building assembled from 16 px wall pieces is boxy at this scale. A level keeps its canvas and angle so that an upgrade swaps the picture in place.

Rules 25 to 27. Rules 25 to 27 come from the first pack (Issue-89): the page's menu needed an icon per facility and the client still had Angular's default favicon. One call for every icon keeps them in one style and costs less than one call per icon; PixelLab's own panel tool (`create_ui_asset`) draws panels of 192 px and up, not icons. 32 px is the favicon's own size and reads at 1× in a menu. A resource's icon came with hide (Issue-340), the first resource to have one. Its pack, the third, was rolled with ideas for timber, ore and cloth beside hide, and only hide was kept then; timber and ore were picked from it when the scene came to draw a drop (Issue-344), at no generation: icons of one kind rolled in one call share its style, where a second call may not match the first. The second pack had already carried later facilities' ideas for the same reason. Rule 27's sentence on a pack's own entry is a candidate rule from the review of PR-346, accepted by the owner on 2026-11-20: `chosenBy` and `verified` stood at the top of the file and gained a sentence for every pack, the rejects of the third were in a note while the first's had a field, and the first pack's five icons named a candidate and no pack, so that candidate 0 was said of two icons from two packs. The actions' icons came with the page's frames (Issue-385), from the fifth and sixth packs: `depart`, crossed swords, since leaving the camp almost always means a fight; `recruit`, `build`, `replays`, `settings` and `more`; and two ways out, `close`, a red X, for a view that sits over the camp, a replay, the open adventure or a menu, and `back`, a green arrow, kept for where a view steps back through others rather than closing.

Rules 28 to 31. Rules 28 to 31 come from the first battle's art (Issue-111). A monster is a hero's set so that whatever draws a hero draws a monster. The quadruped's rows were found by trying: `skeleton-v3` refused the wolf ("no stored 3D skeleton"), uncharged, and the dog template has walks and idles but nothing that fights. The tree's first `down`, described alone, broke the trunk into a stump and left the crown floating in the air; its first `hit` drew white puffs at the trunk, an effect sprite by another name. Interpolated to a stump, the crown still vanished between two frames, whether it lifted, sank or was asked to fade, because PixelLab has no partial transparency; the owner chose the fade drawn in code, starting on the first frame rather than after the last. The owner also chose the stump state and the interpolation, and waived the wolf's lunge and flinch drifts on sight.

Rules 32 to 35. Rules 32 to 35 come from the first action sprites (Issue-130), with the shape the owner gave on Issue-15: both sprites, the weapon by unit type for now, one effect per ability, and a projectile as a target effect that moves. PixelLab's effects tool was tried first on one slash: it exports the effect apart from the sprite with its offset from the feet, and the balance read the same before and after. Its parts come out a cold blue and glowing, so each is given a warm ramp. The weapons came from one pack for 10 generations, like the icons. The first swings showed why each frame's grip is recorded: PixelLab turned the sword about the canvas's centre, so its pommel moved from bottom left to top left, and drew the axe turning about its head and the dagger's blade bending into a hook. Described more closely, the axe only rocked up and back and the dagger still grew a hook. Given an end frame, the icon turned a right angle, both turned about the hand from up to down through level; a right angle is the one turn that does not blur pixel art (game.md, "How the game looks"), and the frames between are still PixelLab's. The sword, made first without one, swung well enough to keep. The hand's point was measured, not guessed: on the act's hold frame every hero set's leading fist stands 10 to 13 px ahead of the canvas's centre and 20 px above the feet, because every set is made on one skeleton.

Rules 5, 28, 33 and 35, the ranged units' art.
