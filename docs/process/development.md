# Development

How a change is run and seen while it is being made. The system runs in the branch's sandbox stack; the laptop runs the fast loop. Nothing emulates AWS (decision 0018).

## Rules

1. **The stack is the system.** Every working branch has a stack, `heat-sb<issue>`, in `heat-sandbox`, created by the first push and re-applied by every push (`.github/workflows/sandbox.yml`). Running the system means pushing to the branch. After the apply, the run publishes the client build and `config.json` into the stack's bucket and tests the stack as a browser would, through its hostname `https://<issue>.heat-sb.dcg-games.com`: it reads the page and `config.json`, checks that the managed login page answers for the stack's browser client and that the authorize endpoint hands off to Google, is refused at `/graphql` without a token, mints the stack's own test user `e2e-<issue>` in the shared pool with a random password that lives only in that job, signs in through the `ci` client, recruits the free villager if the camp has none, is refused a fighter for want of ore unless an earlier run left it some, closes any adventure an earlier run left open the way the client does (submit to `/graphql`, then to `/previous/graphql`, then discard), starts "Timber from the near woods" with the villager through `/graphql` and checks the open adventure on `me`, stamped with `config.json`'s version, the refusals of a second start and of the villager's retirement, and the outdated flag, then submits it with no overrides and checks that the hub's result is the engine's own replay of the snapshot and seed, that every reward was credited or lost at the warehouse's cap and the holdings rose by what was credited, that the villager came home with the job's XP and its level, that a repeated submit pays nothing, that a second villager is recruited for 20 timber of what came home and then retired, so a test user's hall never fills, that the mine is built for 60 timber and 3 cloth once the test user's camp can pay, which is the second run on a new stack, and is refused until then, and that a repeated build charges nothing and the mine has no second level (Issue-93), that the mine's job, "Ore from the hill", is refused while the camp has no mine and once it has one is played with the villager, whose ore pays for a fighter, retired at once (Issue-133), and that `adventure(id)` reads the timeline back from the replay bucket, and reads the deploy's version from `/graphql` and from `/previous/graphql` (`scripts/e2e.mjs`). Timber, because a lone villager clears it on every seed and the wolves kill it on every seed (Issue-126), then reads the cold start from the function's log. A check that fails ends the test and fails the run: every workflow runs its steps as `bash -eo pipefail` (`defaults.run.shell: bash`), so the test's status is not lost in the pipe into its log (Issue-137). The run's summary holds the plan, the URL, the test's output, passed or failed, and the cold start; the branch's deployment on GitHub links to the URL, and the branch's pull request carries it as one comment, posted when the pull request opens and refreshed by every push; the comment is posted only for a working branch's pull request, one whose head is `<type>/<issue>-<description>`, because no other head has a stack (a release pull request's head is `main`, Dependabot's branches have no issue number). The owner reviews a change there (`docs/process/code-changes.md`, rule 24).
2. **The fast loop is local and needs no AWS.** `npm test` at the root runs every package's tests; the hub's start their own DynamoDB Local container through Testcontainers, so Docker Desktop must be running. `npm run typecheck`, `npm run lint`, `npm run schema:print`, `npm run codegen` and `npm run bundle` are the other checks a push runs, the two generators regenerating the committed schema and the client's GraphQL code, which the push's "Build and test" expects to find current; lint needs neither Docker nor AWS, takes about a minute because it reads the types, and `npm run lint -- --fix` applies the fixes ESLint can make itself, which the diff then shows. A finding is fixed before the pull request opens (`docs/standards/typescript.md`, rule 16). The workflows have a linter of their own, actionlint, run by "Build and test" at a pinned release over `.github/workflows/` and on a laptop as `actionlint` from the repository root with no argument (installed by winget, `rhysd.actionlint`, the author's package, kept at the release the workflow pins); a workflow change is linted before it is pushed, and a finding is fixed the same way (Issue-187). The Angular dev server runs locally too (`docs/standards/typescript.md`, rule 15).
3. **A branch is pushed when it is created.** The worktree and the branch are created together and the branch is pushed at once (`docs/process/code-changes.md`, rule 22), so the stack exists from `main`'s code and every plan after that is a delta. A branch of any type gets a stack; a documentation branch's stack costs nothing at rest and goes with the branch.
4. **Call the stack by hand with `player1`.** The automated test's user has no password anyone knows. For a call of your own, the base pool's test users `player1` and `player2` sign in through the `ci` client with the `sandbox-base` environment's secret, which the owner holds and types, never pastes: `$env:E2E_PASSWORD = Read-Host -MaskInput` then `node scripts/e2e.mjs --issue <n> --username player1@heat-sb.dcg-games.com` runs the same test from a laptop, reading the stack's facts from Parameter Store under `/heat/heat-sb<issue>/` (`site_url`, `api_url`, `user_pool_id`, `app_client_id`, `browser_client_id`, `login_host`) through the plan role. A raw call is `POST https://<issue>.heat-sb.dcg-games.com/graphql` with `Authorization: Bearer <access token>`; the API's own URL answers the same, without the distribution in front. The same script with `--stack heat-dev --username player1@heat-dev.dcg-games.com`, the `dev` environment's secret and `AWS_PROFILE=plan-heat-dev` runs it against `dev` (Issue-40), which is what the `Deploy` workflow does after every apply of `dev` with a user of its own. With `--anonymous` in place of `--username` the script runs only the checks that need no token, the page, `config.json`, the login page, the hand-off to Google and the 401, which is prod's smoke test (`release.yml`, Issue-41), because prod's pool has no password-flow client and no test users.
5. **Sign in locally against the branch's stack.** `npm start --workspace @heat/client` serves the client at `http://localhost:4200` and proxies `/config.json`, `/graphql` and `/previous/graphql` to `https://<issue>.heat-sb.dcg-games.com`, the issue read from the branch name (`packages/client/proxy.conf.mjs`; `HEAT_STACK=https://<origin>` points it at another stack). The page is then that stack's client: Sign in goes through the pool's managed login with the `http://localhost:4200` callback the stack's browser client registers, and the tokens are the stack's (decision 0024). A sandbox stack's login page offers email and password beside Google (Issue-86), and that is how an agent signs in from its session browser, on the stack's URL or on the dev server: as a test user of the base, `player1@heat-sb.dcg-games.com` or `player2@heat-sb.dcg-games.com`, with the password the owner keeps for it in `docs/private/heat-sandbox-test-users.env` (`HEAT_TEST_USER_PASSWORD=`, ignored by git), read only to be typed into that page and never printed, committed or repeated in a chat. Google sign-in stays out of agent sessions: an agent never signs in with Google and never asks the owner to do so in the session browser. The dev server rules of `docs/process/code-changes.md`, rule 24, apply: one server at a time, in a terminal tab the owner can see.
6. **Plan locally before pushing an infrastructure change.** From the worktree, with the bundle built, through the plan role (`docs/process/code-changes.md`, rule 23); `scripts/sandbox.mjs` derives the state key and the stack name from the branch:

   ```powershell
   . C:\Users\chanc\IdeaProjects\HEAT\docs\private\heat-tfvars.ps1 -Environment sandbox
   $env:AWS_PROFILE = "plan-heat-sandbox"
   $env:TF_VAR_app_version = git rev-parse HEAD
   npm run bundle
   node scripts/sandbox.mjs init
   node scripts/sandbox.mjs plan -- -lock=false
   ```

   `-lock=false` because the plan role may not write the lock file. `TF_VAR_app_version` is the deploy's version (decision 0030), which the workflow sets from `github.sha`; commit before planning, so the laptop's `HEAD` is the commit the push will deploy. A local bundle that differs from the runner's by a byte shows as a code change in the plan; the pipeline's hash is the one that counts.
7. **Read the stack's logs through the plan role.** The function logs to `/aws/lambda/heat-sb<issue>-hub` as JSON lines (Powertools), one line per GraphQL request with the operation name, duration and error count, and a warning per error; the API's access log, `/aws/apigateway/heat-sb<issue>-api`, shows what the JWT authorizer refused, which the function never sees. The plan role may read log lines from groups whose names carry `heat-sb`. Traces are in X-Ray, sampled at one request a second plus 5%.
8. **The cap.** At most 5 sandbox stacks may exist beside the base (`SANDBOX_STACK_CAP` in the workflow). A push that would create a sixth fails and names the five. Deleting a merged branch destroys its stack at once, in a run of some minutes, because CloudFront disables a distribution and deploys that before it can be deleted; a weekly sweep destroys any stack whose branch is gone, and a `workflow_dispatch` of the sweep with `dry_run` lists them without destroying. The deletion and the schedule run `main`'s copy of the workflow, so a change to those jobs takes effect once merged.
9. **What a sandbox stack lacks on purpose.** No point-in-time recovery, no deletion protection, seven-day log retention, no alarms: a stack lives as long as its branch. Those are `dev`'s and `prod`'s literals.

## Why

The emulator the project started with (decision 0009) could never exercise the piece of the request path most worth exercising, the JWT authorizer, and it was one more thing to keep faithful to API Gateway, forever a behavior behind. A stack costs nothing at rest and is the real gateway, the real authorizer, the real IAM path and the real logs (decision 0018). What stays local is what runs in seconds and needs nothing from AWS.

Pushing at creation puts the cap's refusal at the cheapest moment, before any work exists on the branch, and makes the first real plan a plan of the change rather than of the whole stack.

The GitHub environments `sandbox-<issue>` accumulate, one per issue; they hold nothing and are left alone.
