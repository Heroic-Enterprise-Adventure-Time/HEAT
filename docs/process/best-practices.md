# Best practices first

How decisions are made, especially about security and platform management, and three practices every change follows: the page is responsive, a decision is challenged when it turns out wrong, and a gap in the documents is closed where it is found. Rule 13 is about the pipeline's jobs and roles. These rules apply in every session.

"Security and platform management" covers: accounts and organization structure; identity and access for people, pipelines and services; credentials and secrets; network exposure; data protection; logging and audit; Terraform state; build, release and deployment controls; cost controls.

## Rules

1. **Follow established best practice.** In security and platform management it is not traded for speed.
2. **Propose the recommended approach first.** When the provider or a recognized standard recommends a way of doing something, that is the default proposal. A quicker alternative may be offered beside it, labeled as a shortcut, with what it gives up.
3. **Check, do not recall.** Before proposing a setup in these areas, look up the current guidance, say what it is, and say where it came from. Console steps are verified against documentation, not recalled.
4. **Never skip a step silently.** A step that is deferred is written down as deferred, with the reason and what it leaves exposed.
5. **Scale down only on purpose.** Where the full practice is out of proportion for this project, say what the full practice is, what is proposed instead, and why. The project owner decides, and the decision gets a record in `docs/decisions/`.
6. **Do not hurry these decisions.** A decision in these areas is talked through before it is implemented, even when that slows a checkpoint.
7. **Import, do not recreate.** Something that already exists in AWS and is to be managed by code is imported into state. Recreating it is a change to a working estate and is proposed only with the reason.
8. **Control Tower's own resources are never touched by code.** The service control policies, stack sets, roles, buckets and trails that Control Tower creates in HEAT's accounts belong to it. HEAT's stacks build beside them. The organization-level reasoning is decision 0002 in the `dcg-platform` repository.
9. **Drift toward best practice as requirements evolve.** When a new or changed requirement does not fit the current approach, the first question is whether a different approach serves it better, not how to make the current one fit. A workaround that keeps the current approach is proposed beside the alternative, labeled as a workaround, with what each costs. At natural pauses, a checkpoint merged or a new step of the build order begun, the whole shape is reviewed against current guidance and anything that has drifted is named: that review is the checkup skill, run from a session of its own by `docs/runbooks/checkup.md`, whose findings are issues the owner triages (`docs/process/code-changes.md`, rule 28).
10. **The page is responsive.** What the player sees follows their font size, screen and window: the client is laid out in relative units, `rem` and fractions of the viewport, from sizes declared once in the stylesheet's tokens or measured from the rendered page, and the arithmetic that predicts a layout reads those same sizes at runtime. No constant in TypeScript copies a value the stylesheet holds (`docs/standards/angular.md`, rule 17). A pixel is written only where the thing is a pixel: the whole-number scale of pixel art, a one-pixel line.
11. **A decision is challenged when it turns out wrong.** A recorded decision, or a shape that was never decided but inherited, is reopened the moment work shows it incorrect or no longer right, by anyone, in the branch that found it: the shape changes there, with its decision record (`docs/decisions/`) and the old record's status line. The age of a decision is not a reason to keep it.
12. **A gap in these documents is closed in the pull request that found it.** When work shows a practice that belongs in this document or in a standard and is not there, or one written there that is wrong, the document changes in the same branch and pull request as the work, and the pull request's description lists it. It is not filed as an issue for later: an issue filed for a document is a gap that stays open.
13. **A job that runs downloaded code holds no role and no environment's secrets.** A package, its install step or a browser runs in a job with no `id-token` permission and no environment, because a step cannot give up what its job holds. What it needs from AWS is read by an earlier job, under the role, and handed over (decision 0046). The exception is what has to hold the role to do its work: Terraform, its providers, whose hashes the lock files pin, and the GitHub actions those jobs are built from.

## Why

Hasty decisions and skipped steps in security and platform management always end up being regretted. Identity, account structure and release controls are foundations: everything else is built on them, they are far harder to change afterwards than to set up correctly, and their failures tend to stay quiet until they are serious.

The rule to propose the recommended approach first comes from a real miss. The first plan for command-line access to the project's AWS accounts reused a long-lived access key on a user in the organization's management account, because that matched an existing setup. The recommended practice is single sign-on with short-lived credentials. The project owner caught it. The shortcut should never have been the first thing proposed.

The sentence added to rule 3 on 2026-10-13, and rules 7 and 8, come from the organization-level work in the `dcg-platform` repository. Console descriptions given from memory were wrong more than once during the AWS review; descriptions checked against the documentation were not. Rules 7 and 8 describe how every stack in the organization treats what already exists, and HEAT's accounts are Control Tower accounts, so they apply here as they do there.

Rule 9 was added on 2026-10-16, after the Terraform layout changed from one configuration per stack to one root directory per environment (decision 0016). The first shape had been fitted to a second environment with a `-reconfigure` flag and a map of account ids. It worked, it would have been built upon, and the owner asked for the question to be put the other way round. A workaround hides the mismatch; the next requirement lands on the workaround, and the cost of moving compounds. Paying for the move early is the cheaper habit, and a periodic review is how the need for one is noticed.

Rules 10 to 12 were added on 2026-11-02 (Issue-186), when the review of its pull request found the header's height written twice, as `2.25rem` in the stylesheet and `36` in the layout arithmetic, each true only at the browser's default font size, and the first answer offered was to decline the finding as older than the change. The owner's call was the opposite: the page follows the player's settings, a shape found wrong is reopened where it is found, and the practice goes into the documents in the same pull request, because a note or an issue for later is how the two copies had survived.

Rule 13 was added on 2026-11-04 (Issue-202), from the review of PR-230, which found the browser test's install step and Chromium running with the apply role's keys in their environment when the test needed one parameter read. A browser and a package's install step run code the project did not write, and the role can change the stack. It was rewritten from a step to a job on 2026-11-06 (Issue-231, decision 0046), when the work of meeting it showed that a step with its keys removed could still reach the role.
