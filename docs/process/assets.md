# Generated assets

How HEAT's art and audio are made, recorded and committed. The services, the licences and the alternatives that were rejected are in decision 0025.

## Rules

### Who makes an asset, and where it lives

1. **The services.** Pixel art comes from PixelLab. Sound effects, and later music, come from ElevenLabs. Nothing else generates assets for HEAT without a new decision.
2. **The agent generates, through the owner's connectors.** Each service is reached through an MCP connector attached to the owner's claude.ai account. The service's token lives in that connector and nowhere else: not in the repository, not in a local Claude configuration, not in a GitHub environment. PixelLab's connector is a custom connector at `https://api.pixellab.ai/mcp`, with No sign-in and a required `authorization` request header holding `Bearer <token>`; it has to be added in the claude.ai web interface, because added from the desktop app the header was not sent. A `401: Missing Authorization header` on every call, while the connector shows as connected, is fixed by removing the connector and adding it again there: a header cannot be edited, and its value is sent exactly as typed, so it includes `Bearer `.
3. **Never in CI, never at build time.** An asset is generated once, in a session, chosen by the owner, and committed. The build only reads committed files. Packing a sprite set's frames into its sheet is the build's and is no generation (rule 4): a sheet is a function of the committed frames, so none is committed.
4. **The committed files are the asset of record.** Assets live under `art/<kind>/<set>/`, for example `art/heroes/ranger-01/`. The game uses these files; it never needs the service to still hold them. The page does not fetch a set's frames one by one: the client's build packs each set under `art/heroes`, `art/monsters`, `art/props`, `art/weapons` and `art/fonts` (rule 37) into one sheet, an image named for its pixels, with PixiJS's atlas beside it, `sheet.json`, which names the image and also holds what a scene reads about the set, the row each animation stands on, measured from its pixels (rules 11, 18 and 31), and how its provenance says it plays, the hold frame, a weapon's grips, nocks and frame lengths, a prop's fade (`packages/client/scripts/pack-art.mjs`; decision 0028 as amended by Issue-205). Neither the frames nor the provenance is published. Adding a set is committing its files and nothing else, and a set whose frames are not as many as its provenance says fails the build with its name.
5. **Every set carries its provenance.** `provenance.json` beside the files records what the service's own export does not: the service, the plan and the date of the terms the set was made under, the service's ids, a hero set's classes and presentation (masculine, feminine or either), every parameter of every generation call, whether it was made through the MCP or on the service's website, the generations it cost, and the act's hold frame. `art/heroes/ranger-01/provenance.json` is the shape to copy. A set made before the engine has what it draws leaves the list the engine's art tests read, its `monsters`, `props`, `wielders` or `abilities`, empty, and says what it is for in `madeFor`; the issue that adds the monster, the wielder or the ability names it in that list. A hero set made that way leaves its `classes` empty and is still added to the engine's `SPRITE_SET_PRESENTATION` in the same pull request, because that table lists every set under `art/heroes/` and its presentation is true of the picture whether or not a class uses it yet. What a provenance says of its files is tested: `packages/engine/test/provenance.test.ts` reads every kind under `art/`, and a file the provenance does not name, a name with no file, a canvas that is not the picture's or an effect's frames and rate that are not its manifest's fails `npm test`. An animation's canvas is one pair, or a pair for each direction where they differ.
6. **Committed files match the service's export.** Before a set is committed, its files are compared byte for byte with the same files in the service's download of it.
7. **Characters and objects are tagged in PixelLab when they are made.** Every character made for HEAT is tagged `heat`, its kind (`hero` or `monster`) and its class or monster as soon as it is created, kept or not, so that it can be found among the account's other characters; every object, such as a facility sprite, is tagged `heat`, `facility` and its kind (`heroes-hall`, `job-board`, `warehouse`) with `update_object_tags`, and every interface icon `heat`, `ui-icon` and what it stands for. One that is not kept, or a kept one that is later replaced, also gets `rejected`, so the rejects can be found together and deleted on PixelLab's website. Tilesets cannot be tagged; their rejects are found by the ids in the kept set's provenance. The tag filter matches any of the tags given, so the kept pieces are found under `art/`, each with its PixelLab id in its provenance. A PixelLab website project is not visible through the MCP.

### A hero sprite set

8. **The base character.** `create_character` with:

   | Parameter | Value |
   | --- | --- |
   | `mode` | `standard` (1 generation) |
   | `n_directions` | `4` |
   | `size` | `32` (stored on a 48×48 canvas) |
   | `view` | `low top-down` |
   | `outline` | `single color black outline` |
   | `shading` | `flat shading` |
   | `detail` | `low detail` |
   | `proportions` | default |

9. **The description** is `<appearance>, empty hands, no weapon, no shield, warm earthy tones, NES-era retro pixel art, few colors`. Only `<appearance>` changes from set to set. Characters hold nothing: an action's weapon or spell is a separate effect sprite.
10. **Full colour, touched up by hand.** No colour reduction and no shared palette. Before any animation, the owner may correct single pixels of the rotations in PixelLab's online editor rather than re-roll a look; the animations are built from the edited rotations, and the provenance records every changed pixel.
11. **The animations,** `animate_character` with `mode: skeleton-v3`, which costs 3 generations a direction through the MCP, 2 for the three-frame act:

    | Name in HEAT | Template | Directions | Frames | Played as |
    | --- | --- | --- | --- | --- |
    | walk | `walking` | south, east, north | 6 | a loop |
    | stance | `fight-stance-idle-8-frames` | east | 8 | a loop, in battle between actions |
    | act | `lead-jab` | east | 3 | frame 0, frame 1 held for as long as the action lasts, frame 2 |
    | hit | `taking-punch` | east | 6 | once |
    | down | `falling-back-death` | east | 7 | once, last frame held |

    West is east mirrored. A hero standing outside battle is its still frame: there is no idle animation. The four still frames are the character's rotations; where the owner finds the west rotation bad, `still-west.png` is the east rotation mirrored, and the provenance says so.
    **Frames are lined up by the figure's feet, not by the canvas.** Whatever draws a set puts the lowest opaque pixel of the south still on the spot where the hero stands, and moves each animation by one amount, so that its first frame's lowest pixel lands there too; `down` is moved frame by frame instead, each frame's lowest pixel onto that spot, so the body lands where the feet were. The files stay as PixelLab exports them.
12. **The cost** of a set is about 22 generations: 1 for the look kept, 1 for each look not kept, and 20 for seven animated directions.
13. **Checks before keeping a set.** The hands are empty in every frame. The figure's height varies by no more than 2 px across each animation but `down`, where the figure falls. No stray pixels: none detached from the figure, and none of a colour far from the character's own. A set that fails is re-rolled by the owner, one direction at a time (rule 21), or the owner waives the check for that direction. `docs/runbooks/hero-sprite-set.md` is the order of work, and its script runs every check but the hands.

### A camp's art

14. **The ground is a tileset.** `create_topdown_tileset` with `mode: standard`, 16×16 tiles, `shading: flat shading`, `detail: low detail`, each terrain described as `<terrain>, warm earthy tones, NES-era retro pixel art, few colors`. The ground has no outline, so that the outlined buildings and heroes stand off it. A tileset costs 1 generation. Standard always draws high top-down and ignores `outline`, so neither `view` nor `outline` is passed; only `mode: pro` takes a `view`, at 15 generations, and the owner is asked before one is rolled. `meadow-01` was made on the service's earlier model, which took both and cost 3 or 4, as its provenance says. A new terrain is joined to an existing one by passing that one's base tile id (`lower_base_tile_id` or `upper_base_tile_id`), so the two connect; standard redraws the shared terrain close to the first, not byte for byte. A terrain is described by what it is made of and what marks it, because a plain name can come out as its neighbour: `bare weathered rock` beside packed earth came out as more brown earth, and `rugged grey rock slabs with deep cracks and scattered stones` as rock. Standard also rewrites each description before it draws, its `enhance`, which is left on: the provenance records the text passed and the text drawn, and `tileset.json` keeps both. It can swap the two terrains, so a sheet's all-lower tile is looked at before the set is judged. It is committed as `art/ground/<set>/tileset.png` and `tileset.json`, the sheet and PixelLab's metadata exactly as downloaded; whatever draws the ground picks each tile by its four corners and cuts it out by its `bounding_box`.
15. **A facility is one sprite, not built from tiles.** `create_map_object` with no background image, `view: low top-down`, `outline: single color outline`, `shading: flat shading`, `detail: low detail`, described as `<building>, black outline, warm earthy tones, NES-era retro pixel art, few colors`. The canvas is a whole number of 16 px tiles in each direction: the heroes hall 64×64, the warehouse 48×48, the job board 32×32. A call costs 1 generation.
16. **One angle for every facility:** three-quarter, the front wall facing down-right and a side wall showing, as the heroes hall draws it. A head-on building came out flat. Adding `seen at a slight angle so its side wall shows, three-quarter view` to the description gave the angle; a call that misses it is rolled again.
17. **A facility's level may change its sprite, never its canvas or its angle.** Each facility is `art/facilities/<kind>/level-<n>.png`, with one `provenance.json` for all its levels; a level with no file of its own shows the highest level below it that has one, and the engine's content lists the levels that have a file (`FACILITIES`), which a test checks against the files. Level 0 is a facility the camp has not built: an unfinished building or a cleared site, on the same canvas and at the same angle as its level 1 (Issue-89). A shared facility, such as the job board, is one sprite at every location.
18. **Facilities stand by their base, like heroes by their feet.** Whatever draws a facility puts the lowest opaque row of the sprite on the facility's base line, with the canvas centred on its spot; the files stay as PixelLab exports them. Facilities and heroes are drawn back to front by the line they stand on. In the camp a hero is drawn at half the scene's scale, rounded up, and a facility at the scene's (decision 0028, as amended by Issue-99), so the art is drawn at its own size and the scene does the scaling.
19. **Chosen in the scene.** A camp's pieces are rolled two or more at a time and chosen by the owner in a mock-up of the whole camp map at 3× or 4×, with kept hero sets standing in it. The provenance lists the candidates that were not kept, with their PixelLab ids. A set the owner chose in a mock-up records it as `chosenBy`: who chose, when, and the mock-up's path; and every file under `art/mockups/` is named by the provenance of a set chosen in it. A mock-up is kept as the evidence for those provenances and is not an asset: the game does not draw it, it stands outside rule 4's `art/<kind>/<set>/`, and it needs no provenance of its own.

### Working with the service

20. **Budget.** The plan gives 2,000 generations a cycle; `get_balance` reports what is left. A hero set or a humanoid monster costs about 22, a four-legged monster about 9, a prop about 3, or about 13 when its `down` ends in a state of its own (rule 30), a re-rolled direction 3, a facility sprite 1, a tileset 1, a pack of 64 icon or weapon candidates 10, a weapon's swing 1, a font 15 a roll, the page's frames 10 (rule 40), and an effect nothing.
21. **Limits.** At most 8 jobs run at once, so a set is queued in batches. `wait_for_jobs` is called with a timeout under 300 seconds and called again: a wait of 540 seconds timed out on PixelLab's side although the job had finished. A job that fails with "heavy load" is retried once and is not charged. A skeleton animation is not made twice for the same template and direction, and the MCP has no re-roll. So the work is split: the agent queues a set's animations and checks the result; the owner reviews them and re-rolls any direction with the button on PixelLab's website, and the provenance records that call as made on the website.

### Audio

22. **Sound effects** may be made and used commercially on the owner's paid ElevenLabs plan, with no attribution.
23. **Music is not made for release** until ElevenLabs has answered in writing whether a single-member company qualifies for a plan marked "For Individual Use Only" (decision 0025).
24. **The ElevenLabs connector waits.** Its hosted MCP manages agents only, and its creative tools are announced but not live; it is connected when they are.

### Interface icons

25. **Icons are 32 px and drawn at a whole-number scale.** An icon of the page, such as a facility's entry in the menu, a resource or an action on a button, and the favicon, are 32×32 PixelLab objects, shown at 1× (32 CSS px) or a whole multiple with `image-rendering: pixelated`, so each art pixel stays square, as the scene's are. They share the scene's look: black outline, warm earthy tones, few colours.
26. **Rolled as one pack.** `create_1_direction_object` with `view: top-down`, the description `small game menu icon, black outline, warm earthy tones, NES-era retro pixel art, few colors`, one `item_descriptions` entry per idea (several ideas for each icon), and a 32×32 piece of kept art as the one style image; the style image sets the size, so `size` is not passed. One call returns 64 candidates in one style for 10 generations; ideas beyond those described are filled in by the service.
27. **Chosen from a numbered sheet.** The owner picks from all the candidates side by side at 3×. The picks are promoted with `select_object_frames` and tagged (rule 7); the review object that holds the rest is tagged `rejected`. The icons live in `art/icons/`, one file per icon named for what it stands for, a resource's by its name in the engine's `MATERIALS`, with one `provenance.json` for them all: each pack is an entry of its own there, and each icon names its pack and its candidate. What is true of one pack is recorded in that pack's entry, beside its call: who chose from it and when, how its files were verified, and where its rejects are; a top-level field says only what is true of every pack. A pack may carry ideas for icons a later issue needs: the candidates not kept stay in the pack's review object, and that issue promotes its picks from there. `scripts/icon-set.mjs` draws the numbered sheet and writes a pick's file and its entry; the order of work is `docs/runbooks/resource-icon.md`. The committed file keeps its plain name; the client's build publishes it under a name that carries its file's hash, with an index the page and the battle scene read (`docs/standards/angular.md`, rule 22), so an icon picked again under its name is seen at once, where everything under `/art` is otherwise kept by a browser for a year.

### Monsters and props

28. **A monster is a sprite set like a hero's,** with the same files and the same five animations, made by the same runbook and script, in `art/monsters/<monster>-<nn>/`. Its description is `<appearance>, warm earthy tones, NES-era retro pixel art, few colors`, with `empty hands, no weapon, no shield` before the tones for a monster that has hands. Its provenance lists the `monsters` it draws in place of a hero's classes and presentation, and the candidates not kept; it is tagged `heat`, `monster` and the monster (rule 7). A humanoid monster follows rules 8 to 11 exactly, with one exception: a monster that throws takes the template `throw-object` for its act in place of `lead-jab`, 7 frames for 3 generations, because the jab reads as a punch; its `holdFrame`, the arm at the release, is chosen by eye and recorded. A four-legged one is `create_character` with `body_type: quadruped` and the nearest of PixelLab's animal templates (`dog` for the wolf), with the rest of rule 8. A quadruped has no skeleton for `skeleton-v3`, and its templates have no fight, so its animations are:

    | Name in HEAT | How | Directions | Cost |
    | --- | --- | --- | --- |
    | walk | `mode: template`, the template's 6-frame walk | south, east, north | 1 a direction |
    | stance | `mode: template`, the template's idle | east | 1 |
    | act, hit, down | `mode: v3`, an `action_description` of the movement alone; frame 0 is the east rotation | east | 1 each |

    A `v3` act has no fixed hold frame: the frame where the action lands is chosen by eye and recorded as `holdFrame`, and the act plays the frames before it, holds it for as long as the action lasts, then plays the rest. A quadruped set costs about 9 generations.
29. **A monster is checked as a hero is** (rule 13), with one difference: a monster that lunges or crouches changes height by design, so the owner may waive its act and hit on sight, and the waiver is recorded.
30. **A prop is an object, not a character.** A resource the battle acts on, such as a tree, is one sprite with no directions, made like a facility (rule 15) on a canvas of whole 16 px tiles (a tree 48×64, an ore vein 48×48), and lives in `art/props/<prop>-<nn>/` as `standing.png`, `hit-<i>.png` and `down-<i>.png`, the last frame of `down` held. Its `hit` and `down` are `animate_object` with `mode: v3`, 1 generation each, and the description says `no particles, no effects`, because an ability's effect is a sprite of its own (rule 34). A `down` that leaves something behind, such as a stump, is drawn by making that end state first with `create_object_state` and interpolating to it with `end_frame`; the state is the dear part, 10 generations for an object of one direction (it was 1 for the tree's stump and 4 for the ore vein's rubble), so its description is settled before it is spent. PixelLab draws no partial transparency, so whatever goes away, such as the tree's crown, is described as staying in place, and whatever draws a `down` marked `fadeAboveEnd` fades every row above the top row of its last frame's picture, evenly from fully drawn on the first frame to gone on the last, and draws the rows below as they are; so what goes away fades while the end state forms. An object's animation can be made again through the MCP, unlike a character's (rule 21), so the agent makes it again on the owner's word, and the provenance lists the one it replaced. A prop, its end state too, is tagged `heat`, `prop` and the prop.
31. **A prop stands by its base,** as a facility does (rule 18), and is drawn at a monster's scale. `scripts/prop-sprite-set.mjs` writes its files from PixelLab's export and its provenance from the agent's record. A prop on the party's side, the caravan's cart, stands on a battle line among the heroes, so it is drawn as they are seen there, from the side and facing east: `view: side`, and a description that says `flat side-on profile` and that it `points to the right`. The service follows neither every time, so looks are rolled in batches and the owner chooses in a mock-up of the battle, beside kept hero sets and a monster; one that faces west is rolled again and not mirrored, because a mirrored file is not the service's own (rule 6). It has no clip for a travel, and its `down` ends in its wreck, which lies 4 px lower than the cart stood because a prop keeps its standing picture's base through its `down`. On a travel the scene jolts the still picture a pixel up and down, every `CART_BOB_MS`, and the wreck stays on the road unfaded until the road scrolls it away (built by Issue-353; `docs/design/game.md`, "Caravans").

### Weapons and effects

32. **A weapon is an object, picked from a pack.** Weapons are rolled together, as icons are (rule 26): `create_1_direction_object` with `view: top-down`, the description `single weapon on a transparent background, held by its grip at the lower left, blade or head pointing up and to the right, black outline, warm earthy tones, NES-era retro pixel art, few colors`, several `item_descriptions` for each weapon wanted, and `art/icons/adventure.png` as the one style image, so 32×32. The owner picks from a numbered sheet at 3×; the picks are promoted with `select_object_frames` and tagged `heat`, `weapon` and the weapon (`sword`, `hand-axe`), and the review object `rejected`. A weapon lives in `art/weapons/<weapon>-<nn>/` as `icon.png`, its one still picture and its icon in the inventory, and `swing-<i>.png`; its provenance names the `wielders`, the unit types and monsters that use it, and the pick. A pick that came out mirrored, its grip at the lower right, keeps `icon.png` as PixelLab drew it, and its swing (rule 33) starts from that picture mirrored, passed as the start frame, with the end frame turned from it; so every committed file is still the service's own, the swing faces the way every weapon's does, and the provenance records the `startFrame`.
33. **The swing is drawn frames, held with the act.** `animate_object` with `mode: v3` and `frame_count: 4`, 1 generation, five frames whose frame 0 is the icon, interpolated with `end_frame_base64` to the icon turned a right angle clockwise, which loses nothing, and described as the weapon turning about the end of its handle from pointing up and to the right, through straight ahead, to down and to the right, `the same <weapon> the whole time, no particles, no effects, no motion trail`; PixelLab draws the frames between. Checked frame by frame: the weapon keeps its shape, and it turns about the hand, not its head; one that fails is made again through the MCP (rule 30), and the provenance lists the one it replaced. The provenance records the `holdFrame`, the frame pointing ahead, chosen by eye, and the `grips`, the pixel in the hand on every frame, measured on a grid, because PixelLab turns the weapon about its canvas, not the hand. A weapon whose motion is not even, such as a bow's quick release, records how long each frame before its hold lasts as `frameMs`, and a bow records its `nocks`, the middle of its string on every frame. Whatever draws a weapon shows it only while its wielder acts, which is from the moment its action resolves (decision 0057), plays it with the act on the presentation clock, each waiting on its own hold frame until both are there and playing the rest from then, and puts each frame's grip on the wielder's leading hand, one point from the feet for every set (10 px ahead and 20 above, measured on every hero set's act); it is mirrored with its wielder.
    **A bow is drawn, not swung.** Its pack asks for a bow, and its icon is whatever pose the pick has: the first pack came out on the diagonal whatever the descriptions said. Its `swing-<i>.png` are a draw and a release, `animate_object` with `mode: v3` and `frame_count: 6`, described as an upright bow whose stave keeps its size and place while only the string is pulled back into a V and snaps straight, `no arrow`, with one picture of the bow standing upright at rest passed as both the start frame and the end frame; so frame 0 is that picture, not the icon, and the provenance says where it came from. Its `holdFrame` is the last frame, the bow at rest just after the release, so that the arrow leaves as the hold begins. Beside the `grips` the provenance records the `nocks`, the pixel at the middle of the string on every frame, where the arrow's tail sits: the arrow is never drawn into the bow's frames, and whatever draws the bow shows the arrow's own sprite (rule 35) on the nock while the bow is drawn.
34. **An effect is made in the effects tool, at no cost.** PixelLab's `vfx_workbench` draws an effect from tuned parts rather than generating it, so every effect shares one look, and it is free on the plan. It is made around the sprite it lands on (`start --sprite`), from parts given warm five-colour ramps, dark to light, with the part that makes it what it is marked `core`; it plays once, and is anchored at the target's feet. It is exported with `--game-pack` and saved in the owner's My effects as `HEAT <effect> <nn>`, where the sliders can be moved and the effect exported again with `--replace`. Of the pack, `whole.png`, the effect without the sprite as a sheet, and `manifest.json`, which says where it stands, are committed in `art/effects/<effect>-<nn>/`; `scripts/effect-set.mjs` writes them byte for byte and the provenance from the agent's record of the parts and the edits. Its provenance names the `abilities` it draws, and one effect may serve several, such as both strikes.
35. **An effect plays on whoever the action reached.** Each ability has one effect, or none (moving up). Whatever draws it starts it at the action's blow, when the act and its weapon reach their hold frames after the action resolves, or where its projectile lands, on each unit the action reached, a guard that took a hit rather than the ally it covered, and plays it once on the presentation clock, frame `i` at the target's feet plus the manifest's offset. An effect is made for an actor on the left and mirrored when the other side acts. **A projectile** is a target effect that travels: made in the workbench with `throw`, its projectile part exported on its own (`--part`) and moved in code from the actor to the target, its impact part played on resolve as any effect. Its flight is part of its action and plays, with the wind-up before it, as the action resolves (decision 0057, which reverses decision 0052's wind-up and flight during the warm-up). It is let go when the actor's weapon, or its act where it has no weapon, reaches its hold frame, from the bow's nock or the hand, and it flies for what the warm-up leaves after the wind-up, so that the two together last as long as the warm-up; before it is let go, an arrow is shown on the string, its tail on the frame's nock. Its impact, the target's hit and a fall begin as it lands, and the adventure's clock waits for all of it. It flies a straight line to where the effects tool drew it on its target, lifted in the middle by the arc of the tool's own path as a share of the distance, and is not rotated. It flies at whoever took the hit, which the action's resolve has said by the time it is let go, so where a guard steps in the projectile and its impact both end on the guard. A projectile whose target is gone before it lands is dropped. One `throw` call makes both, from PixelLab's own drawing of the thing thrown (`arrow`, `rock`), and gives each its role; its `from` and `to` are in the effect's canvas, 256 px square with the sprite at its centre, not in the sprite's own pixels. The game pack then holds a clip for each role, and `scripts/effect-set.mjs` commits their sheets, `part-projectile.png` and `part-<impact>.png`, beside `whole.png`; the manifest gives each clip's frames and offset. An impact that falls to the ground, such as a rock's grit, is checked against the target's feet: a part's floor moves with its size, so a part made smaller settles above the ground until it is moved down.
36. **What PixelLab's tools do that their descriptions do not say.** `animate_object` takes `custom_start_frame_base64` and `end_frame_base64` together, which is how a mirrored pick gets a swing that faces right. `animate_object`'s `display_name` does not name the export's folder, and `rename_asset` on the group does not either.

### The scene's text and a drop

37. **A scene writes in a pixel font's glyphs, drawn as sprites.** What a scene says in characters, the amount beside a drop first, is pixel art at the scene's whole-number scale and never a font the browser scales. The font is PixelLab's `create_font`, `glyph_px: 8` and `weight: Regular`, 15 generations a roll: its atlas is one cell a character, 8 columns, row by row in the service's own order, black on transparent and one bit whatever colour or outline the description asks for. Every glyph the scene will draw is read enlarged on the scene's ground before the roll is kept: at 8 px the Bold weight closes a digit's counters. A font lives in `art/fonts/<name>-<nn>/` as `atlas.png`, byte for byte (rule 6), with a `provenance.json` that records the call, the atlas's `glyphPx`, `columns` and `characters`, and any roll it replaced; the service's TrueType file is not committed, and a font takes no tags. The client's build cuts the glyphs the page's list names, `SET_CLIPS.font` in `packages/client/src/app/sprite-sets.ts`, each to the columns it fills, in the stylesheet's `--light` with one pixel of its `--ink` around it, and packs them as a set (rule 4), so the colours are the build's and the atlas stays the service's. Whatever draws them places one sprite a glyph, a glyph's outline sharing a column with its neighbour's. A glyph a scene needs beyond the list is added to the list, and the build cuts it or fails.
38. **A resource an enemy drops has its icon.** The battle scene shows a drop as the resource's icon (rules 25 to 27) at one art pixel to a scene pixel, with the amount in the font of rule 37 on its lower right, rising from the enemy that fell (battle.md, "A drop shows twice"). So a resource is given its icon, by `docs/runbooks/resource-icon.md`, in or before the pull request that makes an enemy drop it: `packages/engine/test/resource-art.test.ts` fails for a dropped resource with no icon in `art/icons/` and its provenance.

### Scripts that draw

39. **A script that draws with the page's colours reads them from the stylesheet's tokens.** A build step or a tool that colours what it draws with a colour of the page's palette, as the art build colours a font's glyphs and `scripts/icon-set.mjs` the numbers of its sheet, takes it from `packages/client/src/styles.css` through `colourToken` in `packages/client/scripts/style-tokens.mjs`, and holds no copy of it. It reads a role token and not the palette, which `colourToken` follows through its `var()` to the colour: the art build's glyphs and the numbers of `scripts/icon-set.mjs`'s sheet read `--scene-glyph` and `--scene-glyph-outline`, so that a change of the page's theme does not recolour the scene (decision 0061). A colour that is no token, such as the scenes' ground, is a named constant that says where the page writes it.

### The page's frames

40. **A frame of the page is a 9-slice picture from PixelLab's UI tool.** The panel's frame and the primary and secondary buttons are rolled together, so that they share one style: `create_ui_asset` with one unlabelled `rounded_rect` piece a frame, `palette` the page's A2 colours as `styles.css` holds them, no style image (the icons' black outline is the scene's, and a frame takes the page's ink), at 256×256 for 10 generations; and `update_ui_asset` with `split` cuts the template into one element a frame, at no cost. They live in `art/frames/`, one file a frame named for it, `primary.png`, each byte for byte the PNG in the template's ZIP download (rule 6), with one `provenance.json` that records every call and, for each frame, its UI asset's id and its slice: the pixels from each side of the frame's opaque box that hold its corners whole, their inner rounding and shading included, so that what is left between them, the edges and the middle, repeats no piece of a corner. The slice is measured by reading the frame's pixels, not by eye, and the provenance's `sliceNote` says what was measured and what an edge still carries, the art's own flecks, which repeat with it. The two buttons take one slice, the larger on each side, because a toggle that is on is drawn on the primary's frame (rule 41) and a button must not change size when it is pressed. A UI asset takes no tags; a frame not kept is found by its template's id in the provenance. The art carries A2's colours, so a change of the page's theme does not recolour a frame: a new theme rolls its frames again.
41. **The build trims a frame and names it in a stylesheet.** `packages/client/scripts/copy-art.mjs` trims each frame to its opaque box, publishes it under a name that carries the trimmed picture's hash, refuses a slice that leaves no middle and a file the provenance does not name, and writes `generated/frames.css`, which `angular.json` takes before `src/primitives.css`: for each frame, `--frame-<name>-image`, `--frame-<name>-slice` and `--frame-<name>-width` (`frame-art.mjs`). `primitives.css` draws each with `border-image` at 1×, its border the slice's own pixels, its corners as drawn and its edges and middle repeated, never stretched, with `image-rendering: pixelated`; so the art's pixels and the border's lengths are written nowhere but the provenance. A button's states are its frame as drawn, changed by CSS, because drawn states lost the frame's depth (decision 0062): pressed a shade darker with its label sunk by `--button-press`, disabled drained of colour, focus a ring that follows the frame's own outline, and a toggle that is on, `aria-pressed="true"`, drawn on the primary's frame (decision 0062's amendment). The frames' names are `FRAMES` in `packages/client/src/app/sprite-sets.ts`, and the build refuses a provenance that names others.
42. **A hero's portrait is cut from its sprite set, not made.** The hero tile shows each hero's head and shoulders, which the client's build cuts from its set's `still-south`: a square of 24 art pixels from the figure's top row, centred on the columns those rows fill (`PORTRAIT` in `packages/client/src/app/sprite-sets.ts`, `portraitBox` in `pack-art.mjs`), published under a name that carries the cut's hash with `art/portraits/pictures.json` naming each by its set, as the icons are (rule 27), and drawn at scale 2. A new hero set has its portrait with nothing more done; a set whose still is too small, or empty, fails the build with its name.

## Why

The dated account of each rule, what was tried and what came out, is `docs/process/history.md`, under this document's name.

**Generated once, committed, with its provenance.** A service's output cannot be reproduced on demand: the same call gives a different result, the service may change or close, and the terms the asset was made under can change after it was made. The committed file and a record of how it was made are what last. The provenance is also the licence evidence if a question ever comes up.

**Tags on every character.** A character that was not kept and carries no tag is findable only by its name (Issue-76).

**Connectors on the account.** The agent needs the tools in every session and on every machine the owner uses; the account is the one place that is true. A token in a repository or a CI environment is a credential with no reason to be there.

**The hero sprite set.** The set is the same for every class so that a class's pool of sprite sets can grow by adding sets, with no per-class art rules. Each of rules 8 to 13 was chosen by the owner from alternatives seen at the game's own scale (decision 0025).

**Hand edits and the mirrored west still.** Re-rolling a look for one bad pixel throws away a look the owner otherwise kept, and an edit made before animation carries into every frame. A west rotation can be bad where the east one is not, and the mirror is what the animations already use for west (Issue-73).

**Lining frames up by the feet.** PixelLab places the figure differently on each animation's canvas. Measuring from the pixels fixes every set, present and future, without editing the exported files (Issue-73).

**A camp's art.** A tileset gives every location the same ground in the same style, laid out by the scene; a painted background would have to be redrawn whenever a camp's facilities change, and two players' camps at one location can have different ones. A facility is one sprite because a building assembled from 16 px wall pieces is boxy at this scale. A level keeps its canvas and angle so that an upgrade swaps the picture in place (Issue-80, decision 0027). A terrain is described by what marks it because its plain name rolled nothing worth choosing, and a second location reuses the first's dirt so that a caravan's road is the same earth at both ends (Issue-350). `chosenBy` names the mock-up so that a choice is found from the provenance of what was chosen, and the mock-up is kept as the evidence of it and nothing more (the review of PR-360; Issue-271).

**Interface icons.** One call for every icon keeps them in one style and costs less than one call per icon, and a second call may not match the first, so a pack carries ideas for the icons a later issue needs. 32 px is the favicon's own size and reads at 1× in a menu (Issue-89, Issue-340, Issue-344). What is true of one pack is in that pack's entry so that a candidate's number names one icon (the review of PR-346). Of the actions' icons, `depart` is crossed swords because leaving the camp almost always means a fight; `close`, a red X, is for a view that sits over the camp, a replay, the open adventure or a menu; and `back`, a green arrow, is for where a view steps back through others rather than closing (Issue-385).

**Monsters and props.** A monster is a hero's set so that whatever draws a hero draws a monster. A prop's animations say `no particles, no effects` because an effect is a sprite of its own, and a `down` is interpolated to an end state and faded in code because PixelLab draws no partial transparency (Issue-111). An end state's description is settled before it is spent because it is the dear part, and the cart has no clip for a travel because at the road's speed drawn spokes only flicker (Issue-350, Issue-353).

**Weapons and effects.** Both sprites, the weapon by unit type for now, one effect per ability, and a projectile as a target effect that moves are the shape the owner gave on Issue-15 (Issue-130). The effects tool exports the effect apart from the sprite, with its offset from the feet; its parts come out a cold blue and glowing, so each is given a warm ramp. Each frame's grip is recorded because PixelLab turns a weapon about its canvas and not the hand. A swing is interpolated to the icon turned a right angle because that is the one turn that does not blur pixel art (game.md, "How the game looks"). The hand is one point for every set because every set is made on one skeleton.

**The ranged units' art.** The engine's art tests compare each provenance's list with the engine's content, so an empty list and a `madeFor` keep the art and the code in separate pull requests. The arrow is a sprite of its own to show on the string, so no frame of the bow holds one. A `throw` is given the canvas's numbers because the tool reads them so, not the sprite's (Issue-284).

**The gatherers' art.** Mirroring a committed icon would break the byte-for-byte check of rule 6, and a weapon facing left would need code to turn it; a mirrored start frame costs nothing (Issue-285).

**The scene's text and a drop.** Text set by the browser is smoothed and scaled apart from the art beside it, so the amount is sprites, and the digits come from PixelLab so that it stays the one source of pixel art (rule 1). The atlas is one bit, so the colour and the outline that make a digit read on the meadow are the build's, taken from the stylesheet's tokens, and the committed file is still the service's own. A font is a kind of sprite set so that the page asks for a glyph through the list the build checks (typescript.md, rule 23), and its sheet is named and cached as every set's is. Rule 38 is a test because the owner expects many resources and traits, added a little at a time: a drop with no icon would show nothing in the scene, and nobody would be told (Issue-344).

**Scripts that draw.** A colour written in two places goes stale in one: a palette changed later would leave the owner picking icons from a sheet in colours the scene no longer uses. The rules that keep a value in one place, `docs/standards/angular.md`, rule 17, and `docs/process/best-practices.md`, rule 10, speak of the page and reach no script (the review of PR-348, Issue-344).

**The page's frames.** PixelLab's UI tool promises no exact edge and its art is not on a clean grid, so each slice is measured, and the edges repeat rather than stretch so that a fleck stays one pixel. The build trims a frame rather than the slice counting its margin, so the committed file stays the service's own (rule 6), and it writes the frames' names into a stylesheet because a border-image is CSS, which reads no index at runtime as the page reads the icons' (Issue-385; decision 0062).

**What a provenance says of its files is tested.** A record nobody checks drifts from the files beside it: thirteen sets said their walk's canvas was 64×64 where the south walk's frames were 48×48, and nothing failed (Issue-271).
