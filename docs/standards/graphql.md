# GraphQL and the hub

Standards for the API and `packages/hub`, beside `docs/standards/typescript.md`, whose rules 8 to 12 cover the hub's tests, its libraries, the printed schema and the bundle. This document says how the schema is designed, what a resolver does and never does, how authorization, input, errors and logging are written, and how the data layer is shaped. The rules come from decisions 0012, 0013, 0014, 0023, 0024, 0029 and 0030, with the API shape accepted practice asks for stated as the rule (Issue-145, Issue-155, decision 0038). A convention a lint rule can express is in `eslint.config.mjs`, not here (typescript.md, rule 16). The detail of a rule, the whole of one written here as a single line, what this document holds back and why its rules are as they are, is `docs/standards/graphql-detail.md`, which nothing loads; its opening says when each section is read (decision 0060).

## Rules

### The schema

1. **Code first; the printed schema is the contract.** The schema is built with Pothos in `packages/hub/src/schema/`, printed to `packages/hub/schema.graphql` and committed, and CI fails when the file is stale (typescript.md, rule 11), so a change to the API is a diff of that file, read in review as the contract it is. Every type and every root field has a description (lint `require-description`); a mutation's says what it does, what a repeat does and how it is refused. The schema and the client's operations are linted under `@graphql-eslint`'s `all` tiers: the companion's "Rule 1".
2. **Non-null by default.** The builder sets `defaultFieldNullability: false`; a field is nullable only where the value may be absent (`retiredAt`, `result` before settlement), where authorization may null it (rule 11), or at a root (rule 6). A list is non-null of non-null.
3. **Names are lint's `naming-convention`,** and a mutation is a verb phrase naming what it does to what, `recruitHero`, `startAdventure`: the companion's "Rule 3".
4. **Scalars and enums.** An identifier is `ID`, a location's and a job's content ids included. A timestamp is `DateTime`, from `graphql-scalars`, which says what else a type can say about an input: `UUID` for a request id the client makes, `NonNegativeInt` for a time on the adventure's clock, `PositiveInt` for a level, `JSON` for a value served as stored; an integer scalar is registered through `wholeNumbersOnly` in `builder.ts`, because the library reads a variable with `parseInt` (decision 0039). A set the hub owns, or that the engine's types close, is an enum, an engine's built from the engine's exported list so that a value added there is a value added here. An enum value is `UPPER_CASE` on the wire and the engine's own string inside the hub (`HEROES_HALL` is `heroes-hall`), and the client maps it back in `packages/client/src/app/game.ts` (decision 0038). A value whose set is the engine's content and grows without a schema change, such as a sprite set's directory, is a `String` whose description says what it names. The enums there are: the companion's "Rule 4".
5. **One input object per mutation,** `input: <MutationName>Input!` and no other argument (lint `input-name` with `checkInputType`), so a mutation grows a field without changing its signature.
6. **A mutation answers a result union: errors as data.** `<MutationName>Result` is a union of `<MutationName>Success`, which wraps what the mutation changed, and one object type per expected refusal, each implementing an `Error` interface with `message` and carrying the fields the client needs (`InsufficientResources.short`, `AdventureOpen.adventureId`, `EngineUpdated.version`). The result is nullable at the root (lint `require-nullable-result-in-root`). `@pothos/plugin-errors` builds the union from the error classes the field declares. The response's `errors` array is for what is not the game's business: malformed input (`BAD_USER_INPUT`), a caller who is not signed in (`UNAUTHENTICATED`), a signed-in caller reading what a scope keeps from them (`FORBIDDEN`), and failures nobody expected. A refusal names a game state the player can act on and that may have changed since the client read; an id or a count the client should never have sent, another player's hero, a job the location does not post, a party of the wrong size, is the client's defect and is `BAD_USER_INPUT`. `Conflict` is a refusal, because the player's action is to try again. A request the schema refuses before any resolver runs is answered by Apollo Server with HTTP 400 and the `errors` array (decision 0038).
7. **Idempotent by construction.** A mutation that creates names its work from the client, a `requestId` that becomes the hero's or the adventure's id, the level being built, so a repeat finds the work done and answers it, whoever sent it again (Issue-211); a repeated settlement answers the record as it is and pays nothing (decision 0014). The hub answers "as it is", never "already done" as a refusal. A request id reused with other input is `BAD_USER_INPUT`, never the first request's answer, because the identifier names one request.

### Resolvers

8. **A resolver is a line.** It maps the field's arguments and the context onto one function in `packages/hub/src/<verb>.ts` (`recruitHero`, `startAdventure`, `submitAdventure`) or one repository read, and answers what that answers. No rule lives in `schema.ts`. A read that applies a rule, such as who may see a record, is a function that takes the repository and the caller's id and is tested as a function, in `packages/hub/src/read.ts`, as `readAdventure` is (the review of PR-254), or in its feature's own module, as `heroesSeenAt` is in `seen.ts` (the review of PR-295).
9. **Rules are checked twice.** A function checks every rule against what it read, so the player gets the reason, and the transaction's conditions check them again, which is what holds under concurrent requests (decision 0013). A request that loses a race reads again and answers with the rule that now fails; `CONFLICT` only when no rule explains the failure. The reads are strongly consistent, and the read that would find the work done comes after the reads a refusal is made from, so that a refusal is final only once the work is read as not done after it (Issue-175).
10. **The hub chooses what must not be the client's.** The seed, a hero's sprite set and name, the snapshot's numbers and the deploy's version are drawn or stamped by the hub, from a cryptographic random source and the engine's content (decisions 0026 and 0030); the client sends ids and choices, never randomness and never a result. Content is read from the engine, never copied into the hub.

### Authorization

11. **A scope on every field that needs one** (decision 0012; the scope-auth plugin). `authenticated` on every root field that reads the caller; `self` on every field of a player's private data, `name`, `camps`, `heroes`, `unlocks` and `openAdventure`, which null the field with an error for anyone else (rule 2). What is public by decision is a list, the companion's "Rule 11", reviewed with what each field contains, and held by one table, `ACCESS` in `packages/hub/test/access.test.ts`, whose test walks the built schema and fails on any field whose access differs (decision 0043): a change to the table changes that list in the same pull request, and a new field names its scope in the pull request's description. A failed scope answers `UNAUTHENTICATED` for a caller not signed in and `FORBIDDEN` for one who is, from the builder's `unauthorizedError`; `callerId(ctx)` stands behind every scoped resolver and throws `UNAUTHENTICATED` where a field forgot its scope. How the walk treats each scope is the companion's "Rule 11".
12. **Identity is the authorizer's.** The HTTP API's JWT authorizer validated the token before the function ran; the handler reads the claims off the event and never sees or parses a token (decision 0024). The hub trusts `sub` and reads no other claim: it has no use for a person's email, so it never holds one (decision 0043).
13. **Private and public data are two tables, and what a caller reads is decided field by field** (decisions 0023 and 0043). Only the hub reads either table. The player table's fields are served under `self`, but for the player's id. The location table holds what everyone may see, and may store an owner id for the hub's own checks, as the adventure record's `playerId` does. No field serves that id without a scope: a later owner field is `owner: Player`, null unless the viewer may see that player, under a scope of its own beside `self`, because a repeated id itself links a player's heroes and adventures. A sighting stores no owner until a feature needs one.

### Input

14. **Nothing from the client is trusted, and a check has one place.** What a type can say is the field's scalar (rule 4). What it cannot, and needs no read, is a zod schema on the input field or argument in `schema.ts`, run by `@pothos/plugin-validation` before any resolver (decision 0039), a party of 1 to `MAX_PARTY` distinct ids among them, with the limit stated in the field's description; a failure says its path and the rule in plain words, `input.heroIds: a party is 1 to 4 heroes`. A verb therefore does not check the shape again; what depends on what it read, or on another field, stays in the verb. A value the engine's content must know is looked up with `Object.hasOwn` or the engine's own lookup, never used to index an object. Malformed input is `BAD_USER_INPUT`, from `badInput` or the plugin's `validationError`. Input is checked before a scope (rule 11), and it can tell a caller only what the printed schema publishes. The rest is the companion's "Rule 14".

### Errors and logging

15. **Types and words.** A refusal is a class in `packages/hub/src/refusals.ts`, named for the rule it states (`HallFull`, `InsufficientResources`, `AdventureOpen`), with a message in the player's words that the client may show as it is and the fields the client needs on its type (rule 6); a function names its refusals on the field that answers them, so the printed union says exactly which a mutation can give. Malformed input is `badInput`, the one `GraphQLError` the functions throw. A failure the player cannot act on, a store unavailable, is thrown as it is and reaches the client as an `INTERNAL_SERVER_ERROR` with nothing of the hub in it.
16. **Log lines, never bodies.** Logging goes through the Powertools logger (typescript.md, rule 12): one JSON line per request with the operation name, the duration and the error count, a warning per error, and a warning for what should not happen, such as a submitted log that differs from the replay's, or a transaction cancelled by another still committing (rule 18), which is also a metric. Never variables, responses, tokens, claims or a player's data, in a log line or in the trace, which `test/tracing.test.ts` holds (decision 0055); the one piece of a request a message may carry is the malformed value it refuses. A metric's dimensions are low-cardinality, a name from a closed set, never an id. Nothing in `packages/hub/src` writes to the console (lint `no-console`). What a span carries is the companion's "Rule 16".

### The data layer

17. **The repository is the only caller of DynamoDB, and ElectroDB is what it is made of.** `Repository` (`db/repository.ts`) holds every read and every transaction, through the `Service` of `db/entities.ts`, one entity per item type, each naming its own table, with key templates at `casing: "none"` (decisions 0041 and 0042). A type written whole is checked at compile time against its entity, because ElectroDB drops an attribute it does not declare, and a value the engine or the settlement owns is one attribute typed from its own type, never a `map` that states it again. `keys.ts` is the one statement of the layout, and a new item type is a new sort-key prefix, never a new table (decision 0023). The SDK clients are built from configuration (`db/client.ts`), so the tests point them at a container (decision 0009), and take their HTTP timeouts from `src/sdk.ts`, which `test/timeouts.test.ts` proves (Issue-211). Where ownership is not checked: the companion's "Rule 17".
18. **A write that depends on a read is a conditional transaction.** `service.transaction.write`, which is `TransactWriteItems`, with a `where` on every item the rule depends on; a cancelled result's `code` per item is mapped to a typed error (`HeroExists`, `InsufficientBalance`, `AdventureClosed`), the first `ConditionalCheckFailed` naming the rule. A `TransactionConflict` is run again from the verb's first read after an exponential backoff with full jitter, `CONFLICT_ATTEMPTS` runs in all, and then answers `Conflict`: es-toolkit's `retry` in `packages/hub/src/conflict.ts`, and settlement's own loop, `SETTLE_ATTEMPTS`, which re-reads between attempts. Every run again is a warning and a count, every `Conflict` answered a count in `countingConflicts`, and alarms watch them (decision 0040). No `ClientRequestToken`: the conditions are the idempotency. The backoff's figures and the counts are the companion's "Rule 18".
19. **An object is written once.** A timeline goes to the replay bucket with `If-None-Match: *`, and a stored one wins (Issue-114). The store is an interface, `Timelines`, with an in-memory implementation for the tests and S3 for the stack.

### Tests

20. **Every refusal and every race has a test** against DynamoDB Local, and the handler is called with the event API Gateway sends (typescript.md, rules 8 and 9). A race's test is deterministic: `test/race.ts` commits the winner before each of the loser's calls on the repository in turn, so every point at which the winner can land is run. A `TransactionConflict` is made by `cancelled`, which fails the loser's write and lets the winner commit before each of the loser's calls after it. A verb that makes calls together is raced with no two of its calls in flight at once. The stack test exercises what the laptop cannot: S3, the authorizer, the real roles and both routes.

### Documents

21. **The codes the response's `errors` array can carry are listed once, in rule 6.** Another document or a comment that describes the array points at rule 6 and does not repeat the list, because a code added to one copy leaves the others false (the review of PR-210, Issue-208).

### The environment

22. **A module that reads the environment names its schema, `<Name>Env`, and reads it in an exported `<name>FromEnv(env = process.env)`,** through `parseEnv` (decision 0039), so a test passes the environment it means and does not re-import the module: `DbEnv` and `configFromEnv`, `VersionEnv` and `versionFromEnv` (the review of PR-217, Issue-206).

### Personal data

23. **A field holding personal data is never public.** Personal data is what names or reaches a person, an email address above all, and a field written to hold it stays closed until a decision opens it, as `Player.name` stays closed until a public name is decided. Such a field takes `self`, or a later scope that says who may see it, and nothing of the kind is on rule 11's public list. A test asserts that a caller the scope refuses gets none of it (Issue-170, decision 0043).
24. **A reader of the location table other than the hub is given no owner id.** A role, a stream's consumer or an export reads a projection without `playerId`, or a decision record says why it may hold it, because no scope applies there and rule 13 rests on the hub being the only reader. Decision 0023 names the live channel and the reporting export as later readers (the review of PR-223).

### What a test draws

25. **A test fixes every draw its outcome depends on.** Where a verb draws, the seed above all, the draw is a parameter of the function whose default is the cryptographic source (rule 10), as `issueSeed` is of `startAdventure`, so that a test passes the seed it means; no caller outside a test passes it, and nothing of a request reaches it (the review of PR-346, Issue-340).
26. **A test that picks a seed for an engine draw asks the engine for that draw,** by running what the hub will run, `expandStages` for who a job sets against the party and `replay` for what an adventure brings home, and does not restate how the engine derives a generator's seed or a unit's id, which would pick the wrong seed the day the engine numbered differently (the review of PR-347, Issue-341).
27. **What a test passes in place of the engine's content is a verb's last parameter, whose default is the engine's,** as the job `submitAdventure`'s replay reads is, so that a test settles a job the game does not have; no caller outside a test passes it, and nothing of a request reaches it (the review of PR-359, Issue-351).

### A condition several transactions carry

28. **A condition that several transactions carry is written once in the repository, and each transaction calls it,** because a copy that differed would be a location open by one verb and closed by the others: `unlockHeld`, which start, recruit and build call (decision 0059), and `cappedCredits` and `warehouseHeld` (the reviews of PR-359 and PR-371).

### What a request fills

29. **A verb's parameters that a request fills come before those only a test passes,** as a caravan's cargo and its heroes who stay go ahead of `now` and `issueSeed` in `startAdventure`, so that a resolver never passes `undefined` to reach one, one argument away from passing a test's parameter by mistake (the review of PR-371, Issue-354).
