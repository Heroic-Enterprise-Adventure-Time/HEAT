# GraphQL and the hub

Standards for the API and `packages/hub`, beside `docs/standards/typescript.md`, whose rules 8 to 12 cover the hub's tests, its libraries, the printed schema and the bundle. This document says how the schema is designed, what a resolver does and never does, how authorization, input, errors and logging are written, and how the data layer is shaped. Written on 2026-10-24 (Issue-145) from the code on `main` and from decisions 0012, 0013, 0014, 0023, 0024, 0029 and 0030, with the API shape accepted practice asks for stated as the rule; the code reached it on 2026-11-02 (Issue-155, decision 0038). A convention a lint rule can express is in `eslint.config.mjs`, not here (typescript.md, rule 16); the rules below say which rule holds each where one does.

## Rules

### The schema

1. **Code first; the printed schema is the contract.** The schema is built with Pothos in `packages/hub/src/schema/`, printed to `packages/hub/schema.graphql` and committed, and CI fails when the file is stale (typescript.md, rule 11), so a change to the API is a diff of that file, read in review as the contract it is. The file is linted under `@graphql-eslint`'s `all` tier; `alphabetize` is off because the printer orders the file, `no-root-type` because it forbids the `Mutation` root, `strict-id-in-types` because the API's value types (`Reward`, `Holding`, `UnitStats`) have no identity, and `require-field-of-type-query-in-mutation-result` because the client reads the player again after a mutation rather than refetching through a `query` field. Every type and every root field has a description (lint `require-description`); a mutation's says what it does, what a repeat does and how it is refused. The client's operations, `packages/client/src/app/graphql/*.graphql`, are linted under the plugin's operations `all` tier against the same schema, so a document the hub would refuse fails lint; `no-one-place-fragments` is off because a fragment there names the shape a view type derives from (angular.md, rule 5), and the two lint blocks share one parser configuration, because the plugin keeps the first it is given for every file after.
2. **Non-null by default.** The builder sets `defaultFieldNullability: false`; a field is nullable only where the value may be absent (`retiredAt`, `result` before settlement), where authorization may null it (rule 11), or at a root (rule 6). A list is non-null of non-null.
3. **Names** (lint `naming-convention`): types `PascalCase`, fields and arguments `camelCase`, enum values `UPPER_CASE`, no `Type`, `Enum` or `Input` noise in a type's name, no `get` or `query` prefix on a root field. A mutation is a verb phrase naming what it does to what: `recruitHero`, `startAdventure`, `discardAdventure`.
4. **Scalars and enums.** An identifier is `ID`, a location's and a job's content ids included. A timestamp is `DateTime`, from `graphql-scalars`. A set the hub owns, or that the engine's types close, is an enum: `HeroStatus` and `AdventureStatus`, the hub's own; `UnitType`, `Material`, `FacilityKind`, `AdventureOutcome`, `StageKind` and `StageEnding`, the engine's, built from the engine's exported lists so that a value added there is a value added here. An enum value is `UPPER_CASE` on the wire (rule 3) and the engine's own string inside the hub (`HEROES_HALL` is `heroes-hall`), mapped by the enum definition; the client maps it back where it reads the hub, in `packages/client/src/app/game.ts`, so that nothing past that file sees a wire value (decision 0038). A value whose set is the engine's content and grows without a schema change, such as a sprite set's directory, is a `String` whose description says what it names.
5. **One input object per mutation,** `input: <MutationName>Input!` and no other argument (lint `input-name` with `checkInputType`), so a mutation grows a field without changing its signature and the client has one object to build.
6. **A mutation answers a result union: errors as data.** `<MutationName>Result` is a union of `<MutationName>Success`, which wraps what the mutation changed (`hero`, `camp`, `adventure`), and one object type per expected refusal, each implementing an `Error` interface with `message` and carrying the fields the client needs (`InsufficientResources.short`, `Requires.missing`, `AdventureOpen.adventureId`, `EngineUpdated.version`). The result is nullable at the root (lint `require-nullable-result-in-root`). `@pothos/plugin-errors` builds the union from the error classes the field declares, so a function keeps throwing a typed error and the plugin resolves it to its type. The response's `errors` array is for what is not the game's business: malformed input (`BAD_USER_INPUT`), a caller who is not signed in (`UNAUTHENTICATED`), and failures nobody expected. The line between them: a refusal names a game state the player can act on and that may have changed since the client read; an id or a count the client should never have sent, another player's hero or adventure, a job the location does not post, a party of the wrong size, is the client's defect and is `BAD_USER_INPUT`. `Conflict` is a refusal, because the player's action is to try again. `joinGame`, which nothing refuses, answers a union of its success alone. The shape is Apollo's "Errors as data" guide, read 2026-10-24; what was weighed is decision 0038.
7. **Idempotent by construction.** A mutation that creates names its work from the client, a `requestId` that becomes the hero's id, the level being built, so a repeat finds the work done and answers it; a repeated settlement answers the record as it is and pays nothing (decision 0014). The hub answers "as it is", never "already done" as a refusal.

### Resolvers

8. **A resolver is a line.** It maps the field's arguments and the context onto one function in `packages/hub/src/<verb>.ts` (`recruitHero`, `startAdventure`, `submitAdventure`) or one repository read, and answers what that answers. No rule lives in `schema.ts`.
9. **Rules are checked twice.** A function checks every rule against what it read, so the player gets the reason, and the transaction's conditions check them again, which is what holds under concurrent requests (decision 0013). A request that loses a race reads again and answers with the rule that now fails; `CONFLICT` only when no rule explains the failure.
10. **The hub chooses what must not be the client's.** The seed, a hero's sprite set and name, the snapshot's numbers and the deploy's version are drawn or stamped by the hub, from a cryptographic random source and the engine's content (decisions 0026 and 0030); the client sends ids and choices, never randomness and never a result. Content is read from the engine, never copied into the hub.

### Authorization

11. **A scope on every field that needs one** (decision 0012; the scope-auth plugin). `authenticated` on every root field that reads the caller; `self` on every field of a player's private data, `camps`, `heroes` and `openAdventure`, which null the field with an error for anyone else (rule 2). Public by decision, and listed here so that the list is reviewed: `player(id)` with `id` and `name`; `version`; `SeenHero`'s fields, which never say whose a hero is (decision 0029); and a settled `adventure(id)`, for its replay. A new field names its scope in the pull request description. `callerId(ctx)` stands behind every scoped resolver and throws `UNAUTHENTICATED` where a field forgot its scope.
12. **Identity is the authorizer's.** The HTTP API's JWT authorizer validated the token before the function ran; the handler reads the claims off the event and never sees or parses a token (decision 0024). The hub trusts `sub`, and reads `email` only to name a profile on first sign-in.
13. **Private and public data are two tables** (decision 0023). The player table is read under `self` only; the location table holds what everyone may see and nothing that says whose a hero is.

### Input

14. **Nothing from the client is trusted.** A function checks shape before it reads: a UUID is matched, a party is 1 to `MAX_PARTY`, a log has at most `MAX_OVERRIDES` entries with whole-number times and the party's own heroes; a value the engine's content must know, a location, a job, a unit type, is looked up with `Object.hasOwn` or the engine's own lookup, never used to index an object. Malformed input is `BAD_USER_INPUT`.

### Errors and logging

15. **Types and words.** A refusal is a class in `packages/hub/src/refusals.ts`, named for the rule it states (`HallFull`, `InsufficientResources`, `AdventureOpen`), with a message in the player's words that the client may show as it is and the fields the client needs on its type (rule 6); its object type's name is what the client reads, and a function names its refusals on the field that answers them, so the printed union says exactly which a mutation can give. Malformed input is `badInput`, the one `GraphQLError` the functions throw. A failure the player cannot act on, a store unavailable, is thrown as it is and reaches the client as an `INTERNAL_SERVER_ERROR` with nothing of the hub in it.
16. **Log lines, never bodies.** Logging goes through the Powertools logger (typescript.md, rule 12): one JSON line per request with the operation name, the duration and the error count; a warning per error with its message and path; a warning for what should not happen, such as a submitted log that differs from the replay's. Never variables, responses, tokens, claims or a player's data. Nothing in `packages/hub/src` writes to the console (lint `no-console`).

### The data layer

17. **The repository is the only caller of DynamoDB.** `Repository` (`db/repository.ts`) holds every read and every transaction; keys are built in `db/keys.ts` and nowhere else, and a new item type is a new sort-key prefix, never a new table (decision 0023). The SDK clients are built from configuration (`db/client.ts`), so the tests point them at a container and the code does not know (decision 0009).
18. **A write that depends on a read is a conditional transaction.** `TransactWriteItems` with a condition on every item the rule depends on; a failed condition is mapped by position to a typed error (`HeroExists`, `InsufficientBalance`, `AdventureClosed`) that the function reads, and a `TransactionConflict` is retried by the caller. No `ClientRequestToken`: the conditions are the idempotency, and a repeat is a typed error the caller maps.
19. **An object is written once.** A timeline goes to the replay bucket with `If-None-Match: *`, and a stored one wins (Issue-114). The store is an interface, `Timelines`, with an in-memory implementation for the tests and S3 for the stack.

### Tests

20. **Every refusal and every race has a test** against DynamoDB Local, and the handler is called with the event API Gateway sends (typescript.md, rules 8 and 9). The stack test exercises what the laptop cannot: S3, the authorizer, the real roles and both routes.

## Held back

Nothing, since Issue-156 (2026-11-02) generated the client's operations and types from the committed schema (angular.md, rule 5).

## Why

Code first with the printed schema committed is decision 0012's shape, and the committed file is what makes a schema reviewable (typescript.md, "Why"). The rules for scalars, input objects and result unions are the GraphQL community's accepted practice, as Apollo's schema design guides state it, and were taken on 2026-10-24 when the owner weighted accepted practice over the code as it was: the hub's `GraphQLError` with a code in `extensions` was Apollo's older documented shape and still correct, but a union per mutation puts every refusal a player can get into the contract, typed, where a client reads it with `__typename` instead of a string it has to know. The two tiers of error, data for the game's refusals and the `errors` array for what is not the game's business, follow the same guide. Both changes touched the client and the stack test, which is why they were an issue of their own, Issue-155, and not a rubric's pull request; the enum values' two spellings, the API's on the wire and the engine's inside, are the shape the tools on both sides are built for, and renaming the engine's values would have been a migration of stored data for a naming preference (decision 0038).

Rules checked twice is the shape every transaction took from Issue-81 on: the read gives the reason, the condition gives the guarantee, and neither alone does both. The hub choosing the seed and the name is decision 0001's verification made real: a client that chose its randomness could choose its outcome.

Authorization by declared scopes is decision 0012's reason for Pothos's scope-auth plugin, and the list of public fields is in this document so that adding to it is a reviewed change. Logging lines and never bodies is the hub's observability module as first written: a GraphQL response can hold a player's whole camp, and a log that held it would be a second copy of the private table.
