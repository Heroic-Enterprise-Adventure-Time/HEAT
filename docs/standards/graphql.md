# GraphQL and the hub

Standards for the API and `packages/hub`, beside `docs/standards/typescript.md`, whose rules 8 to 12 cover the hub's tests, its libraries, the printed schema and the bundle. This document says how the schema is designed, what a resolver does and never does, how authorization, input, errors and logging are written, and how the data layer is shaped. Written on 2026-10-24 (Issue-145) from the code on `main` and from decisions 0012, 0013, 0014, 0023, 0024, 0029 and 0030, with the API shape accepted practice asks for stated as the rule; the code reached it on 2026-11-02 (Issue-155, decision 0038). A convention a lint rule can express is in `eslint.config.mjs`, not here (typescript.md, rule 16); the rules below say which rule holds each where one does.

## Rules

### The schema

1. **Code first; the printed schema is the contract.** The schema is built with Pothos in `packages/hub/src/schema/`, printed to `packages/hub/schema.graphql` and committed, and CI fails when the file is stale (typescript.md, rule 11), so a change to the API is a diff of that file, read in review as the contract it is. The file is linted under `@graphql-eslint`'s `all` tier; `alphabetize` is off because the printer orders the file, `no-root-type` because it forbids the `Mutation` root, `strict-id-in-types` because the API's value types (`Reward`, `Holding`, `UnitStats`) have no identity, and `require-field-of-type-query-in-mutation-result` because the client reads the player again after a mutation rather than refetching through a `query` field. Every type and every root field has a description (lint `require-description`); a mutation's says what it does, what a repeat does and how it is refused. The client's operations, `packages/client/src/app/graphql/*.graphql`, are linted under the plugin's operations `all` tier against the same schema, so a document the hub would refuse fails lint; `no-one-place-fragments` is off because a fragment there names the shape a view type derives from (angular.md, rule 5), and the two lint blocks share one parser configuration, because the plugin keeps the first it is given for every file after.
2. **Non-null by default.** The builder sets `defaultFieldNullability: false`; a field is nullable only where the value may be absent (`retiredAt`, `result` before settlement), where authorization may null it (rule 11), or at a root (rule 6). A list is non-null of non-null.
3. **Names** (lint `naming-convention`): types `PascalCase`, fields and arguments `camelCase`, enum values `UPPER_CASE`, no `Type`, `Enum` or `Input` noise in a type's name, no `get` or `query` prefix on a root field. A mutation is a verb phrase naming what it does to what: `recruitHero`, `startAdventure`, `discardAdventure`.
4. **Scalars and enums.** An identifier is `ID`, a location's and a job's content ids included. A timestamp is `DateTime`, from `graphql-scalars`, and that library says what else a type can say about an input: `UUID` for a request id the client makes (an identifier the hub issues stays `ID`), `NonNegativeInt` for a time on the adventure's clock, `PositiveInt` for a level, and `JSON` for a value served as it was stored. An integer scalar is registered through `wholeNumbersOnly` in `builder.ts`, because the library reads a variable with `parseInt` (decision 0039). A set the hub owns, or that the engine's types close, is an enum: `HeroStatus` and `AdventureStatus`, the hub's own; `UnitType`, `Material`, `FacilityKind`, `AdventureOutcome`, `StageKind` and `StageEnding`, the engine's, built from the engine's exported lists so that a value added there is a value added here. An enum value is `UPPER_CASE` on the wire (rule 3) and the engine's own string inside the hub (`HEROES_HALL` is `heroes-hall`), mapped by the enum definition; the client maps it back where it reads the hub, in `packages/client/src/app/game.ts`, so that nothing past that file sees a wire value (decision 0038). A value whose set is the engine's content and grows without a schema change, such as a sprite set's directory, is a `String` whose description says what it names.
5. **One input object per mutation,** `input: <MutationName>Input!` and no other argument (lint `input-name` with `checkInputType`), so a mutation grows a field without changing its signature and the client has one object to build.
6. **A mutation answers a result union: errors as data.** `<MutationName>Result` is a union of `<MutationName>Success`, which wraps what the mutation changed (`hero`, `camp`, `adventure`), and one object type per expected refusal, each implementing an `Error` interface with `message` and carrying the fields the client needs (`InsufficientResources.short`, `Requires.missing`, `AdventureOpen.adventureId`, `EngineUpdated.version`). The result is nullable at the root (lint `require-nullable-result-in-root`). `@pothos/plugin-errors` builds the union from the error classes the field declares, so a function keeps throwing a typed error and the plugin resolves it to its type. The response's `errors` array is for what is not the game's business: malformed input (`BAD_USER_INPUT`), a caller who is not signed in (`UNAUTHENTICATED`), a signed-in caller reading what a scope keeps from them (`FORBIDDEN`), and failures nobody expected. The line between them: a refusal names a game state the player can act on and that may have changed since the client read; an id or a count the client should never have sent, another player's hero or adventure, a job the location does not post, a party of the wrong size, is the client's defect and is `BAD_USER_INPUT`. `Conflict` is a refusal, because the player's action is to try again. `joinGame`, which nothing refuses, answers a union of its success alone. The shape is Apollo's "Errors as data" guide, read 2026-10-24; what was weighed is decision 0038.
7. **Idempotent by construction.** A mutation that creates names its work from the client, a `requestId` that becomes the hero's id, the level being built, so a repeat finds the work done and answers it; a repeated settlement answers the record as it is and pays nothing (decision 0014). The hub answers "as it is", never "already done" as a refusal. A request id reused with other input, a `requestId` that recruited a villager sent again for a fighter, is `BAD_USER_INPUT`, never the first request's answer: the identifier names one request, and a mismatch is the client's defect (the Builders' Library, "Making retries safe with idempotent APIs").

### Resolvers

8. **A resolver is a line.** It maps the field's arguments and the context onto one function in `packages/hub/src/<verb>.ts` (`recruitHero`, `startAdventure`, `submitAdventure`) or one repository read, and answers what that answers. No rule lives in `schema.ts`.
9. **Rules are checked twice.** A function checks every rule against what it read, so the player gets the reason, and the transaction's conditions check them again, which is what holds under concurrent requests (decision 0013). A request that loses a race reads again and answers with the rule that now fails; `CONFLICT` only when no rule explains the failure. The reads are strongly consistent, because an eventually consistent read may not show the winner's writes yet, and the read that would find the work done (the hero by its request id, the level built, the record settled or discarded) comes after the reads a refusal is made from: a repeat that won changed what the loser reads, so a refusal is only final once the work is read as not done after it (Issue-175).
10. **The hub chooses what must not be the client's.** The seed, a hero's sprite set and name, the snapshot's numbers and the deploy's version are drawn or stamped by the hub, from a cryptographic random source and the engine's content (decisions 0026 and 0030); the client sends ids and choices, never randomness and never a result. Content is read from the engine, never copied into the hub.

### Authorization

11. **A scope on every field that needs one** (decision 0012; the scope-auth plugin). `authenticated` on every root field that reads the caller; `self` on every field of a player's private data, `camps`, `heroes` and `openAdventure`, which null the field with an error for anyone else (rule 2). Public by decision, and listed here so that the list is reviewed: `player(id)` with `id` and `name`; `version`; `SeenHero`'s fields, which never say whose a hero is (decision 0029); and a settled `adventure(id)`, for its replay. A new field names its scope in the pull request description. A failed scope answers `UNAUTHENTICATED` for a caller not signed in and `FORBIDDEN` for one who is, from the builder's `unauthorizedError`, because the plugin's own error keeps its code where Apollo does not read it and would answer `INTERNAL_SERVER_ERROR`. `callerId(ctx)` stands behind every scoped resolver and throws `UNAUTHENTICATED` where a field forgot its scope.
12. **Identity is the authorizer's.** The HTTP API's JWT authorizer validated the token before the function ran; the handler reads the claims off the event and never sees or parses a token (decision 0024). The hub trusts `sub`, and reads `email` only to name a profile on first sign-in.
13. **Private and public data are two tables** (decision 0023). The player table is read under `self` only; the location table holds what everyone may see and nothing that says whose a hero is.

### Input

14. **Nothing from the client is trusted, and a check has one place.** What a type can say is the field's scalar (rule 4), so the contract shows it. What it cannot, and needs no read, is a zod schema on the input field or argument in `schema.ts`, run by `@pothos/plugin-validation` before any resolver (decision 0039): a party of 1 to `MAX_PARTY` distinct ids, a log of at most `MAX_OVERRIDES` entries, the length of an ability id, a known location where a field does nothing else with it. A limit a schema holds is stated in the field's description, so the printed schema shows it as a scalar's does. A failure says its path and the rule in plain words, `input.heroIds: a party is 1 to 4 heroes`. A verb therefore receives input of the right shape and does not check it again; what depends on what it read, or on another field, stays in the verb: the job exists at this location, the hero is the player's, the level is the next, an entry names a hero of the party. A value the engine's content must know is looked up with `Object.hasOwn` or the engine's own lookup, never used to index an object. Malformed input is `BAD_USER_INPUT`, from `badInput` or from the plugin's `validationError`, which calls it; a scalar's refusal is Apollo's own `BAD_USER_INPUT`, with HTTP 400 because execution never started. Input is checked before a scope (rule 11), which the plugin's place in Pothos decides, and it can tell a caller only what the printed schema publishes.

### Errors and logging

15. **Types and words.** A refusal is a class in `packages/hub/src/refusals.ts`, named for the rule it states (`HallFull`, `InsufficientResources`, `AdventureOpen`), with a message in the player's words that the client may show as it is and the fields the client needs on its type (rule 6); its object type's name is what the client reads, and a function names its refusals on the field that answers them, so the printed union says exactly which a mutation can give. Malformed input is `badInput`, the one `GraphQLError` the functions throw. A failure the player cannot act on, a store unavailable, is thrown as it is and reaches the client as an `INTERNAL_SERVER_ERROR` with nothing of the hub in it.
16. **Log lines, never bodies.** Logging goes through the Powertools logger (typescript.md, rule 12): one JSON line per request with the operation name, the duration and the error count; a warning per error with its message and path; a warning for what should not happen, such as a submitted log that differs from the replay's, or a transaction cancelled by another still committing (rule 18). Never variables, responses, tokens, claims or a player's data; the one piece of a request a message may carry is the malformed value it refuses, a scalar's or `badInput`'s, because that is the client's own defect and nothing of a player's. Nothing in `packages/hub/src` writes to the console (lint `no-console`).

### The data layer

17. **The repository is the only caller of DynamoDB.** `Repository` (`db/repository.ts`) holds every read and every transaction; keys are built in `db/keys.ts` and nowhere else, and a new item type is a new sort-key prefix, never a new table (decision 0023). The SDK clients are built from configuration (`db/client.ts`), so the tests point them at a container and the code does not know (decision 0009).
18. **A write that depends on a read is a conditional transaction.** `TransactWriteItems` with a condition on every item the rule depends on; a failed condition is mapped by position to a typed error (`HeroExists`, `InsufficientBalance`, `AdventureClosed`) that the function reads, and a `TransactionConflict` is retried by the caller. The other transaction is still committing, and the SDK does not retry a cancelled transaction, so a read made at once may not show it: the verb runs again from its first read after an exponential backoff with full jitter, a wait drawn from zero up to 50 ms and then up to 100 ms, the SDK's own schedule and the form the developer guide recommends between concurrent clients, `CONFLICT_ATTEMPTS` runs in all, and then answers `Conflict`. The retry is es-toolkit's `retry` (typescript.md, rule 17), in `packages/hub/src/conflict.ts`; settlement keeps its own loop, `SETTLE_ATTEMPTS`, which re-reads between attempts, and waits the same backoff. Every run again is a warning in the log (rule 16), because the conflict rate is what the alarms do not see. No `ClientRequestToken`: the conditions are the idempotency, and a repeat is a typed error the caller maps.
19. **An object is written once.** A timeline goes to the replay bucket with `If-None-Match: *`, and a stored one wins (Issue-114). The store is an interface, `Timelines`, with an in-memory implementation for the tests and S3 for the stack.

### Tests

20. **Every refusal and every race has a test** against DynamoDB Local, and the handler is called with the event API Gateway sends (typescript.md, rules 8 and 9). A race's test is deterministic: `test/race.ts` commits the winner before each of the loser's calls on the repository in turn, so every point at which the winner can land is run, not only those that concurrent requests happen to hit. A failure that sequential requests cannot produce, a `TransactionConflict`, is made by `cancelled`, which fails the loser's write and lets the winner commit before each of the loser's calls after it in turn. A verb that makes calls together is raced with no two of its calls in flight at once, since a call is counted as it starts. The stack test exercises what the laptop cannot: S3, the authorizer, the real roles and both routes.

### Documents

21. **The codes the response's `errors` array can carry are listed once, in rule 6.** Another document or a comment that describes the array points at rule 6 and does not repeat the list, because a code added to one copy leaves the others false. From the review of PR-210 (Issue-208), which found it in four other places.

## Held back

- **A snapshot read for a lost race** (Issue-175, 2026-11-02). Rule 9's re-read is separate reads, a `Query` of the camp and a `GetItem` of the hero, and DynamoDB isolates them from a transaction only as read-committed: while the winner's transaction is committing, a read can see some of its items new and others old (the developer guide's "Isolation levels for DynamoDB transactions"). A loser that reads in that window can still answer a refusal for a repeat it lost to; the window is the winner's commit, milliseconds, against the seconds between a request and its repeat. `TransactGetItems` over the items a verb reads closes it, at the cost of a read per verb built from keys rather than the camp's `Query`, and a retry when the read conflicts with a write. Held back as out of proportion while nothing has shown the window; a race that does is the reason to build it.

## Why

Code first with the printed schema committed is decision 0012's shape, and the committed file is what makes a schema reviewable (typescript.md, "Why"). The rules for scalars, input objects and result unions are the GraphQL community's accepted practice, as Apollo's schema design guides state it, and were taken on 2026-10-24 when the owner weighted accepted practice over the code as it was: the hub's `GraphQLError` with a code in `extensions` was Apollo's older documented shape and still correct, but a union per mutation puts every refusal a player can get into the contract, typed, where a client reads it with `__typename` instead of a string it has to know. The two tiers of error, data for the game's refusals and the `errors` array for what is not the game's business, follow the same guide. Both changes touched the client and the stack test, which is why they were an issue of their own, Issue-155, and not a rubric's pull request; the enum values' two spellings, the API's on the wire and the engine's inside, are the shape the tools on both sides are built for, and renaming the engine's values would have been a migration of stored data for a naming preference (decision 0038).

One place for each check is decision 0039. The checks had been written by hand in the verbs, correct and invisible to a reader of the contract, so they ran after the reads they should have saved, and a test had to reach a verb to see them.

Rules checked twice is the shape every transaction took from Issue-81 on: the read gives the reason, the condition gives the guarantee, and neither alone does both. The hub choosing the seed and the name is decision 0001's verification made real: a client that chose its randomness could choose its outcome.

Authorization by declared scopes is decision 0012's reason for Pothos's scope-auth plugin, and the list of public fields is in this document so that adding to it is a reviewed change. Logging lines and never bodies is the hub's observability module as first written: a GraphQL response can hold a player's whole camp, and a log that held it would be a second copy of the private table.
