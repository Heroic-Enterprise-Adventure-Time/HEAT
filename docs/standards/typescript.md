# TypeScript and Node

Standards for every TypeScript package in this repository: the engine, the hub (a Lambda function, decision 0012), the Angular client, and the tooling around them. The client follows these where Angular's own conventions do not say otherwise; "The client" below says where they do.

## Rules

### Versions and dependencies

1. **Latest, preferring LTS where it exists.** Node is the current LTS line, pinned by major in `.node-version` at the repository root; `fnm`, CI, the bundler's target and the Lambda runtime identifier (`nodejs<major>.x`, in Terraform) all follow that one number. CI runs one exact release of that major, pinned with its checksum in `.github/actions/node`, which refuses any other major (`docs/process/best-practices.md`, rule 14; decision 0048); the pin is moved to the line's latest patch in a pull request of its own. Libraries are kept at their latest release; a library with an LTS line is kept on that line. Falling behind is a defect to fix, not a state to maintain. Dependabot opens the pull requests (`.github/dependabot.yml`); a major that cannot be taken yet is listed under "Held back" in `docs/standards/typescript-dependencies.md`, with the reason and what releases it, and is ignored in `.github/dependabot.yml` by the same pull request.
2. **Exact pins, committed lock file.** `package.json` names exact versions, never ranges, and `package-lock.json` is committed. CI installs with `npm ci`, so what runs there is what ran on the laptop.
3. **Install scripts are approved by name.** npm withholds packages' install scripts until they are listed under `allowScripts` in the root `package.json`. A new one is approved with `npm install-scripts approve <package>`, in the pull request that introduces the dependency, and the pull request description says what the script does.
4. **One source of truth for functions and routes.** `manifest.json` at the repository root lists every Lambda with its handler, memory, timeout and routes. The bundler and Terraform read it; nothing declares a function or route anywhere else.

### Language and modules

5. **ES modules only.** Every package is `"type": "module"`. Imports of local files carry the `.js` extension, as Node's ESM resolution requires. The base settings live in `tsconfig.base.json`; a package overrides only what it must, and says why in a comment.
6. **Strict everything.** `strict`, `exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`, `noPropertyAccessFromIndexSignature` and `verbatimModuleSyntax` are on and stay on, in `tsconfig.base.json`. A type error is fixed at its cause. `any` is a last resort and carries a comment. The non-null assertion `!` is not used: a value that may be absent is narrowed, or its absence fails with a message, as `must(value, what)` does, one function in the engine (`packages/engine/src/must.ts`, exported from `@heat/engine`, the package every other package imports, rule 7) and used by every package's source and tests, and as `callerId` does in the hub's resolvers (lint rule `no-non-null-assertion`, rule 16). In source, `must` names the invariant the code relies on, a Map entry just written or an index a loop keeps in range, so that the invariant failing fails there with a message rather than later as a TypeError. A property of an index signature is read with brackets, `env["HEAT_VERSION"]`, which is what the flag enforces, so that a dynamic key looks dynamic.
7. **Shared code is a package, not a Lambda.** Logic the client and the backend both need, above all the engine, is a workspace package that both import. A Lambda never invokes another Lambda to run shared logic.

### Testing

8. **Vitest, in every package, run by `npm test` at the root.** Unit tests need nothing installed. Integration tests start their own containers through Testcontainers, so they need Docker and nothing else, on a laptop and on CI alike (decision 0009). Two kinds of test are outside Vitest. The browser test of a running stack is Playwright's, run by the workflows after the apply and not by `npm test` (decision 0045; `docs/standards/angular.md`, rule 18). The tests of what lives in no package, the hooks under `.claude/hooks/` and the scripts under `scripts/`, are `*.test.mjs` files beside what they test, run by Node's own runner, `node --test`, through `npm run test:hooks` and `npm run test:scripts`, which `npm test` runs first: they need nothing installed, as a script that a job runs under a role may import nothing but Node's own modules (`docs/process/best-practices.md`, rule 13). A package's own build script is tested the same way, beside it: the client's art packer by `packages/client/scripts/pack-art.test.mjs`, which the client's `npm test` runs before its specs, because Angular's test builder takes only the application's specs. A package's `tsconfig.json` covers its tests and its `vitest.config.ts` as well as its source, so `npm run typecheck` and the typed lint (rule 16) see them; a package that emits, the engine, builds from `tsconfig.build.json`, which narrows that to `src`.
9. **Handlers are tested as functions.** A Lambda handler is exercised by calling it with a synthesized event of the exact shape AWS sends, never through a mocked SDK inside the code under test. What a handler's middleware does is tested the same way, by calling the handler, not by calling the library in its place, so that a test shows the middleware doing it (the review of PR-209).

### The hub

10. **Apollo Server, Pothos code-first, scope-auth for authorization.** Field-level access is declared as scopes on fields and types; a field the caller may not read resolves to null with an error on that field, so such fields are declared nullable.
11. **The printed schema is committed, and the client's code is generated from it.** `npm run schema:print` writes `packages/hub/schema.graphql` from the Pothos builder; CI fails if the committed file is stale. Every pull request that changes the API therefore shows the change as a schema diff. `npm run codegen` then generates the client's operations and types from that file with GraphQL Code Generator's client preset (`codegen.mjs` at the root), into `packages/client/src/app/graphql/generated/`, committed too and checked current by CI the same way, so the client never reads a running hub to build and the same pull request shows the client's types changing beside the schema (`docs/standards/angular.md`, rule 5).

### Bundling

12. **One ESM file per function, with the AWS SDK beside it.** `scripts/bundle.mjs` bundles each function from the manifest with esbuild into `dist/<name>/`, targeting the Node major in `.node-version`, dependencies included, Powertools among them, all but the AWS SDK v3: the files of `@aws-sdk` and `@smithy` that the bundle's imports load, traced by `@vercel/nft`, are copied beside the file as `dist/<name>/node_modules` from what the lock file installed, because AWS's OpenTelemetry layer instruments the SDK as it is loaded and cannot see one inside the file (decision 0055). It is the function's own copy, never the runtime's. Terraform zips that directory and passes it to the function with its hash, so a code change is a change in the plan (decision 0017). Logging goes through the Powertools logger as JSON lines and metrics through its metrics as embedded metric format lines in the log, both at one version, configured by the environment variables Terraform sets on the function. Tracing is OpenTelemetry's: the function's span and each SDK call's are the layer's, a root field's is the schema's tracing plugin (rule 17), and nothing in a function's own code starts the SDK or exports a span. `@middy/core` wraps a handler with the two Powertools middlewares, `injectLambdaContext` and `logMetrics`, with the function's own handler innermost, and only those: what middy's other middlewares do, Apollo's plugins and the integration's own option already do for the hub. Its early timeout is off, `timeoutEarlyInMillis: 0`, so that a function never answers with work still pending (decision 0040).

### The client

13. **Angular, latest major, every `@angular/*` package on one exact version.** `packages/client` is an Angular application generated by the Angular CLI: standalone components, zoneless, the router, Vitest through `@angular/build:unit-test` with jsdom, no server-side rendering. Angular's packages move together, with `ng update` on a branch of their own, because the update runs the migrations between majors; Dependabot therefore ignores `@angular/*` majors, and `angular-eslint`'s, whose major tracks Angular's, and takes the minors and patches with everything else. Angular states the TypeScript versions it accepts (22 accepts `>=6.0 <6.1`), so the repository's one TypeScript pin follows Angular's window. How the client itself is written, its components, where its data lives, its templates and the scene's boundary, is `docs/standards/angular.md`, which applies beside this document.
14. **One tsconfig base, the bundler's overrides.** `packages/client/tsconfig.json` extends `tsconfig.base.json`, as rule 5 says, and overrides what the Angular build needs: `module: preserve`, `moduleResolution: bundler`, the DOM libraries, no declarations, and Angular's own flags, each with its reason in the file. Rule 6's flags stay on. Local imports in the client are extensionless, Angular's convention, because the bundler resolves them and Node never runs them; rule 5's `.js` extension is for the packages Node runs. The browser test's files are the client's too, extensionless, because Playwright's loader resolves them.
15. **The dev server and the build.** `npm start --workspace @heat/client` serves the client at `http://localhost:4200` with live reload, and `proxy.conf.mjs` sends `/graphql`, `/previous/graphql` and `/config.json` to the branch's stack, so the local page is that stack's client (decision 0018; `docs/process/development.md`, rule 5; Issue-46). `npm run build --workspace @heat/client` is the production build, into `packages/client/dist/client/browser`, under Angular's default budgets but one: the initial bundle warns at 750 kB rather than 500 kB, raised for the GraphQL client (Issue-156), while the error budget stays Angular's 1 MB; "Build and test" runs it on every pull request, and its output is what a stack's bucket serves (Issue-39). `npm test` runs the client's tests once (`ng test --watch=false`) beside every other package's. The art the client draws is written into the git-ignored `packages/client/generated/art` before every serve, build and test (`packages/client/scripts/copy-art.mjs`) and served at `/art`, because Angular takes assets only from inside its workspace root and the art has one home, at the repository root with its provenance (Issue-81). A sprite set, under `art/heroes`, `art/monsters`, `art/props` and `art/weapons`, and a font's glyphs under `art/fonts`, cut from its atlas (`docs/process/assets.md`, rule 37), is packed there into one sheet, an image named for its pixels and the atlas that names it, `sheet.json`, which is published to be read again within a minute, and its frames and provenance are not published (`pack-art.mjs`; `docs/process/assets.md`, rule 4; Issue-205); `art/effects` and `art/ground` are copied as they are, and a facility's pictures under names that carry a hash of the file, with `pictures.json` beside them, which gives each picture's name and the row it stands on and is published with the same short lifetime, so the row a scene reads is always the row of the picture it draws. An icon is copied the same way, under a name that carries its file's hash, with `art/icons/pictures.json` naming each, which the page reads before it starts and the battle scene before a run (`src/app/icon-names.ts`), so an icon made again reaches a browser that kept the old one; the favicon alone keeps its name, at the page's root, where it is published to be read again within a minute (the review of PR-348). A frame under `art/frames` is trimmed to the box its pixels fill and copied under a name that carries the trimmed picture's hash, and its name and slice go into `packages/client/generated/frames.css`, a stylesheet the page is built with (`docs/process/assets.md`, rule 41; Issue-385). A hero's portrait is cut from its set's still facing south and published the same way as an icon, with `art/portraits/pictures.json` naming each by its set, which the page reads with the icons' index (`src/app/icon-names.ts`; `docs/process/assets.md`, rule 42). The favicon is one of that art, `art/icons/favicon.png`, so the client has no `public` folder; the build also puts it at the site root as `/favicon.png`, which `scripts/publish-client.sh` publishes with the page's short cache rather than the year-long one of everything else, because browsers ask for a favicon at a fixed address (Issue-89).

### Lint

16. **Lint is the floor.** `npm run lint` at the root runs ESLint over every workspace from one flat config, `eslint.config.mjs`, and "Build and test" runs it beside the typecheck, so a finding fails the pull request. A change is not ready for review until it lints clean, and a convention a lint rule can express is expressed as one, in the config, not as prose here; model-driven review, the review skill on a pull request (`docs/runbooks/review-change.md`) and the checkup skill at a pause (`docs/runbooks/checkup.md`), starts where lint stops (decision 0033). The rule sets are the published ones, at their strictest tier, an `all` tier taken whole; which they are, the order imports are sorted in, and the rules named off with their reasons are `docs/standards/typescript-dependencies.md`, "Rule 16", and the config. A rule is turned off, or its option changed, only with a one-line reason in the config, and the reason is about the rule, never about the code. A rule the code cannot meet yet is held back for those files only, by file pattern at the end of the config, naming the issue that removes the hold-back, and is listed under "Held back" in the standards document whose convention it expresses.

### Libraries

17. **A known library over our own.** For a common problem, a popular, well-known, current library is preferred over a solution of our own, and is adopted whole where it fits, as Angular, Apollo, Pothos, Powertools and PixiJS are: exact-pinned (rule 2), tracked by Dependabot (rule 1), and named here so that each idiom has one spelling. The weighting is the owner's: the application is built as an enterprise system would be, and a common problem takes the library used there, for what it shows and teaches, not only when the code outgrows it. Writing our own is the exception, taken when no current library does the job or when what the code needs is smaller than the library's cost, and the code says so in a comment. The validation library is zod, spelled `import * as z from "zod/mini"` in every package (decision 0039). The data layer is ElectroDB, behind the repository (decision 0041; `docs/standards/graphql.md`, rule 17). The browser test is Playwright (decision 0045). A component spec is Angular Testing Library (decision 0044; `docs/standards/angular.md`, rule 15). A span of the hub's own is made through the OpenTelemetry API, and a root field's by Pothos's tracing plugin with its OpenTelemetry wrapper (decision 0055). The utility library is es-toolkit (decision 0036), a dependency of the engine, the hub and the client: where it has a named function for what the code does, `range`, `clamp`, `sortBy`, `uniq`, `sum`, `sumBy`, `upperFirst`, `groupBy`, `keyBy`, `mapValues`, that function is used, in source and tests alike; the standard library is used where it reads as plainly on its own, `flatMap`, `find`, a spread, `Object.fromEntries` over pairs, a numeric comparator on numbers. Not replaced by it: `must` (rule 6), which returns the narrowed value where `invariant` only asserts; a `Map` or `Set` that is a cache, a registry or a membership test; and a loop that re-reads between attempts, which `retry` does not express. The art build's libraries, and what was weighed against a library and kept, each with its reason, are `docs/standards/typescript-dependencies.md`, "Rule 17".

### Closed sets

18. **A list that enumerates a closed union is checked against it.** An exported list of a union's members, `UNIT_TYPES`, `MATERIALS`, `GATHERING_TRAITS`, `FACILITY_KINDS`, `MONSTER_TYPES`, `RESOURCE_TYPES`, `STAGE_ENDINGS`, `ADVENTURE_OUTCOMES`, `UNLOCK_IDS`, is the one declaration: the list is `as const` and the union is `(typeof LIST)[number]`, so a member added to one is added to the other. Where the union is declared elsewhere, `StageKind` from `Stage`, the list `satisfies` it and a typed assignment beside it fails on a member the list lacks. A list annotated `readonly T[]` is not checked: a member added to the union alone compiles and is dropped from whatever the list feeds, the API's enums among them (graphql.md, rule 4). A closed set spelled in more than one place inside a package has one exported list, and every other place reads it, an unexported inline list included: `HERO_STATUSES` in the hub's `db/statuses.ts` feeds the entity, the union and the API's enum (the reviews of PR-192, Issue-155, and PR-212, Issue-200).

### Shared test helpers

19. **A helper shared by a package's test files is written once**, in one module under the package's `test/` that every test file imports, never copied into each, so that it changes in one place; `packages/hub/test/refusal.ts` holds `refusal` and `BAD_USER_INPUT`. The client's module is `src/app/testing/`, beside the code the specs import, which its application build excludes. This covers a block of set-up repeated across test files, named or not (the reviews of PR-192 and PR-214).

### Types over a library's

20. **A type that corrects a library's says the value's true shape, and any cast the library's signature needs stands at the call.** A type bent so that a value passes reads as true everywhere it is used; the cast at the call says once where the library's signature is wrong (the review of PR-214).

### Security fixes no update reaches

21. **An `overrides` entry is the last resort for a security fix no dependency update reaches.** It is scoped under the package that holds the vulnerable range, pinned exactly (rule 2), and listed under "Held back" (rule 1) with what releases it and an open issue that tracks the release; it leaves `package.json` and that list in the same pull request. What the lock file needs for an override to take effect is `docs/standards/typescript-dependencies.md`, "Rule 21" (Issue-316).
22. **A Dependabot alert is dismissed only with a "Held back" entry that gives the reason and what releases it, and an open issue that tracks the release.** Rule 1's ignore in `.github/dependabot.yml` is for a major of a direct dependency, and does not apply (the review of PR-236).

### What a build writes for the page

23. **What a build writes for the page is checked on both sides by one list.** A name the page asks a build's output for, such as a clip a scene reads from a sprite set's sheet, or a set's kind, is one exported list that the build checks its output against and the page reads. Neither side spells it on its own. The ground sets' is `packages/client/src/app/ground-sets.ts`, `GROUNDS` and the files the page asks each for, which the art build refuses a set without (the review of PR-361). The sprite sets' is `packages/client/src/app/sprite-sets.ts`: `SET_CLIPS`, the clips of each kind of set, and `PACKED_AREAS`, the kind each area under `art/` holds. The art build imports it as it is, Node stripping its types, so the file keeps to what stripping leaves working, and refuses a set without one of the clips; the page's `loadSpriteSet` takes a clip's name and a set's path only as the list types them, so a scene that asks for a clip the build does not check does not compile. Rule 18 is the same rule inside a package; this one reaches from a build script to the TypeScript it feeds (the review of PR-334, Issue-205).

### What a test helper takes from the source

24. **A value a shared test helper must agree with in the source is exported from the source and imported by the helper, never copied into it.** A limit the page applies, such as the longest frame the battle view takes, `MAX_FRAME_MS` in `battle-view.ts`, which the specs' frame loop and `runToBlow` in `testing/fake-battle.ts` read, is one constant: a copy in the helper would go on driving the page in frames the browser no longer gives, with nothing failing. Rule 19 says where a helper lives; this says where its numbers come from (the review of PR-338, Issue-335).

### What a test says it covers

25. **A test that says it covers every member of a content list reads that list from the content.** A test named for everything a villager can be forced to do, or for every type Millbrook recruits, iterates over `UNIT_PROFILES.villager.actions` or the location's `recruits`, and does not spell the members again: a member added to the content later would go untested while the test's name stayed true. A test of some members, named for them, lists the ones it means. Rule 18 keeps a list and its union together; this keeps a test's loop and the content together (the review of PR-347, Issue-341).

26. **A test that says it covers every case of its own file iterates over one list of them.** Where a test is named for every party a file plays, or every case above it, the file keeps those cases in one list, each test takes its case from the list, and the test that covers them all iterates over it: a case added to one test and not to the list does not compile or is not played. A test of some cases, named for them, lists the ones it means. Rule 25 says this of a list in the content; this says it of a list the test file makes (the review of PR-349, Issue-291).

### What a comment says was measured

27. **A comment that states a result over seeds states one that a test asserts.** A comment beside a job or a unit type that says how a party fares, how often something happens or what comes home says no more than a test in the repository holds, in the test's terms, and changes in the commit that changes the test; what was measured once and is held by no test goes into the decision record or the pull request, with how it was measured. `docs/README.md`, rules 5 and 6, hold documents to what is true; this holds a comment to it (the review of PR-349, Issue-291).

### What a test says it covers, of the schema

28. **A test that says it covers every verb or field of a kind reads them off the built schema.** A test named for every mutation that takes a location, or every field behind a scope, finds them by walking the schema the hub builds, as `packages/hub/test/access.test.ts` does for who may read what, and compares its own cases with what it finds: a fourth mutation that takes a location then fails the test until it has a case. A list the test file writes and compares with itself passes whatever is added. Rules 25 and 26 say this of a content list and of a file's own cases; this says it of the API (the review of PR-359, Issue-351).

### What a script takes from the source

29. **A value a script under `scripts/` must agree with in a package's source is read from the source, never copied into the script.** A colour a scene is made with, a list the page reads or a limit the engine applies is imported by the script from the file that declares it, which keeps to what Node's type stripping leaves working where the script runs it as it is, as `packages/client/src/app/ground-sets.ts` and `sprite-sets.ts` do; where it cannot be imported, the change that moves the value searches `scripts/` for it. `scripts/icon-set.mjs` reads the colour its icons are judged against from `GROUNDS`, the page's list of ground sets. Rule 24 says this of a test helper and `docs/README.md`, rule 5, of a document; this says it of a script (the review of PR-361, Issue-352).

### What a package mirrors from another

30. **A union a package mirrors from another is imported from the package that owns it, never spelled again.** Its type is named, `UnitKind` and not its members, or a type derived from it, so that a member added there reaches every place that reads it: rule 18 holds a list and its union together inside one package, and nothing holds two spellings in two packages together. The client's `FieldUnit` takes its kind from the engine's `UnitKind` (the review of PR-369, Issue-353).

### What a test file takes from the helpers

31. **A content id that a package's shared test helpers name as a constant is read from the helper by every test file, and not spelled again.** The engine's `test/adventure/helpers.ts` names each job and Highcrag, `QUARRY_FACE`, `CARAVAN_BACK`, `HIGHCRAG`; a test that spells an id instead keeps the old one when the job is renamed, and a table keyed by every job takes the constants as its keys. Rule 24 says where a helper's values come from; this, where a test file's do (the review of PR-373).
32. **A block of set-up that one test file repeats is a function of that file.** Rule 19 shares a helper across files; within one file, two tests that build the same stub, proxy or fixture call one function with what differs as its arguments, as `staleFacility(kind, level)` in the hub's `test/start.test.ts` does for a camp read stale once, so a fix to the stub is made once (the review of PR-374).

### What a test starts

33. **An image a test starts is named by an exact version and its digest, `name:version@sha256:…`, never by `latest` or a bare tag.** "Build and test" pulls and runs it, so a moved tag runs code nobody reviewed (`docs/process/best-practices.md`, rule 14). The reference is the `FROM` line of a `*.Dockerfile` beside the set-up, as `packages/hub/test/setup/dynamodb.Dockerfile` is, because Dependabot's `docker` ecosystem moves a version and digest there together and reads no string in TypeScript; the digest is the registry's, read when the version is taken. `imageFrom` (`packages/hub/test/setup/image.ts`) reads it and refuses a reference without a digest, and `packages/hub/test/images.test.ts` refuses a `GenericContainer(` call under `packages/` that does not use `imageFrom`, and a `*.Dockerfile` Dependabot does not watch (Issue-396).

## Held back

The majors not taken and the security fixes no dependency update reaches, each with the reason and what releases it, are listed under "Held back" in `docs/standards/typescript-dependencies.md` (rules 1, 21 and 22). A lint rule not yet met is listed in the standards document whose convention it expresses (rule 16): none, in this document or in `docs/standards/graphql.md`, since Issue-155.

## Why

Latest with LTS preferred is the owner's standing policy for every tool and library: a project that exists to show current practice should run on current versions, and the cost of staying current in small steps is far below the cost of a large jump later. Exact pins and the lock file make the laptop and CI identical, which decision 0009 depends on. The install-script approval is npm's own control since 11.19; recording approvals in the repository turns a per-machine prompt into a reviewed decision. The manifest exists because the bundler and Terraform would otherwise each hold a copy of the same routes and drift. Committing the printed schema is how a code-first project keeps schema-first's one real advantage, a reviewable contract.

Lint is the first layer of the review programme (Issues 144 to 147): the one layer that is deterministic and free, so that the model-driven layers spend nothing on what a linter knows. The strictest published tier was the owner's call, for a codebase meant to show current practice, and its cost was measured before it was taken; most of that cost was non-null assertions in tests, which is why rule 6 says "not used". The client's and the schema's rule sets are the `all` tiers because the owner weights accepted practice over the code as it is (Issue-145), and a rule named off is named for a convention this project holds against the rule, not for the code's convenience.

Angular releases its packages as one set and names the TypeScript versions it accepts, so its packages are pinned to one version and moved as one, and the repository's one TypeScript pin follows Angular's window (Issue-45).

Rule 17's utility library (the review of PR-153, Issue-149; Issue-154) is there because an idiom written by hand, each one correct, is a second read to see what it means. The project has two readers, a person and a coding agent, and a named function serves both: lodash's vocabulary, which es-toolkit keeps, is read without learning, and a named call is harder to get wrong than three nested `Math` calls. Under rules 1 and 2 and es-toolkit's per-function modules the dependency costs little, and the one real cost, two spellings for one idiom, is what the rubric in the rule removes. What was weighed, lodash, remeda, tiny-invariant and the idioms as they were, is decision 0036.

Rule 8's tests of the hooks and the scripts run under Node's own runner because what they test lives in no package and needs none (Issue-328, the review of PR-333).
