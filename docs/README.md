## How documents are written

1. **Write for an agent first.** Be explicit and concrete, and assume no background. A person can read a document written that way. An agent cannot reliably work from one written for a person who already knows the project.
2. **Rules first, reasons after.** A document opens with short rules that can be checked. The reasons follow in their own section, which for a standard is in its detail file (rule 20).
3. **One topic per file,** under about 200 lines. Longer files are followed less reliably. What an `AGENTS.md` loads, the root's in every session and an area's, with its standards, in every session that works in that area, is in context at every call, so it is also held to a size in bytes, the loader and its imports together: `scripts/check-loaded-documents.mjs` names each loader's size, and "Build and test" fails a pull request that passes it. Such a pull request makes room, by moving out of a loaded document what a session does not need at its start (for a standard, by the tiers of rule 20), or raises the number in the script and says why in its description (decision 0060).
4. **Write a document when there is a decision to record,** not before. Do not write down what an agent would do anyway, or what it can read from the code.
5. **Keep documents true.** A change in behavior and the document that describes it go in the same pull request. A rename of something a document quotes, a code, a type, a field, is followed by a search of every document and diagram for the old name, the root `README.md`, the Mermaid diagrams and the standards included, not only the files the change touches, because an old name survives where nobody was looking (the review of PR-192, Issue-155). A loader (`AGENTS.md`, a standard's preamble) names what exists and does not count it or list it where another document is the list; a count or a list copied there is the next stale phrase (the review of PR-243, Issue-242).
6. **Say what is real.** Nothing is described as built, tested or enforced unless it is.
7. **Mark the status of design items.** Each item in a design or architecture document is labeled Decided, Working assumption or Open. The labels are defined at the top of each of those documents.
8. **Design and process documents say what is true now.** When a decision changes, edit the document and add a decision record. The record keeps what was rejected and the history; in the document, how a rule got there is a reference to the record and not a sentence (rule 17). At the pauses that rule 9 of `process/best-practices.md` names, a checkpoint merged or a step of the build order begun, the documents are swept for history that has crept in, and it is moved to a record or cut.
9. **AWS account ids do not appear in committed files.** Documents and code name accounts by name (`heat-dev`, `heat-platform`) and never by id. The rule is about the organization's accounts: an ARN AWS publishes for a resource of its own, as it does for a managed Lambda layer, carries AWS's account and is written as published (decision 0055). Credentials never appear anywhere. This repository is written to be safe to publish; the organization-level `dcg-platform` repository takes the opposite rule, for reasons recorded there as its decision 0001. The ids reach the pipeline as repository secrets, `HEAT_<ENVIRONMENT>_ACCOUNT_ID`, never as variables, because GitHub masks a secret in every log line and the logs are public with the repository (decision 0035).
10. **A procedure lives in one document.** Another document that needs it names it and points at it; it does not restate the steps. A process rule says that the procedure is followed and where it is; a decision record says why it has the shape it has; a skill says how Claude Code's arguments map onto it (decision 0033).
11. **Rule numbers are stable.** A new rule is appended to its document, never inserted; a retired rule keeps its number and says it is retired, with the record that retired it. A finding, a review thread, an issue and another document cite a rule by its number, and the checkup's deduplication keys on it (`runbooks/checkup.md`, rule 7), so a renumbering would break every citation (the review of PR-163, Issue-147).
12. **An image under `docs/` says what it shows and when.** Its alt text, or a note beside the file, names the stack or commit it was captured from, or the committed art it was composed from, as every set under `art/` carries its provenance (the review of PR-179, Issue-177).
13. **A Mermaid diagram is written for GitHub's renderer.** A semicolon anywhere in a message or a note ends the statement, and GitHub shows "Parse error" in place of the diagram: use a comma. An angle bracket in a label is read as HTML: leave it out. The diagram is checked on the branch's page before the pull request opens (Issue-180).
14. **What a session learns goes into a document, not into a memory.** A fact, a procedure or a correction that another person's session would need is written into the document whose topic it is, in the pull request of the work that found it (`process/best-practices.md`, rule 12). An agent's local memory holds only what is personal or true of one machine, and a private note only what cannot be committed (rule 9). Claude Code keeps its memory per machine, so what is written there reaches nobody else (Issue-318).
15. **What a decided but unbuilt change will replace says so, and is found by searching.** An item in a design or architecture document that a decision not yet built will replace goes on saying what is true now, and says in the item itself which decision replaces it and which issue builds that; the decision's own items are marked "Decided, not built" with that issue (rules 6 and 7). When a decision is recorded, every document and every decision record is searched for the terms of what it replaces, as rule 5 asks for a rename, and not recalled: each item found takes its pointer, and each record whose Decision states what is replaced is named on the new record's Amends line, with its Status line and its index row amended (`decisions/README.md`, rules 5 to 7). A search finds what memory misses (the review of PR-342, Issue-336). The search covers the code that reads what is replaced, not only the documents: each caller found is named where the decision or the rule describes the change (the review of PR-387, Issue-383).
16. **A member added to a closed set is followed by a search of every document for the set's other members,** so that each list that states the whole set is found and takes the new one. Rule 5's search starts from an old name, and an addition has none (the review of PR-345, Issue-339).
17. **A rule carries its reason as a clause and its origin as a reference; the account is kept apart.** A rule says what to do, why in a clause, and where it came from as a number in brackets, an issue's, a pull request's or a decision's. The dated account, what happened, in which session and what was tried first, goes to the decision record where there is one, and otherwise to the `history.md` beside the document, under the document's name and by the rule's number. An account is added there in the pull request that adds or changes the rule or the item it explains, and is not rewritten afterwards, so that it stays a record of what happened. Nothing loads a `history.md`; it is read when a rule's reason is in doubt or the rule is about to change (Issue-363, Issue-364; decision 0060).
18. **When an issue builds what a document called decided and not built, every document is searched for the issue's number,** and each sentence found that still calls the work unbuilt is brought up to date in the same pull request: the pointer rule 15 asks for is the search term for its own update, and memory misses what a search finds (the review of PR-369, Issue-353).
19. **A comment beside a size limit in `scripts/check-loaded-documents.mjs` gives the reason the number was set and the issue that set it, not the room left under it.** The script prints the room on every run, and a figure in the comment is wrong after the next change to a loaded document (rule 5; the review of PR-376, Issue-375).
20. **A document that holds a standard's detail, and that nothing loads, says before its first section which standard it serves and when each of its sections is read.** It has no rules of its own: its sections are named for that standard's rules, a rule it cites by bare number is that standard's, and rule 2's shape, rules first and reasons after, does not apply to it. The loader that points at it names it and what it holds, and leaves the occasions to the document (rule 5; the review of PR-376, Issue-375). Each standard has one, `<standard>-detail.md`, which holds, besides the detail of a loaded rule, the whole of a rule the standard writes as one line, the standard's "Held back" and its "Why", by the tiers of decision 0060, as amended by Issue-428 (Issue-428).

## Not documents

`docs/private/` is ignored by git and holds working notes: account ids, inventories, runbooks in progress, and the hand-over notes from the `dcg-platform` repository. Nothing there is reviewed or kept true. Where a committed document and a private note disagree, the committed document wins, and the AWS APIs win over both. One file there, `heat-working-context.md`, is read at the start of every session (`AGENTS.md`, "Starting on an issue"): it carries what cannot be committed, the account ids, how the agent reaches AWS and the owner's own context. It carries no rules, no lessons and no state of the work: the rules and the lessons are in these documents (rule 14), and the state is the issues, the pull requests and the log. `process/sessions.md`, rule 15, lists the private files a machine needs.

## Where documents live

Content that a person or another tool might need lives under `docs/`, in plain Markdown. Nothing of that kind lives under `.claude/`, which holds only what is specific to Claude Code: `settings.json`, the hooks it wires under `.claude/hooks/`, and skills that point at files in `docs/runbooks/`. A hook is committed there, and wired through `${CLAUDE_PROJECT_DIR}`, when it is this project's behavior; a path under one person's home directory is never written into either. A skill holds its frontmatter and how Claude Code's arguments map onto the runbook it points at, and nothing the runbook already says (rule 10).

## How agents load these documents

- `AGENTS.md` is the entry point. It imports the documents that every session needs, using `@path` references.
- Each area of the repository has its own `AGENTS.md` that imports the standards for that area (the index above names each). Those load only when an agent works on a file in that area.
- Beside every `AGENTS.md` there is a `CLAUDE.md` containing only `@AGENTS.md`.

The last rule has no exceptions. Claude Code reads `AGENTS.md` by itself only when no `CLAUDE.md` exists at or above the working directory, so one `CLAUDE.md` without a partner in another directory silently switches that directory's `AGENTS.md` off. Pairing them everywhere avoids that, and it also covers sessions that look for `CLAUDE.md` by name.

Two more things were found by testing with Claude Code 2.1.295:

- An import inside a path-scoped rule under `.claude/rules/` loads at session start, which defeats the scoping. That is why area standards are loaded through per-area `AGENTS.md` files and not through rules.
- `@path` expansion is a Claude Code feature. Other tools follow the nested `AGENTS.md` convention but may treat an import as a plain file reference, so each import is written as an instruction: "Read and follow ...".
