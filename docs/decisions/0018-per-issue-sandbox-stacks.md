# 0018: Per-issue sandbox stacks in a dedicated account, one hostname per stack, the local emulator retired

- **Status:** Decided
- **Date:** 2026-10-16
- **Amends:** 0010 and 0015, the API's hostname: one hostname per environment, the APIs on paths behind CloudFront, for dev and prod too. 0016, the one-root-per-environment rule: the ephemeral stacks share one root.
- **Supersedes:** 0009's table of stand-ins and its local run of the system. 0009's rule that the hub's data-layer tests run against Testcontainers stays.

## Decision

**The account.** A fourth AWS account, `heat-sandbox`, created by the organization layer in the `dcg-platform` repository through Control Tower's account factory under the NonProd organizational unit, with the organization's roles placed, as `heat-dev` was. The `bootstrap` stack gets a root for it, with the plan and apply roles of decision 0017 and a budget with its action. Nothing in it is permanent except the sandbox base below.

**A stack per issue.** Branches are named `<type>/<issue>-<short-description>`, so the issue number is in the branch name. A push to such a branch creates or updates the stack `heat-sb<issue>` in `heat-sandbox`, with the state key `environment/sandbox/<issue>/terraform.tfstate` in the platform bucket. Deleting the branch destroys the stack, through the push trigger's `delete` event, and a weekly scheduled run destroys any stack whose branch no longer exists, in case a deletion event was missed. The workflow refuses to create a stack beyond a cap on concurrent stacks, so a burst of branches cannot multiply the account's resources; the number is set when the workflow is written (Issue-37) and is a committed value.

**One root for the ephemeral stacks.** `terraform/environment/sandbox` is one root directory used by every sandbox stack. The issue number arrives as a variable and the state key as `-backend-config`, both supplied by the workflow from the branch name. This amends decision 0016, whose rule is one root directory per environment, for this case only: the two faults 0016 guards against do not arise here. A workflow run has no memory of a backend, so there is no directory that remembers the wrong one and no `-reconfigure` to forget. And the key and the stack name derive from one value, the issue number, so the pair cannot mismatch. Permanent environments, `sandbox-base`, `dev` and `prod`, stay a directory each, with the key written in.

**The sandbox base.** One permanent root, `terraform/environment/sandbox-base`, applied by the pipeline on merge to `main`. It holds what every stack shares and what is slow or manual to create: the hosted zone `heat-sb.dcg-games.com`, delegated to `heat-sandbox` by the organization layer; one wildcard certificate for `*.heat-sb.dcg-games.com` in us-east-1, validated through that zone; one Cognito user pool with its domain, Google registered as its identity provider once, the test users, and a password-flow app client that the end-to-end tests and the agent sign in with. Each stack adds its own app client to that pool, with two callback URLs: the stack's hostname and `http://localhost:4200`, the Angular dev server (below). Registering app clients costs nothing, and a pool's first 10,000 monthly active users are free without expiry, so the shared pool costs nothing.

**A site per stack, one hostname.** `<issue>.heat-sb.dcg-games.com` is a CloudFront distribution per stack, on the wildcard certificate, with one record in the base zone. Its default behavior serves the Angular client from the stack's bucket through origin access control. A second behavior sends `/graphql` to the stack's HTTP API at its default endpoint, with caching disabled and the managed origin request policy `AllViewerExceptHostHeader`, which forwards every viewer header, cookie and query string except `Host`. When the live channel is built (build order step 4), a third behavior sends its path to the stack's WebSocket API, with the `Sec-WebSocket-*` headers forwarded. The browser therefore talks to one origin for the page, the API and the socket: no CORS, and no API Gateway custom domain. `dev` and `prod` take the same shape at `heat-dev.dcg-games.com` and `heat.dcg-games.com`, which amends 0010 and 0015, where each API had the environment's hostname directly.

A distribution is pay-as-you-go. It has no fixed monthly charge, and the account's always-free allowance covers 1 TB of transfer, ten million requests and two million CloudFront Functions invocations a month, with certificates free. CloudFront's flat-rate Free plan is not used: it is limited to three per account, one distribution each, and an account using the AWS Free Tier is not eligible.

**The local emulator is retired.** serverless-offline, the Serverless Framework and its licence, `local/serverless.ts`, `compose.yml` and the table script leave the repository in Issue-38, when the first stack exists to replace them. Running the system means pushing to the branch: the stack is the system, with the real gateway, the real authorizer, the real IAM path and the real logs. What stays local is the fast loop: the engine's unit tests and the hub's data-layer tests against DynamoDB Local started by Testcontainers, on a laptop and on the CI runner alike.

Display work on the Angular client needs a loop of seconds, not the minutes a push and apply take. For that the Angular dev server runs on the laptop, from the issue's worktree, with a proxy configuration sending `/graphql` to the stack's hostname, and signs in through the stack's app client with the `http://localhost:4200` callback. The browser then runs the local client against the real stack. That is why each stack's app client carries the localhost callback, and why nothing in the client's code branches on where it runs.

**What the emulator could never prove.** Found while pinning it on 2026-10-16, and recorded here so it is not lost: serverless-offline never verifies a JWT signature. With its `ignoreJWTSignature` option on, it checks that a token is present, unexpired, and has the configured issuer and audience; with the option off, the authorizer is skipped and every route is open. An emulated gateway therefore cannot exercise the authorizer, which is the piece of the request path most worth exercising. A stack can.

**Process.** The owner reviews a pull request at its stack URL, so the branch no longer needs to be checked out in the owner's IDE. Each issue is worked in its own git worktree and session, created from `origin/main` and removed after the merge, while the checkout the IDE has open stays on `main`; when local iteration is wanted, the owner opens the worktree folder. More than one piece of work may therefore be in flight. Pull requests and issues are referred to as PR-n and Issue-n in conversation and documents. The rules are in `docs/process/code-changes.md` and `docs/process/collaboration.md`.

## Considered and not chosen

**One shared sandbox**, the shape first proposed on 2026-10-16. It serializes work: the sandbox reflects whichever branch pushed last, and the next branch's apply reconciles away what the previous one created. Two issues in flight would fight over it, and the rule that only one piece of work is in flight (code-changes rule 27, before this record) existed for exactly that reason.

**A user pool per stack.** Google's redirect URI is `https://<user pool domain>/oauth2/idpresponse`, registered in the Google Auth Platform console per pool domain by hand, and changes "can take from five minutes to a few hours to take effect" (Cognito developer guide, "Add Google as a social identity provider", checked 2026-10-16). Every stack would need a console step by the owner and a wait. One pool with one registration, and an app client per stack, needs neither.

**Sandbox stacks in `heat-dev`.** The account exists and is already the non-production one. Against it: the churn of stacks created and destroyed daily lands beside the pipeline's `dev` environment, a runaway stack would trip `dev`'s budget action and freeze `dev` with it, and a mistake in the sweep could reach `dev`'s resources. A separate account is one directory and one account-factory request, and it is the practice the organization's structure is built for.

**A hostname per API**, `api.<issue>.heat-sb.dcg-games.com` beside the site, the 0010 shape. Two records and two certificates per stack, API Gateway custom domains to manage, and CORS between the site and the API. One hostname removes all three.

**Keeping the emulator and making it faithful**, by replacing serverless-offline with a manifest-driven local gateway that verifies Cognito tokens, proposed on 2026-10-16 before the pivot. It would be HEAT's own emulator to keep faithful to API Gateway, forever one behavior behind, and the thing it emulates costs nothing to run for real.

**A certificate per stack.** ACM certificates are free, but DNS validation takes minutes per stack on every creation. One wildcard in the base is validated once.

**CloudFront's flat-rate Free plan** for the per-stack distributions: three per account at most, so it cannot cover per-issue stacks, and the account's eligibility turns on Free Tier status. Pay-as-you-go costs nothing at rest and is the same for every distribution.

## Facts checked

All read on 2026-10-16.

- **CloudFront and WebSocket** (CloudFront developer guide, "Use WebSockets with CloudFront distributions"): "WebSocket functionality is automatically enabled to work with any distribution"; the cache behavior must forward `Sec-WebSocket-Key` and `Sec-WebSocket-Version` in its origin request policy, and AWS recommends also forwarding `Sec-WebSocket-Protocol`, `Sec-WebSocket-Accept` and `Sec-WebSocket-Extensions`; "CloudFront only supports WebSocket connections over the HTTP/1.1 protocol".
- **API Gateway as a CloudFront origin** (CloudFront developer guide, "Use managed origin request policies"): `AllViewerExceptHostHeader` "is intended for use with Amazon API Gateway, AWS Lambda function URL, and Lambda Web Function origins. These origins expect the `Host` header to contain the origin domain name, not the domain name of the CloudFront distribution." The same guide's table of request headers: `Upgrade` is removed "unless you've established a WebSocket connection", and `Authorization` is forwarded on `POST`.
- **Stage paths.** An HTTP API's `$default` stage "is served from the base of your API's URL" (API Gateway developer guide, "Stages for HTTP APIs"), so the `/graphql` behavior needs no origin path. A WebSocket API is invoked at `wss://<api-id>.execute-api.<region>.amazonaws.com/<stage>` (the same guide, "Invoke WebSocket APIs"), so its behavior carries the stage as the origin path. A custom domain mapped to a WebSocket API "can't" also map to an HTTP API, which is one more reason the hostname is CloudFront's and not the gateway's.
- **Not yet checked, deferred to build order step 4:** whether the WebSocket API accepts a connection path beyond its stage, which decides whether the socket's behavior needs a CloudFront Function to rewrite the path to the stage root; and whether CloudFront ends an idle WebSocket connection before the gateway's ten-minute idle timeout, which the client's ping interval from 0010 must stay inside. The CloudFront documentation read today states no idle timeout for an established WebSocket connection.
- **CloudFront pricing** (pricing page, pay-as-you-go, and the developer guide, "CloudFront flat-rate pricing plans"): pay-as-you-go has no fixed charge per distribution and lists under the always-free tier "1 TB of data transfer out to the internet per month", "10,000,000 HTTP or HTTPS Requests per month", "2,000,000 CloudFront Function invocations per month" and free SSL certificates; flat-rate plans are quoted at "Free plans per AWS account: 3", each plan "covers one CloudFront distribution with up to one apex (root) domain", and an account is not eligible if "your account is using AWS Free Tier".
- **Cognito pricing** (pricing page): the Lite and Essentials tiers include 10,000 monthly active users free per account, and "the free tier does not automatically expire at the end of your 12-month AWS Free Tier term"; "there is no additional charge for the number of app clients you have registered in your account".
- **Google registration** (Cognito developer guide, "Add Google as a social identity provider", which says it was verified against the Google console on 2026-10-02): the authorized redirect URI is the `/oauth2/idpresponse` endpoint of the user pool domain; the authorized domains are the registrable domains of the pool, so one Google client serves the three pools (sandbox, dev, prod) with one redirect URI each, entered by the owner.
- **The emulator finding**: observed in `local/serverless.ts` and serverless-offline's documentation of `ignoreJWTSignature` during Issue-33, 2026-10-16.

## What is owed, and by whom

- **`dcg-platform`, in its own sessions:** the `heat-sandbox` account through the account factory under NonProd with the organization's roles placed; delegation of `heat-sb.dcg-games.com` to `heat-sandbox`, `heat-dev.dcg-games.com` to `heat-dev` and `heat.dcg-games.com` to `heat-prod`. No change to `AuditRole` or `PlatformAdminRole`.
- **The owner, once:** the Google Auth Platform project and its OAuth client with the three pools' redirect URIs; the client id and secret into the GitHub environments; the GitHub environments `dev` (branch `main`) and `prod` (tags `v*`). The per-stack environments `sandbox-<issue>` need no step: the workflow creates each by referencing it (decision 0019).
- **Deferred to later checkpoints, named above:** the cap on concurrent stacks (Issue-37); zip determinism and the cold start measurement (Issue-38); the WebSocket behavior's path and idle behavior (build order step 4).
