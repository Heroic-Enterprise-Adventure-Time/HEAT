# 0055: Tracing through OpenTelemetry: AWS's Lambda layer, the AWS SDK beside the bundle, and a span for each root field

- **Status:** Decided
- **Date:** 2026-11-17
- **Settles:** Issue-326: how the hub is traced now that the X-Ray SDK, in maintenance since 2026-02-25, loses support on 2027-02-25. It amends decision 0040, whose third middleware is gone, and reopens the overview's "there are no layers" (`docs/process/best-practices.md`, rule 11).

## Decision

**The hub is traced by the AWS Lambda Layer for OpenTelemetry, for traces only.** It is the path AWS recommends in place of the X-Ray SDK, and the owner's call was to give the recommended path a solid try on the issue's stack before anything else was weighed. Every function carries the layer, by the ARN AWS publishes for us-east-1 with its version in it, its wrapper as `AWS_LAMBDA_EXEC_WRAPPER`, `OTEL_AWS_APPLICATION_SIGNALS_ENABLED = false` and `OTEL_SERVICE_NAME` (`terraform/modules/environment/functions.tf`). The layer makes the function's span and one for each DynamoDB and S3 call, named for the operation, and sends them to X-Ray through Lambda's own agent. It needed no account-level setting and no managed policy. Active tracing stays, and the function's role is narrower than it was: of its two X-Ray actions, `xray:PutTraceSegments` stays and `xray:PutTelemetryRecords`, which it held for the X-Ray SDK's daemon, is gone. Without it, on the issue's stack, a deploy's 66 traces arrived whole and the function's log showed no denial (the owner's call, 2026-11-17). What Lambda's own agent made of the refusal is on AWS's side and was not seen.

**Layers are acceptable, here and for other purposes where they fit** (the owner, 2026-11-17). What the overview said against them was said of shared code, which stays compiled into the bundle (decision 0012). A layer's version never changes, so the number in the ARN is the pin; nothing tracks it, and it moves by a change to that line.

**The AWS SDK is shipped beside the bundle, in the function's own `node_modules`, and no longer inside the file.** The layer instruments a library by intercepting its load, and a library inside the one bundled file is never loaded: with the SDK bundled, the trace showed each call only as an anonymous HTTP `POST`. `scripts/bundle.mjs` therefore leaves the SDK's two scopes, `@aws-sdk` and `@smithy`, out of the file and copies into `dist/<name>/node_modules`, from what the lock file installed, the files the bundle's imports load at run time, as `@vercel/nft` traces them: 110 files of 31 packages, 1.8 MB, where the packages whole were 1,586 files and 8 MB, half of it a build Node never loads here. The script refuses a bundled package that would have loaded an SDK copy of its own. It is the function's own copy at the lock file's versions, which is what AWS asks for: "we strongly recommend that you include the AWS SDK clients that you need in your deployment package".

**A span for each root field a request runs, through Pothos's tracing plugin.** `@pothos/plugin-tracing` with `@pothos/tracing-opentelemetry` wraps the fields of `Query` and `Mutation`, and `traceRootField` in `packages/hub/src/observability.ts` names each span for its field, `Query.me` or `Mutation.startAdventure`, where the function's own span says only `POST /graphql`. The field's name, which the wrapper records as `graphql.field.name`, and the deploy's version, `heat.version`, are X-Ray annotations, so a trace is found by `annotation[graphql.field.name] = "submitAdventure"`. The name is the schema's, a closed set, never the operation name a client sends.

**Nothing of a request is on a span.** The wrapper's arguments and source stay off, because they are the request's variables and its document, and so does an error: a refusal is thrown as a class and answered as data (`docs/standards/graphql.md`, rule 6), and an exception on the span would mark an expected answer as a failure. A raw trace of a settled adventure, read on the issue's stack, holds on its SDK spans the table's or the bucket's name, the operation, DynamoDB's counts and AWS's request ids, and no key, item, object key, id, token or claim. `packages/hub/test/tracing.test.ts` holds the root field's span to five attributes and no event.

**The layer records the access key id of the function's role session on every SDK span,** as `aws.auth.account.access_key`. It is an identifier and not a credential: the secret key and the session token are not recorded, and CloudTrail records the same id. Accepted as it is (the owner, 2026-11-17).

**An agent reads an environment's traces through that environment's plan role without asking first** (the owner's standing yes, 2026-11-17; `docs/process/best-practices.md`, rule 15). What is allowed: `xray:GetTraceSummaries` and `xray:BatchGetTraces` through `plan-heat-<environment>`, `prod`'s included. `AuditRole`, the agent's other read-only role, may list summaries and is denied a whole trace, so reading one meant asking each time; the owner weighed adding the action to `AuditRole`, an organization-wide role defined in `dcg-platform`, and gave the standing yes instead. What it leaves exposed: what a trace holds, which is the function's and the tables' names, the operations and their timings, AWS's request ids and the access key id above, and nothing of a player; the role is the project's own, read only, and already reads the same environment's logs. Why asking is not worth keeping: the answer was always yes, and Issue-328 reads traces on every pull request. What stands in its place, in the default mode and in auto alike: the session's own permission flow for the command, which this changes nothing in, since the yes replaces a question in conversation and no prompt of the tool's.

**The Powertools tracer leaves the hub.** `captureLambdaHandler`, the two client captures and `@aws-lambda-powertools/tracer` with the X-Ray SDK under it are gone. Powertools stays for the log and the metrics, and middy hosts its two remaining middlewares, `injectLambdaContext` and `logMetrics` (decision 0040).

**`@opentelemetry/api` is held at the layer's version, 1.9.1.** The API ignores a provider registered by an older minor, so a newer copy in the bundle would record nothing, silently, under a layer whose release carries 1.9.1. The SDK the tracing test registers is the 2.x line for the same reason, which npm marks deprecated in favour of a package that needs the API at 1.10. Both are listed under "Held back" in `docs/standards/typescript.md` and ignored in `.github/dependabot.yml`, and both move with the layer.

**The cold start is measured, not budgeted** (the owner, 2026-11-17): it is reported on every run, watched, and finding its main contributors is Issue-330. Each figure is one sample from the issue's stack:

| | Initialization | First request | Memory |
| --- | --- | --- | --- |
| `main`'s code, the Powertools tracer | 918.70 ms | 81.15 ms | 143 MB |

## Considered and not chosen

- **The runtime's own AWS SDK,** by leaving the SDK out of the package. The owner asked whether it is the recommended path. It is not: the Lambda guide says to rely on it only "when you can't include additional packages", and that it is "a specific minor version", "not the latest", which "depends on the runtime version and your AWS Region". What `npm test` proves, the timeouts of Issue-211 among them, would run on another SDK in Lambda.
- **The SDK left in the bundle, with a span of our own for each call,** a middleware on each client through the OpenTelemetry API. It keeps the one file and the lowest cold start of the three, and it writes by hand what a library records. Proposed first, and set aside when the recommended form was tried and worked.
- **The OpenTelemetry SDK bundled, with no layer:** the guide's manual setup, a simple span processor, the X-Ray UDP exporter and the X-Ray Lambda propagator. The exporter on npm is 0.0.2 of 2025-10-01, on SDK 1.x; its move to 2.x is in its repository and unpublished. The instrumentations would still not see a bundled SDK.
- **A walk of our own over the SDK's packages and their dependencies,** which `scripts/bundle.mjs` first had: whole packages, 34 of them, with their type declarations filtered out. It worked on the stack. The review of PR-331 named the library that does it, and tracing files in place of packages left fourteen files in every fifteen behind.
- **Staying on the Powertools tracer until Powertools has an OpenTelemetry one.** Its RFC of 2025-07-17 says "we have not committed to implementing it", with no date for TypeScript, and the SDK under the tracer ends on 2027-02-25.
- **An Apollo plugin of our own, or the client's operation name, for what a request did.** The first is machinery where the schema builder's own plugin exists (`docs/standards/typescript.md`, rule 17); the second is a free string from the caller.
- **The managed policy `CloudWatchLambdaApplicationSignalsExecutionRolePolicy`, and Application Signals.** The guide attaches the policy; traces alone needed neither. Nor `AWSXRayDaemonWriteAccess`, the policy the Lambda guide names for active tracing, which holds `xray:PutTelemetryRecords` and three sampling reads beside the one action the role keeps.
- **The layer's opt-in mode, `OTEL_AWS_LAMBDA_FAST_START`,** traces only, which its source says "greatly reduces cold start" and less so on Node 24. Not tried: it belongs with the work on the cold start, Issue-330.

## Facts checked

All read on 2026-11-17.

- **The X-Ray SDK's end** (X-Ray developer guide, "X-Ray SDK and daemon end of support timeline"): maintenance from 2026-02-25, support ends 2027-02-25; X-Ray keeps accepting traces.
- **What AWS recommends for Lambda** (the same guide, "Migrating from X-Ray instrumentation to OpenTelemetry instrumentation", "Lambda environment instrumentation changes"): the AWS Lambda Layer for OpenTelemetry, recommended, with `OTEL_AWS_APPLICATION_SIGNALS_ENABLED=false` for traces only; or a manual setup. An attribute becomes an X-Ray annotation when its key is in the span's `aws.xray.annotations`.
- **The layer** (the ADOT documentation, "AWS Distro for OpenTelemetry Lambda"): `arn:aws:lambda:us-east-1:615299751070:layer:AWSOpenTelemetryDistroJs:16`, the account being AWS's own publisher; Node.js 24.x on arm64 supported; traces "exported in OTLP format through the Lambda embedded agent"; AWS SDK and HTTP instrumentation on by default. Its source, `aws-observability/aws-otel-js-instrumentation`, `lambda-layer/packages/layer`: the wrapper registers an import hook and loads the auto-instrumentation, whose release v0.13.0 carries `@opentelemetry/api` 1.9.1, `@opentelemetry/sdk-trace-base` 2.8.0 and `@opentelemetry/instrumentation-aws-sdk` 0.74.0. That layer version 16 is that release is inferred from its being the latest, and is consistent with the traces, which say `telemetry.auto.version` 0.13.0-aws and `telemetry.sdk.version` 2.8.0.
- **The API's compatibility rule** (`@opentelemetry/api` 1.9.1 as installed, `build/src/internal/semver.js`, `isCompatible`): a copy accepts a global registered by the same major when its own minor is no later than the global's, and rejects it otherwise. The registry on that day: `@opentelemetry/api` 1.10.0 the latest; `@opentelemetry/sdk-trace-base` 2.12.0, deprecated, peer `>=1.3.0 <1.10.0`; `@opentelemetry/sdk-trace` 3.1.1, peer `>=1.10.0 <1.11.0`.
- **The SDK in the package** (Lambda developer guide, "Using the SDK for JavaScript v3 in your handler", "Runtime-included SDK versions" and "Code best practices for Node.js Lambda functions"): the sentences quoted above, and "package all of your dependencies with your deployment package".
- **How Node resolves the SDK from the package:** the SDK's packages name `./dist-cjs/index.js` as `main` or under the `node` condition of `exports`, ahead of `import`, so the function loads the CommonJS build and the type declarations are never read (their `package.json` files, as installed).
- **What the agent's roles may read:** `AuditRole` may call `xray:GetTraceSummaries` and is denied `xray:BatchGetTraces` and `lambda:GetLayerVersion`; a whole trace was read through the plan role, with the owner's yes.
