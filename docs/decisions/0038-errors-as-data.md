# 0038: Refusals as data in a result union per mutation, one input object per mutation, and the engine's sets as enums

- **Status:** Decided; amended 2026-11-02 by Issue-156: the client's mapping back is typed from the enums GraphQL Code Generator emits, not by its `enumValues`, which sets the runtime value of a generated TypeScript enum that Apollo does not translate on the wire
- **Date:** 2026-11-02
- **Settles:** Issue-155: how a mutation refuses, how it takes its arguments, and how ids, timestamps and the engine's closed sets appear in the API; agreed in shape on 2026-10-24 (Issue-145), when `docs/standards/graphql.md` stated the accepted practice as rules 4 to 6 and held the code back until this issue.

## Decision

**A mutation answers a result union, and a refusal is a member of it.** `<MutationName>Result` is a union of `<MutationName>Success`, which wraps what the mutation changed in one field named for it (`hero`, `camp`, `adventure`, `player`), and one object type per refusal, each implementing an `Error` interface with `message` and carrying the fields the client needs: `InsufficientResources.short`, `Requires.missing`, `AdventureOpen.adventureId`, `EngineUpdated.version`, `AdventureVerifiable.version`, `HallLevel.level`, and `heroId` on `HeroDead`, `HeroRetired`, `HeroNotHere` and `HeroAdventuring`. The refusal types are shared across the mutations that can give them, not one set per mutation. The hub's functions throw the classes in `packages/hub/src/refusals.ts`, and `@pothos/plugin-errors` (4.9.3) builds the union from the classes each field names and resolves a thrown one to its type; no default error class is registered, so anything else thrown stays in the response's `errors` array. `joinGame`, which nothing refuses, answers a union of its success alone, so a refusal can be added without breaking a client.

**What is a refusal and what is not.** A refusal names a game state the player can act on and that may have changed since the client read: the hall full, a hero dead, an adventure open, the camp changed under the request (`Conflict`, whose action is to try again). An id or a count the client should never have sent is the client's defect and stays `BAD_USER_INPUT` in `errors`: another player's hero or adventure, which is not said to exist, a job the location does not post, a party of the wrong size, a unit type the location does not recruit. This folds the former codes `NOT_FOUND`, `NO_SUCH_ADVENTURE`, `NOT_YOUR_HERO`, `NO_SUCH_JOB` and `PARTY_SIZE` into `BAD_USER_INPUT`. `UNAUTHENTICATED` and a failure nobody expected stay in `errors` too, as Apollo's guide has it.

**One input object per mutation**, `input: <MutationName>Input!` and no other argument; `joinGame` takes none.

**Every root field is nullable**, mutations and queries alike, so that one field's failure nulls that field and not the whole response. `version` and `heroesSeenAt`, non-null before, are nullable now; the client already handled `me` being null and handles these the same way.

**Scalars and enums.** Every identifier is `ID`, typed `string` on both sides of the hub's builder, a location's and a job's content ids included. Every timestamp is `DateTime` from `graphql-scalars` (2.0.1). Every set the engine's types close is an enum: `UnitType`, `Material`, `FacilityKind`, `AdventureOutcome`, `StageKind`, `StageEnding`, beside the hub's own `HeroStatus` and `AdventureStatus`. The enum values are `UPPER_CASE` on the wire and the engine's own kebab-case strings inside the hub, mapped by the enum definition (`HEROES_HALL` is `heroes-hall`), and the client maps them back at its API boundary, in `game.ts`, with es-toolkit's `constantCase` against the engine's exported lists, so that nothing past that file sees a wire value. The engine gained `FACILITY_KINDS`, `ADVENTURE_OUTCOMES`, `STAGE_KINDS` and `STAGE_ENDINGS` for it.

**The deploy that ships this change breaks the two-route bridge once.** Decision 0030 keeps the previous deploy live at `/previous/graphql` so that an adventure issued by it is verified by the code that issued it. That bridge carries a change of the engine; it cannot carry a change of the wire shape itself, which this is: in the deploy that ships it, the previous route speaks the old positional schema, so a client of this version that is refused with `EngineUpdated` on the current route gets a validation error from the previous one, and an adventure open across the deploy can be neither submitted nor discarded until the next deploy moves the previous route to this schema, after which the client discards it with nothing credited. Accepted as the cost of the one change of this kind, stated on the pull request; in `prod` the open adventures are the owner's, so the release is made with none open.

## Considered and not chosen

- **A code in `extensions` on a `GraphQLError`, the shape the hub had.** Apollo's older documented shape and still correct. Rejected because the refusals a player can get were strings the client had to know, outside the contract, and each refusal's fields (`short`, `missing`, `adventureId`) were untyped bags; a union per mutation puts every refusal into the printed schema, typed, read by `__typename`, and the two tiers of error, data for the game's refusals and `errors` for what is not the game's business, follow Apollo's "Errors as data" guide (read 2026-10-24 and again 2026-11-02).
- **One refusal type per mutation per code**, keeping `NOT_FOUND`, `NO_SUCH_JOB`, `PARTY_SIZE`, `NOT_YOUR_HERO` and `NO_SUCH_ADVENTURE` as types. Rejected because none names anything the player did or can do; each would have carried a client mapping that said nothing useful, and a type per mutation would have duplicated `InsufficientResources`, `Requires` and `Conflict`.
- **Holding `require-nullable-result-in-root` back for `version` and `heroesSeenAt`** rather than making two query fields nullable. Rejected: the rule's reason, one field's failure not nulling the response, holds for a query as for a mutation, and the client's cost is two null checks.
- **Renaming the engine's values to `UPPER_CASE`** so that the wire form and the engine's coincide and no mapping is needed. Rejected because a GraphQL enum value must be a Name, so `heroes-hall` and its four siblings cannot travel as they are whatever the convention; the mapping is therefore forced for the facility kinds and costs nothing to apply to every set, and both tools exist for it (Pothos's `value` on an enum member, GraphQL Code Generator's `enumValues` for Issue-156). Renaming would instead have meant a migration of stored data in `dev` and `prod` (`unitType` on every hero and snapshot, `material` on every holding and ledger key, the facility kind in a sort key), a normalizer for every stored timeline, which the client promises to play whatever its version, and a lowercasing step for routes and art paths. The hub's own `HeroStatus` and `AdventureStatus` are stored in `UPPER_CASE` because they were born as API values with no other home; a set the engine owns is stored in the engine's form and translated at the edge.
- **A shim for one release that sends the previous route the old document shape** when the current route answers `EngineUpdated`. Rejected because it is code for a schema the client no longer knows, deleted after the next release and never run again, to save adventures that are the owner's own test runs; the next change of the wire shape, if one comes, decides again with its own cost.
- **A `Refusal` base class registered as the plugin's default type**, so that any thrown refusal became data without naming it on the field. Rejected because the field's list is the contract: the printed union says exactly which refusals a mutation can give, and a function that throws one the field does not name is a defect the tests catch as an error in `errors`, not a silent new member.
