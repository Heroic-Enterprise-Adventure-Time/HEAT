# 0024: Browser sign-in: managed login on a custom domain, the code grant with PKCE through oidc-client-ts, one public client per stack with rotating refresh tokens

- **Status:** Decided. Amended on 2026-10-20 by Issue-86: a sandbox stack's browser client also offers the pool's own email and password sign-in beside Google, so that the agent's session browser signs in as a test user without Google; `config.json` says so with `passwordSignIn`, and the client then shows the managed login page instead of skipping it. `dev` and `prod` stay Google only. Amended on 2026-10-21 by Issue-96: sign-in returns to the in-app path that sent a signed-out player home, carried in the library's custom state; the redirect URI stays the origin. The hub no longer reads the email claim, per 0043.
- **Date:** 2026-10-18
- **Settles:** the overview's working assumption that "the browser signs in with the authorization code flow and PKCE, and the API validates the tokens", and the shape of the browser app client that 0018 and 0022 left to Issue-46.

## Decision

**Where a player signs in.** Through the pool's managed login on a custom domain, `auth.<zone name>`, the same shape in every environment: `auth.heat-sb.dcg-games.com`, `auth.heat-dev.dcg-games.com`, `auth.heat.dcg-games.com` (`terraform/modules/login-domain`, 0022 as amended). Google is the pool's one provider (0018 as amended), so the client sends the browser to the authorize endpoint with `identity_provider=Google` and the managed login page, whose one control would be a Google button, is not shown. A sandbox stack is the exception (Issue-86): its client also has the pool's own users as a provider, the page shows an email and password form beside the Google button, and the client leaves `identity_provider` out so that the page is shown and a person can still choose Google. The form is for the base's test users; the pool creates no user and recovers no password by itself (decision 0022), so the form signs in and does nothing else.

**The grant.** The authorization code grant with PKCE, the one the Cognito guide recommends for public clients, performed by `oidc-client-ts`, an OpenID Connect relying-party library with no framework dependency, wrapped in one Angular service (`packages/client/src/app/session.ts`). The library generates the verifier and the state, exchanges the code at the pool's token endpoint, which answers browsers cross-origin, keeps the tokens in session storage, and renews them with the refresh token before they expire. A deep link opened signed out (Issue-96) is kept by the camp's guard and sent as the library's custom `state`, which it holds in session storage with the verifier and gives back with the user, never in a URL; after the callback the session puts the path in the address bar for the router's first navigation, if it is a path of the page and nothing else. The redirect URI registered on the client stays the origin. The endpoints are given to it from `config.json`, so no discovery request is made; the authority is the pool's issuer, which is what the tokens name and what the API's JWT authorizer verifies against. Sign-out forgets the tokens and leaves through Cognito's logout endpoint with `client_id` and `logout_uri`, which the library's generic sign-out does not match.

**The client per stack.** One public app client per stack in the shared pool (`terraform/modules/environment/sign_in.tf`), `<prefix>-browser`: the code grant only, the scopes `openid email profile`, Google as its only provider in `dev` and `prod` and Google with the pool's own users in a sandbox stack (the module's `password_sign_in`, a literal of each root), callback and sign-out URLs the stack's hostname and `http://localhost:4200`, so that the Angular dev server signs in to a real stack. A managed login branding style with Cognito's provided values, because a client created through the API has none and the login page needs one. The JWT authorizer accepts two audiences: this client and the base's `ci` client, whose tokens the stack test carries.

**Token lifetimes.** Access and ID tokens of one hour, Cognito's default and the `ci` client's; a refresh token of 30 days, Cognito's default, with refresh token rotation on and a grace period of ten seconds. Rotation is incompatible with the `REFRESH_TOKEN_AUTH` flow, so the client's explicit flows name `USER_SRP_AUTH` alone, the one flow the API requires to be named that reveals nothing a browser cannot already do; nothing uses it.

**What the client knows.** `config.json`, written beside the build by the apply job from the stack's outputs: `graphqlPath`, `userPoolId`, `clientId`, `loginHost`, `passwordSignIn`, and since Issue-113 `version`, the deploy's version of decision 0030. It is read before the application starts; a page that cannot read it says so instead of failing. On the dev server, `proxy.conf.mjs` fetches it, and `/graphql`, from the branch's stack, found from the issue number in the branch name.

**Which token the API gets** is Issue-15's call: the authorizer accepts the ID token's `aud` and the access token's `client_id` alike, and the hub reads the email claim when it is there, which only the ID token carries.

## Considered and not chosen

**Cognito's prefix domain**, `<prefix>.auth.us-east-1.amazoncognito.com`. The first shape of Issue-46's first pull request. Same price, no record or certificate of HEAT's, and the guide says it has little visible effect when every sign-in is a third-party redirect. The owner chose the custom domain for every environment on 2026-10-17: a sign-in host under the game's own domain, and no dependence on a region-wide prefix being free, which `heat` is not. The cost is a placeholder A record at the sandbox zone's apex, for Cognito's check that the parent resolves, and a module composed after the environment module in `dev` and `prod`, where the parent record is the site's.

**The flow written by hand** with the Web Crypto API: PKCE, state, the code exchange and the refresh are a few hundred lines, and a showcase could show them. Rejected because the guide's own instruction is to handle the token endpoint with an OpenID Connect library, and sign-in is the one place where a small mistake is a security hole rather than a bug.

**An Angular-specific library**, `angular-oauth2-oidc`. Mature, but it peer-depends on the Angular major and moves with it; `oidc-client-ts` depends on nothing but `jwt-decode` and is unaffected by `ng update`.

**AWS Amplify's Auth category.** It does the redirect flow against Cognito and much else; the rest is weight the client does not need, and its configuration model competes with `config.json`.

**Showing the managed login page.** With Google as the only provider the page is one button. The authorize endpoint with `identity_provider` is the guide's own test URL and the same flow; the branding style still exists, for the day a second provider or a password form is wanted.

**Password sign-in in `dev` too** (Issue-86). dev's pool has test users and its `ci` client accepts their password, so a form there would be the same credential behind a second door. Not chosen: dev's records are players' as well, nothing in a session needs to sign in to dev in a browser, and the form would be the one difference between dev and prod's login pages, which dev exists to rehearse.

**A second app client per sandbox stack for the password**, leaving the Google client untouched. Two clients, two callbacks and two sets of tokens for one page, and the client would need to choose between them. One client with two providers is what managed login is built for.

**A stricter password policy for the test users** (Issue-86). The pool's policy is Cognito's default, eight characters with all four classes; NIST SP 800-63B rev 4 asks for at least 15 where a password is the only factor, and for a blocklist, which Cognito offers only on the Plus plan. Considered and not chosen by the owner on 2026-10-20, from what the password protects: a test user's game records in a sandbox stack. It grants no AWS access, reaches no player's records, and the same password already works through the `ci` client's API, so the form adds no new way to use it. The lockout below limits guessing. If the test users ever guard anything else, this is reopened.

**Discovery from the issuer** instead of the endpoints in `config.json`. One request fewer per page load, and a deterministic set of endpoints; the issuer's discovery document names the same ones.

**Local storage for the tokens.** Survives the tab, and so survives into any script that ever runs on the origin. Session storage is the library's default and enough for a game; Issue-58's Content-Security-Policy is the other half of that defence.

**No refresh token rotation.** The guide calls rotation "a security best practice"; what it costs is the `REFRESH_TOKEN_AUTH` flow, which the browser does not use, and a ten-second window for a second tab.

**Longer tokens.** One hour and 30 days are Cognito's defaults and a game needs no more; a player who returns after a month signs in with Google again, which is a click.

## Facts checked

All read on 2026-10-17 and 2026-10-18.

- **The token endpoint** (Cognito developer guide, "The token endpoint"): "The token endpoint returns an `Access-Control-Allow-Origin: *` response header. You can call the token endpoint cross-origin from a browser-based application. For example, you can complete an authorization code grant with Proof Key for Code Exchange (PKCE) from a public client"; "Handle token requests with an OpenID Connect (OIDC) library in your application"; the refresh grant "Returns a new refresh token with new ID and access token when refresh token rotation is active".
- **App clients** (the guide, "Application-specific settings with app clients"): "As a best security practice in public-client apps, activate only the authorization-code grant OAuth flow, and implement Proof Key for Code Exchange (PKCE)"; callback URLs must be HTTPS "except for `http://localhost` for testing purposes only"; a public client "does not have a client secret".
- **Refresh tokens** (the guide, "Refresh tokens"): default expiry 30 days, settable "between 60 minutes and 10 years"; rotation "reissues a refresh token within the same fixed validity window"; "you must disable this authentication flow [`REFRESH_TOKEN_AUTH`] in your app client"; the grace period is "up to 60 seconds"; "As a security best practice, enable refresh token rotation on your app clients". The API reference, `CreateUserPoolClient`: without `ExplicitAuthFlows` a client "supports `ALLOW_REFRESH_TOKEN_AUTH`, `ALLOW_USER_SRP_AUTH`, and `ALLOW_CUSTOM_AUTH`", which is why the flows are named.
- **The branding style** (API reference, `CreateManagedLoginBranding`): "To create a new style with default settings, set `UseCognitoProvidedValues` to `true` and don't provide values for any other options"; a client may have one style, replaced by deleting it.
- **The custom domain** (the guide, "Using your own domain for managed login"): in 0022's amendment and the sandbox base's README.
- **`oidc-client-ts`** (npm, 3.5.0, published 2026-03-13): one dependency, `jwt-decode`; no install script. Its `UserManager` takes `metadata` in place of discovery, performs PKCE for `response_type: "code"`, stores the user in `sessionStorage` by default, and with `automaticSilentRenew` uses the refresh token when one is present, taking a rotated refresh token from the response.
- **The provider** (hashicorp/aws 6.69.1): `aws_cognito_user_pool_client` has `refresh_token_rotation` with `feature` and `retry_grace_period_seconds`, and `read_attributes`; `aws_cognito_managed_login_branding` has `use_cognito_provided_values`.

Read on 2026-10-20 for Issue-86:

- **What managed login shows** (the guide, "Configure authentication methods for managed login"): "the configuration of your user pool automatically sets the handling of managed-login authentication flows"; with a SAML provider and "local user pool login" assigned to a client, "your managed login pages display authentication-method prompts and a button for" the provider; "The self-service account recovery setting of your user pool determines whether your sign-in pages display a link where users can reset their password"; "When MFA is off or optional in your user pool, your sign-in pages don't prompt to set up MFA". Passwordless and passkey sign-in need `ALLOW_USER_AUTH` on the client (the guide, "Authentication"), which this client does not name.
- **Sign-up and recovery stay closed** (API reference, `AdminCreateUserConfigType`): with `AllowAdminCreateUserOnly` true "only administrators can create new user profiles"; (the guide, "Passwords, account recovery, and password policies"): "The value `admin_only` turns off self-service account recovery". Read back through the audit role the same day: administrator-only creation, MFA off, `admin_only` recovery, the default password policy, and `PASSWORD` as the only first factor.
- **Guessing** (the guide, "Things to know about authentication with user pools"): "After five failed sign-in attempts with a user's password, regardless of whether those are requested with unauthenticated or IAM-authorized API operations, Amazon Cognito locks out your user for one second", doubling with each further failure to about 15 minutes.
- **Observed on `heat-sb86`** the same day, since the guide does not say which explicit flow managed login's password form needs: with `COGNITO` and `Google` on the client and `ALLOW_USER_SRP_AUTH` its only explicit flow, the login page shows an email field, a password field and "Sign in with Google", and no sign-up or forgot-password link; `player1` signs in with it and lands back on the stack and on `http://localhost:4200`. `dev`'s login page shows only "Sign in with Google".
- **The password guidance** (NIST SP 800-63B rev 4, section 3.1.1.2): a minimum of 15 characters for a password "used as a single-factor authentication mechanism", no composition rules, rate limiting, and a blocklist check when a password is set.
