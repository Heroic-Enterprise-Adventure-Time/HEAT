# The adventure loop

How an adventure is started, played, verified and replayed: the seed and the snapshot, the override log, one version per deploy, and what each flow writes. The game's side is `docs/design/game.md`, "The adventure loop", and `docs/design/battle.md`; the first cut's shape is decision 0030. The services and the tables these flows use are in `docs/architecture/overview.md`, "Services and data"; this was a section of that document until Issue-282.

Each item carries a status: **Decided**, **Working assumption** or **Open**, as `docs/design/game.md` defines them. An item marked **Built** names the issue that built it, and one marked **not built** the issues that will (`docs/README.md`, rule 15).

## The loop

- **Decided.** The server issues the seed and a frozen snapshot of the party at start, so a client cannot choose its seed. The snapshot holds each hero's id, unit type, name, sprite set, level and effective stats, and the job by its id; the job's stages, expanded from the seed (the item built by Issue-341, below), the monsters and the abilities are read from the static content by the version that issued the adventure, which is the only version that verifies it.
- **Decided.** The browser submits only its override log: each entry the simulated time it was accepted, the unit it is for, and the override. The hub regenerates the timeline, so the stored replay is always produced by the server.
- **Decided.** One version for the whole app, client, hub and engine: the commit the workflow deployed, written into the function's environment and into `config.json` (decision 0030). An adventure is stamped with it at start. The current deploy verifies only its own version; the deploy before it stays live beside it (the overview, "Environments"), reachable at a second route, and verifies the adventures it issued. A submit of another version is refused with `EngineUpdated` and the current version; the client then tries the previous route, and the same refusal there means the adventure is too old: the client asks the hub to discard it, which clears the open item and marks the record discarded, crediting nothing (but a caravan's cargo, which its discard returns: decision 0059, built by Issue-354), and tells the player. So an adventure survives one deploy and not two. On `prod` that is two releases back to back; on `dev` two merges, which is ours to live with.
- **Decided.** The client sends its version on every request, and every response says when it differs from the hub's, the answer to a request the hub refuses before running it included: a document that asks for a field a newer schema has dropped is refused at validation with HTTP 400, the flag is on that refusal, and the client reads it there, which is how a tab loaded before such a deploy hears of it (Issue-339, the review of PR-345). The client reloads itself to the new deploy, at once with no adventure open and otherwise once the adventure is over, waiting until the result is shown, so a player mid-adventure when a deploy lands finishes on the client they loaded and submits to the previous route; a reload, not a prompt, by the owner's call on Issue-115. A tab reloads away from a version only once, so a page still outdated after its reload, as when `config.json` and the hub are briefly out of step during a deploy, stays as it is rather than reloading in a loop. A push over the live channel comes with the channel.
- **Decided.** The engine's own clock and stages. Every fight and gather stage carries its own time limit in the job's content; reaching it ends the adventure as a retreat, so no run can stall (battle.md). The engine stamps the timeline with a schema version. A change to the events' shape or meaning moves it, and a timeline stored under another version is "replay unavailable": the client compares the stored version with its own engine's and says so in place of playing it. None is migrated (2026-11-10, Issue-283, decision 0051; the first cut left this to be decided when it happened). The version is 3, since Issue-339 (decision 0058).
- **Decided.** Determinism is a property within one version, and every adventure is fixed to one: the engine's test is that a run stepped by wall-clock time and the replay of its override log stepped event by event produce the same timeline and result. Nothing watches for a change to the timeline across versions, because nothing is ever verified across them; a replay is a log of what the verifying version did, and makes no decisions of its own.
- **Working assumption.** The one-adventure rule is one conditional item per player in DynamoDB. Starting an adventure puts it if absent, or returns the one already open. Settlement deletes it in the same transaction that credits rewards. Proven in the spike under concurrent starts.
- **Built (Issue-112).** The adventure engine in `packages/engine/src/adventure/`: `AdventureEngine` runs a job's stages on one clock with the battle engine's stepping API, each fight and gather a `CombatEngine` seeded `<seed>#<stage>` with its events shifted onto the adventure's clock; the party orders, press on and retreat, in the one override log beside the forced actions, an order stamped at the step that took it up; a retreat attempted in a fight with its own seeded generator and certain at a stage's end; and `replay(snapshot, seed, overrides)`, which returns the timeline, stamped with its schema version, and the result settlement reads. The snapshot (`AdventureSnapshot`), the jobs, the retreat rule and the XP threshold table (`LEVEL_XP`, `levelForXp`) are in the engine; the battle engine gained a retreat hook and a carry limit. The determinism test steps both jobs by wall-clock frames with clicks and orders and checks `replay` of the log gives the same timeline and result.
- **Built (Issue-113).** Starting, `startAdventure` in `packages/hub/src/start.ts`, its input the location, the job and the party: an open adventure refused with `AdventureOpen`, naming it; the job on the location's board and one to four heroes, each the player's, or `BAD_USER_INPUT`; each at that camp (`HeroNotHere`), alive (`HeroDead`, `HeroRetired`) and on no adventure (`HeroAdventuring`). The snapshot is the engine's `AdventureSnapshot`, its stats the unit type's, since levels add none yet and there are no picks; the seed and the id are random UUIDs. One transaction puts the open-adventure item if absent and the record (location, job, snapshot, version, start time, seed, status) if new, and marks each hero with the adventure's id on the condition that it is alive, at the location and on no adventure, so a racing start, retire or death fails one side; a start that loses reads again and answers with the open adventure or the hero's reason. `retireHero` refuses a marked hero with `HeroAdventuring`, as a condition in its transaction too; the owner's rule of 2026-10-22. `Adventure` exposes the location, the `job`, the typed `snapshot` and the `version`, and `me.openAdventure` reads the record. The deploy's version is `HEAT_VERSION` on the function and `version` in `config.json` (the overview, "Environments"); a request whose `heat-version` header names another version gets `extensions.outdated: true` on its response, errors included, and one without the header is not flagged. Proven by data-layer tests of every refusal, of concurrent starts with shared and separate heroes, and of a start racing a retire; the stack test starts "Wolves on the mill road" with the villager and checks the open adventure and its version against `config.json`, the refusals and the flag, then settles through the spike's `settleAdventure`, which now clears the party's marks, until Issue-114 replaces it.
- **Built (Issue-114).** Submitting, `submitAdventure` in `packages/hub/src/submit.ts`, its input the adventure and the override log: another player's adventure is `BAD_USER_INPUT`, as if it did not exist; a settled one answers as it is, so a repeat pays nothing and still gets the result; a discarded one is `AdventureDiscarded`; one issued by another version is `EngineUpdated`, carrying the hub's version. The log comes in as flat `OverrideInput` entries, checked into the engine's entries (a hero of the party, a whole-millisecond time, at most 2,000), and replayed with `replay` from the record's snapshot and seed; a log that differs from the one the replay keeps is logged, not refused, because a client resumed with a newer engine submits one honestly and the issuing version's replay is the result either way. The timeline goes to `<prefix>-replays` as `<adventureId>.json` with `If-None-Match: *`, so it is written once; a submit that finds one stored, from a submit that lost its transaction or raced this one, replays that timeline's log instead, so the record's result and the stored replay always agree. Settlement then reads the camp, its holdings and the party and writes, in one transaction (`Repository.settle`): the open item deleted on its adventure id; the record `SETTLED` with its result and time on the condition that it is open, and, since Issue-289, with the keys that put it in its job's replays (`docs/architecture/camps.md`); the camp's warehouse level checked against the one the cap came from, and its living count decremented by the dead on the condition that it covers them; each survivor's XP and its level from `LEVEL_XP`, never lowered, its mark removed and its sighting refreshed; each dead hero `DEAD` on the condition that it was alive, its mark removed and its sighting deleted; each holding written with its credit up to `warehouseCapacity` on the condition that its balance is the one read; one ledger entry per material, `LEDGER#<adventureId>#credit#<material>`, with the credit and what the cap lost; and, since Issue-288, the adventure's item in its location's feed, `LOCATION#<location>` / `DONE#<settledAt>#<adventureId>`, whose fields are in `docs/architecture/camps.md`; and, since Issue-351, an item for each unlock the run earned, written only where the player holds none (the item built by Issue-351, below). A balance or the warehouse that moved in between is read again, three times at most, then `Conflict`. The result on the record and the response: the outcome, each stage's ending, the rewards, what was credited and what was lost, each hero's XP gained, XP, level, health and death, and, since Issue-351, the unlocks the run earned. Discarding, `discardAdventure` in `packages/hub/src/discard.ts`: one transaction deletes the open item, marks the record `DISCARDED` on the condition that it is open and the caller's, and removes the party's marks, crediting nothing but a caravan's cargo, which it returns to the camp the caravan left up to its cap and lets go of the slots held at the destination (decision 0059, built by Issue-354); an adventure that this deploy or the previous one issued is refused with `AdventureVerifiable`, because it can still be submitted and a discard would undo its deaths (the owner's rule of 2026-10-22); the previous deploy's version reaches the function as `HEAT_PREVIOUS_VERSION` (the overview, "Environments"). `adventure(id)` answers a settled adventure to any signed-in player, for its replay, and an open or discarded one only to its own; `replaysOf(job)` lists a job's settled adventures the same way (Issue-289); its `timeline`, a `JSON` scalar, is read from the bucket. `version` answers the route's deploy. The spike's `settleAdventure` and the engine's `rewardsForSeed` are gone. Proven by data-layer tests with the bucket in memory (`MemoryTimelines`), the S3 store by the stack test: a completed job, a repeated and a racing submit, the cap part full and full, a balance moved between the read and the write, a death, `EngineUpdated`, a stored timeline that wins, and the discard's refusals and its close. The stack test plays "Timber from the near woods", because a lone villager loses "Wolves on the mill road" on every seed (Issue-126).
- **Built (Issue-115).** The client's start, in `packages/client/src/app/`. The job board is its own panel, `/camp/<location>/job-board`, listing the jobs the location's board posts with their pay and, since Issue-339, their bonus XP; a job's detail, `/camp/<location>/job-board/jobs/<id>`, says its description, its pay, each resource beside the camp's balance of it and the room left under the warehouse's cap, its bonus XP, and what a retreat keeps in words (`camp/panels/job-words.ts`), and since Issue-339 neither its stages nor a yield (decision 0058), then picks one to four of the camp's living heroes in no order, and Depart calls `startAdventure` and goes to `/adventure`; a refusal is shown in place under Depart, in the player's words for each code. `/adventure` shows the open adventure's job and party from its snapshot, and sends the address to the camp when none is open; the header bar's "Adventure in progress" and an entry at the end of the facility menu, with `art/icons/adventure.png`, lead there while one is open. - **Built (Issue-15, the play).** The client plays the open adventure at `/adventure`, a route loaded on first use. `AdventureRun` (`packages/client/src/app/adventure/run.ts`) runs the engine from the record's snapshot and seed, stepped by wall-clock time at 1×, 2× or 4× and paused at will (`play.ts`), and keeps the override log off the engine's own events, `action-overridden` and `order`, so the log it submits is the one the engine keeps. Each hero's unit type's action list is its force buttons, a forced action shown as queued until the hero's next turn uses or drops it; press on and retreat are the party's orders; a stage's last ten seconds are counted down. The log and the time reached are saved in `localStorage` under `heat.adventure.<id>` whenever the log grows and every simulated second; a run with a saved log steps event by event to the saved time, handing each entry in before the step that reaches it as `replay` does, and plays on, and one without starts again from the same seed. At the end the client submits the log to `/graphql`, on `EngineUpdated` to `/previous/graphql`, and on `EngineUpdated` there too discards it and says it was lost to a game update (`Game.submitAdventure`); a failure to reach the hub keeps the log and offers to try again. The result is a dialog over the battle as it ended (Issue-441, decision 0065): how it ended as its title, the rewards and each hero's XP counted up (`Gains` in `primitives/gains.ts`), what the cap lost, any level gained, the dead, and one button, OK, to the camp the party left from. The player is read again at once, and a waiting reload (`Updates`) holds until the player leaves the result, by that button or any other route, which puts the result away. A hero on the adventure is kept out of the camp scene, and the warehouse's panel lists the camp's stock against its cap, so the settlement shows. The second pull request of Issue-15 draws it: the battle scene of decision 0028's amendment, the clock held at each entry while the scene brings everyone on, and the replay, which plays the stored timeline in the same scene with the same pause and speeds, with no engine (`TimelineRun` in `run.ts`); since Issue-441 a replay is played on the replay's page alone (Issue-290, below), and the adventure's page no longer reads a timeline.

- **Built (Issue-339).** What an adventure yields (decision 0058; battle.md, "What an adventure yields"), in all three packages. - **Built (Issue-344).** The scene's picture of a drop (decision 0058's first amendment; battle.md, "A drop shows twice"), in `packages/client/src/app/adventure/battle/`, with no change to the engine, its events or the timeline. - **Decided.** Resuming replays the override log so far up to the saved point with the client's own engine, whatever version issued the adventure; the result is whatever the issuing version verifies at submit. The log in progress is kept in the browser's storage, keyed by the adventure id. If it is lost, the run restarts from the beginning with the same seed.

## What verification proves

The client holds the seed, so a modified client can try override sequences offline and submit the best one. Verification proves that the outcome is reachable under the rules with that seed. It does not prove that a person played it live. Closing that gap would mean the server revealing randomness stage by stage, which is the per-step traffic this design avoids.

An enemy's drops are rolled from the seed, the stage and the enemy alone (decision 0058, Issue-339), so trying override sequences cannot improve a roll; what it can still change is which heroes are standing when an enemy goes down, which is the game. Nor can it change who a job sets against the party: a job's stages are expanded from the seed alone, before the first one runs (Issue-341).
